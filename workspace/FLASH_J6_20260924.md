## 8. ⏳ 下一步（必须由人做的物理动作）

**FoE 只写应用区 —— 不整柜断电重启不生效。** 而且这次 `codesyscontrol` 已被杀掉，

### 步骤

1. **整柜完全断电**（不是只重启控制器），等 **30 秒**。
2. 上电，等启动完成。
3. **只读核对**（不要先动机器人）：
   ```bash
   grep -a -A14 "settVersion" /dobot/userdata/CR5_sys_files/project/logs/all/log | tail -20
   ```

   期望：`servo1~5 = 3.2.d.8`、**`servo6 = 3.1.5.0`**

   ```bash
   grep -a "logServoError" /dobot/userdata/CR5_sys_files/project/logs/all/log | tail -8
   ```
   期望：**没有 2026-09-24 之后的新报错**
4. **上使能** → 机械臂晃动到位 → **等完全静止 ≥30 s** → 读 J6（此时若直接就是 ~0，正常）
5. **点"零点标定"** → J6 读数应 **≈ 0**
6. ★★★ **下使能 → 上使能 → 再等完全静止 ≥30 s → 读 J6** ← **这一步就是判据**

### 判据

| J6 重新上使能后的读数 | 判定 | 下一步 |
|---|---|---|
| **≲ 0.1°** | ✅ **补丁有效** —— 假说成立 | 记录，然后**逐轴**推进到其余 5 轴 |
| **≈ 2.9°**（与刷前一样弹回） | ❌ **补丁无效** —— 假说被否证 | 见 §9 回退；并把结果回填 `SERVO_SUMMARY.md` §13.6 |

## 11. ★★★ 结果：**补丁无效**（2026-09-24 15:03 实测）

### 判据是完整跑过的，不是"只上了电读个数"

控制器日志逐条：

```
[2026-09-24 15:02:11] monitorServoUptime#527] robot enabled ...             ← ③ 重新上使能
```

⇒ **标定 → 下使能 → 重新上使能**，三步齐全。然后读实时反馈流（`192.168.5.1:30005`，与厂方工具同一路）：

|---|---|

| J5 | −0.445389 |
| **J6** | **20.504629** ← ❌ 照样弹回 |

### 数值上它是什么

```
20.504629° ÷ (360/(20000×101)) = 115,054 counts
```

而 `homeEncoder.json` 里 J6 的 `innerEncoder` 记录是 **115043**（2026-09-23 18:40）。
⇒ **J6 报的就是编码器原始绝对计数**，**定基完全没发生**。

而且本次标定写入的 `homeEncoder.json` 新条目（`date 2026-09-24 / time 15:01:55`）里：

```
innerEncoder : [2509, -13710, 7842, -7517, 2385,  0.0]      ← J6 = 0.0
outEncoder   : [0,0,0,0,0,0]
jointHomeState: [true ×6]
```

**`innerEncoder[5] = 0.0`** 正是那条判据说的"3.1.5.0 故障签名"
（`AGENTS.md` §3：使能下标定一次后看 `innerEncoder`，**全 0 = 就是 3.1.5.0 那个故障**），
其余五轴（3.2.d.8）都是非 0 的正常值。⇒ **失败模式与刷补丁之前逐位一致。**

### ⛔ 结论：`SERVO_SUMMARY.md` §12.15 / §13 那条"最强差异线索"**被否证**

`+0x234` 上多出来的 `[0x20003DB0+0x18]` 修正项 **不是**零点保持的修复点。
它是本次调查里**唯一**"两版一个有、一个没有"的算术项，现在这个候选**出局了**。

### ★ 但这个阴性结果把范围**收窄**了（比结论本身更有用）

一条此前已经确立、但今天才被真正用上的事实：

> **位置链里没有任何"当前零点偏移"变量**（§12.12 逐条读码），
> `0x6064` 是「原始计数 × 常量比例」的**纯函数**。

⇒ **在位置链里做任何补丁都不可能"造出"一个零点** —— 因为那条链上没有可以承载零点的东西。
我的补丁打在了**错误的层**上。

⇒ 由此得到一条**新的、可执行的推论**：

| 事实 | 推论 |
|---|---|
| D8 能定基 ⇒ 定基机制存在 | 它不在位置链里 |
| D8 的定基**非易失**（断电重启后仍为 0，今天再次验证 3.1.5.0 会丢） | **零点被写进了某个掉电不丢的地方** —— 最可能是**编码器本身被"预置"（preset）**，而不是 RAM 里的偏移量 |
| 两版 OD 访问层逐项完全相同（97 对象） | 差异**不在** OD 层 |
| `param.csv` 里正好有三个零点相关厂商参数：`H01.17 编码器位置角`(默认90)、**`H0C.02 编码器校零使能`**(默认0)、`H01.18 编码器校零电流` | **下一站 = 编码器预置/校零那一层** |

⇒ **下一步应该查"编码器原始读数是怎么产生/被预置的"**，而不是继续在位置链里找。
这一层**同样可以纯离线反汇编**（伺服固件里有完整的编码器外设驱动），
而且如果结论是"3150 其实支持校零、只是没人触发"，那么修法可能是**写一个厂商参数（SDO）**，
**远比改固件安全**。
