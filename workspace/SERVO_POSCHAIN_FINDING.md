## 42. 第二十八轮：`mode` 的来源 —— **两版逐条同构，`mode` 不是差异**（【逐条读码】）

按 §41.6 定的规矩，这一轮**先读两版对应代码块，再下结论**。

### 42.1 `mode` 的寻址形态

它不是常规的 `[rN,#imm]`，而是"**立即数当基址、轴号寄存器当索引**"：

```asm
movs r0, #0xcc
ldr  r0, [r0, r4]      ; mode = *(0xCC + 轴号*0x329)   （D8）
```
3150 对应形态是 `movs r0,#0xB4` + `ldr r0,[r0,r4]`（`0xB4 = 0xCC − 0x18`，同一个平移）。

**普查**（该 idiom，按读写分）：

| 镜像 | 立即数 | 读 | 写 |
|---|---|---|---|
| 3.2.D.8 | `0xCC` | **25** | **1**（`0x080216DE`） |
| 3.1.5.0 | `0xB4` | **24** | **0** |

**⇒ 3150 的"写 = 0"又是同一个陷阱** —— 我去读那段就发现它有。

### 42.2 ✅ 读出来的结论：两版**逐条同构**（这也是 `mode` 唯一的写入点）

D8 `0x080216D4..0x0802170C`：

```asm
080216d4: subs  r4, #0xa4           ; r4 = 源结构基址
080216d6: mov.w r0, #0x184
080216da: ldr   r1, [r0, r5]        ; 源 +0x184
080216dc: movs  r0, #0xcc
080216de: str   r1, [r0, r4]        ; ★ 目标 mode = 源 +0x184
080216e0: mov.w r0, #0x188
080216e4: ldr   r1, [r0, r5]
080216e6: movs  r0, #0xd0
080216e8: str   r1, [r0, r4]        ; ★ +0xD0 = 源 +0x188
080216ea: mov.w r0, #0x18c
080216ee: ldr   r1, [r0, r5]
080216f0: movs  r0, #0xd4
080216f2: str   r1, [r0, r4]        ; ★ +0xD4 = 源 +0x18C
080216f4: mov.w r0, #0x190
080216f8: ldr   r1, [r0, r5]
080216fa: movs  r0, #0xd8
080216fc: str   r1, [r0, r4]        ; ★ +0xD8 = 源 +0x190
080216fe: mov.w r0, #0x194
08021702: ldr   r1, [r0, r5]
08021704: str.w r1, [r4, #0xdc]     ; ★ +0xDC = 源 +0x194
08021708: adds  r0, r0, #4
0802170a: ldr   r1, [r0, r5]
0802170c: str.w r1, [r4, #0xe0]     ; ★ +0xE0 = 源 +0x198
```

**这是一串"从源结构逐字段搬 6 个 4 字节量"的拷贝循环**（`+0x184/0x188/0x18C/0x190/0x194/0x198` → `+0xCC/0xD0/0xD4/0xD8/0xDC/0xE0`）。

**3150 同一位置（`…63DA` 一带）逐条同构，全部偏移减 `0x18`**：

| D8 目标 | ← 源 | 3150 目标 | ← 源 |
|---|---|---|---|
| `+0xCC` | `+0x184` | `+0xB4` | `+0x16C` |
| `+0xD0` | `+0x188` | `+0xB8` | `+0x170` |
| `+0xD4` | `+0x18C` | `+0xBC` | `+0x174` |
| `+0xD8` | `+0x190` | `+0xC0` | `+0x178` |
| `+0xDC` | `+0x194` | `+0xC4` | `+0x17C` |

**⇒ `mode` 的整条写入链，两版逐条同构。**
**⇒ `mode` 不是版本差异。**（这也是本次调查里**第一个用【逐条读码】得出的否定结论**。）

### 42.3 `mode` 的**来源**在固件之外

查"谁写源字段 `+0x184`"：
* 该 idiom（`movs r0,#0x184` + `[r0,rY]`）在**两版都是 0 处**；
* 全镜像 `#0x184]` 的访问里，**唯一真正的内存访问就是 `0x080216D6` 那次读**，
  其余全是 `ldr rX,[pc,#0x184]`（字面量池）与 `[sp,#0x184]`（栈）。

**⇒ `+0x184`（源结构）在固件里从未被写入** ⇒
**它的内容由固件之外提供**（很可能是**控制器通过 EtherCAT 写下来的**，或 DMA/共享区）。

**⇒ `mode` 是"上位给的值"，不是固件自己算的。** 这一点对现场排查有用：
**若能读到 `mode` 的实际值，就能判断驱动器当前走的是哪一个位置来源分支。**

### 42.4 本轮小结与目标状态

| 项 | 结论 | 证据等级 |
|---|---|---|
| `mode` 的写入链两版是否不同 | **相同**（逐条同构，全部偏移 −0x18） | ✅【逐条读码】 |
| `mode` 由谁产生 | **固件之外**（源字段 `+0x184` 固件内零写入） | ✅【逐条读码】+【普查】 |
| `mode` 是否与两版差异相关 | **不相关** | ✅【逐条读码】 |

**⇒ 又一次印证 §41.6 的制度**：这一轮的两个普查（写=0、源字段 0 处）
**都指向一个错误方向**，是【逐条读码】把它们扭转过来的。

**下一轮**：`mode` 既已排除，剩下**经【逐条读码】确认的差异只有两个环节**
（取整实现 §29/§34、`20000` 站点 §37）。若要继续，
应回到这两个里更可疑的**取整实现**，把 §34 那两段**完整函数**读完（不只站点邻域），
确认"就近取整 vs 双精度取整"在**边界值与负值**上的具体行为差。

## 41. ⛔⛔ 第二十七轮：**§20 也有同类错误** —— 状态机的判别式失效（两个方向都失效）

§40 我发现"`+0xBA` 计数为 0"是**字段整体平移 `0x18`** 造成的假象。
本轮回头检查 §20 的"状态机在 D8 里函数体不存在"——**它用的是同类间接证据，于是也出问题了。**

### 41.1 §20 的判别式，两个方向都不可靠

§20 的判别式是：`movw rX,#0x329` 后 0x50 字节内同时出现 `[rX,#0x24]` 访问 + `cmp …,#7` + `tbb`。
（它用**字面偏移 `#0x24`** 作为条件之一 —— 这正是 §40 暴露的那类脆弱假设。）

本轮我把它放宽（窗口 0x60、只要求 `movw #0x329` + `cmp` + `#7`）：

| 镜像 | 命中 |
|---|---|
| 3.2.D.8 | **2 处**：`0x0801479C`、`0x080207E6` |
| 3.1.5.0 | **2 处**：`0x08013D2A`、`0x080157B8` |

### 41.2 但**放宽后的命中也是假阳性**

逐个读：
* D8 `0x0801479C` —— 是一条 `tbb [pc,r7]`，**紧随其后是未对齐的 fall-through 数据**
  （`stm r2!,{…}` / `lsrs r5,r0,#0x1c` / `adr r3,#0x1c8`），**不是状态机**；
* 也就是说：**窗口放宽后，`tbb` 与"前置的 movw/cmp"并不构成证据** ——
  它们只是碰巧落在同一段地址范围里。

⇒ **§20 的判别式：收紧时给出假阴性（§20 本身），放宽时给出假阳性（本轮）。**
**这个判别式整体不可用。**

### 41.3 用"直接比对"审计 §20（唯一可靠的办法）

我用 §34 里验证过的办法：**把 3150 的状态机（`0x08015778`，`0x140` 字节，131 条指令）
的指令形态整段拿去 D8 全镜像滑窗匹配**（助记符 + 操作数形态，寄存器名与立即数归一化）。

结果：**没有任何 >85% 的匹配**（唯一两个"100%"是长度退化为 1 条的畸形匹配，无意义）。

> ⚠️ 这个否定**也偏弱**：滑窗用 capstone 逐 2 字节解码，遇到数据段会解出长度不一的序列，
> 使比对长度错位。**它不能作为"不存在"的强证据。**

**⇒ §20 的结论（"D8 里该状态机整体不存在"）应降级为「未证实」，而不是「已证明」。**
目前只能说：**用我现有手段在 D8 里找不到它的对应物**（`tools/servo_blockdiff.py` 的报告里
`0x0801580C..0x08015A64`、`0x08015BBE..0x08015DD2` 是 3150 侧的变更区，
提示那块**确实**与 D8 不同，但"不同"不等于"D8 没有"）。

### 41.4 把两轮的错误合并成一条教训

§39→§40（`+0xBA`）与 §20→§41（状态机）是**同一个错误的两次出现**：

> **用"某字面偏移的计数/形态"去判"某段逻辑在某版里是否存在"，是不可靠的。**
> 因为：① 结构体内字段会**整体平移**（本次测得 `0x18`）；
> ② 依赖字面偏移的判别式在收紧/放宽时会分别给出**假阴性 / 假阳性**。

**⇒ 判"有无"的正确做法**（本次唯一验证过的）：
**读那段代码本身，并到对方镜像的对应代码块里逐条比对。**
（§40 就是这么发现错的一 一 它比任何计数规则都可靠。）

### 40.2 为什么会误判（**第 7 类静默错误**）

我之前的规则是"**RAM 地址没有全局位移**"（§22，`+0` 命中 409、`+0xF0` 命中 205）。
那条规则是**在 RAM 基址层面**测的，**不适用于"同一个结构体内的字段偏移"**。

**⇒ 结构体内部的字段是会整体平移的**（这里是 `0x18`），
所以我用"绝对偏移计数"去判"某字段是否存在"，**必然覆盖不了这种情况**。

而且我的**正负对照选得不对**：`0x31F`/`0x1AF`/`0xBB` 三个对照都**恰好属于没有平移的那批**
（`0x1AF`/`0x31F` 两版都在同一偏移），于是对照全过、结论照错。

**⇒ 第 7 类静默错误：**
> **"某偏移在一版里计数为 0"不能推出"该字段不存在"——
> 必须先排除"该字段整体位移了"这一可能。
> 判据：去该字段所在函数的对应代码块里**逐条比对**，看它是否只是换了偏移。**

**（这条与 §39 的教训恰好相反方向：§31 是"自我否定过头"，这次是"自信过头"。
两者共同点都是：用**间接指标**（计数、形态）替代**直接证据**（读那段代码）。）**

### 35.1 D8 的完整数据流（两个分支结构相同、符号相反）

```asm
; ---- 分支甲：0x080154B4（条件 bge，+0x18 >= 0）----
ldr r0, [base+4]         ; A
ldr r1, [base+0xc]       ; B
subs r0, r0, r1          ; A - B
adds r0, r0, r6          ; + 校正量 C(寄存器)
str r0, [base+0x18]      ; ★ +0x18 = A - B + C
ldr r0, [base+0x18]
cmp r0, #0
bge  <正常>
movs r0, #0
str r0, [base+0x14]      ; ★ 负值 ⇒ +0x14 直接置 0
b    <出口>

; ---- 正常路径 0x080154D4 ----
vldr s0, [base+0x18]     ; x = +0x18（整数）
vcvt.f32.s32 s1, s0      ; float(x)
vldr s0, [rX, #0xc]      ; D
vcvt.f32.s32 s0, s0      ; float(D)
vdiv.f32 s2, s1, s0      ; ★ 比例 = x / D
vstr s2, [base+0x10]     ; ★ +0x10 = 比例（浮点）
vldr s0, [base+0x10]
vmov.f32 s1, #0.5
vadd.f32 s0, s0, s1      ; ★ 比例 + 0.5
vcvt.s32.f32 s0, s0      ; 截断
vstr s0, [base+0x14]     ; ★ +0x14 = (int)(比例 + 0.5)  ← **就近取整的整数商**

; ---- 后续 0x08015502 ----
ldr r0, [base+0xc]       ; B
ldr r1, [base+0x14]      ; ★ 刚算出的整数商
ldr r2, [rX, #0xc]       ; D
mla r0, r1, r2, r0       ; B + 商*D
ldr r1, [base+4]         ; A
subs r0, r0, r1          ; (B + 商*D) - A
str r0, [base+0x1c]      ; ★ +0x1c = (B + 商*D) - A
```

**分支乙（`0x0801551E`）结构完全相同，只是判定反了**（`ble` 而非 `bge`、
`+0x18 > 0` 时置零），所以两段互为"正/负"情形的处理。

### 35.2 这段算式的物理含义（**从算式形态推断，未证明**）

记 `x = A − B + C`、`D` 为另一个量、`q = round(x / D)`，则：

| 字段 | 表达式 |
|---|---|
| `+0x18` | `x = A − B + C`（**原始差值**） |
| `+0x10` | `x / D`（**浮点比例**） |
| `+0x14` | `q = round(x / D)`（**整数商**） |
| `+0x1C` | `B + q·D − A`（**残差 / 余数**，符号与 `x` 相反） |

两个都是整数：`q` 是**商**、`+0x1C` 是**余数**（`(B + q·D) − A = q·D − x = −(x − q·D)`）。

**⇒ 这就是标准的「整数除法的商与余数」分解**：
把 `x` 按步长 `D` 分解成 **圈数 `q`（+0x14）** 与 **圈内余量（+0x1C）**。

> **这与 §19 里 3150 的 `0x20003DB0` 结构（"商/余数对"）是同一类东西！**
> 两版**都要做"位置 → 圈数 + 余量"的分解**，只是**实现与落点不同**。

### 35.3 因此 §34 的"取整差异"有了明确语义

两版都对 `x / D` 做"就近取整得到整数商 `q`"，但：

| | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| 比例 | **单精度** `vdiv.f32` | 单精度 `vdiv.f32`（前段相同） |
| 取整 | `(int)(比例 + 0.5)` —— **单精度 + 0.5 后截断** | 提升为**双精度**，与 `0.5` 做双精度加减，再转整数 |
| 负值处理 | 由**前面的 `cmp/bge` 分支**决定（负值直接置 0） | 由**两个站点分别用软加/软减**处理 |

**⇒ 关键后果**：`q` 是**圈数**。**圈数算错 1，位置就会偏整整一圈（= `D` 对应的位移）**。
而两版的取整路径在**边界值**（`x/D` 恰好在 `.5` 附近）与**负值**上会给出不同结果。

> 我仍不知道 `x` 与 `q` 最终如何变成上报的 `0x6064`。

  **D8 把"位置分解"从集中式改成了就地式**。

**⇒ 这是目前对"两版差异"最完整、最自洽的解释。**

## 32. 第十八轮：§31 的疑问有答案了 —— **是 IEEE 双精度，但是「软件」实现**

§31.3 我提出疑问："`0x08000368` 到底是 64 位整数还是 IEEE double？" §31.7 把它列为第 1 项。
本轮用**偏置常量判据**把它定死了。

### 32.1 判据：指数宽度与偏置

读 `0x080006E2`（那个"转整数"例程）内部的常量：

```asm
080006e4: ubfx r2, r1, #0x14, #0xb      ; ★ 从 r1 取 11 位字段（双精度指数字段）
080006ee: ubfx r1, r1, #0, #0x14        ; 取 52 位尾数的低 20 位
080006f6: orr  r1, r1, #0x100000        ; 补隐含位
080006f2: movw r3, #0x3ff               ; ★ 1023 = 双精度指数偏置
080006fa: cmp  r2, r3                   ; 指数 < 偏置 → 数值 <1 → 结果 0
08000702: movw r3, #0x433               ; ★ 1075 = 1023 + 52
08000706: cmp  r2, r3                   ; 指数 ≥ 1075 → 全为整数部分
```

**⇒ 判据成立**：
* **11 位指数字段**（`ubfx …, #0x14, #0xb`）= 双精度格式（单精度只有 8 位）；
* **偏置 `1023`（`0x3FF`）** = IEEE-754 double 的指数偏置（单精度是 `127`）；
* **`1075 = 1023 + 52`** = "指数达到偏置+尾数位宽" ⇒ 该数已是整数。

⇒ **`0x080006E2` 确实是「IEEE-754 双精度 → 整数」的软件转换例程。**

## 30. 第十六轮：三个浮点子程序全部识别 —— 软浮点（soft-float）库

### 30.1 识别结果

| 子程序 | 识别 | 依据 |
|---|---|---|
| **`0x08000368`** | **双精度加法/减法** | `eor.w r0,r1,r3` 后再 `lsrs #0x1f` = **两操作数符号异或**（减法要借位）；`bic r1,#0x80000000` = 取绝对值；`subs.w/sbcs` 比较两数大小后**对调**；随后必然是指数对齐 + 尾数加减 —— 标准 soft-float `dadd`/`dsub` 骨架 |
| **`0x080004AA`** | **`dsub` 入口**（取负后转加法） | 只有两条：`eor r3,r3,#0x80000000`（翻转第二个操作数符号）→ `b 0x08000368` |
| **`0x080006E2`** | **双精度 → 整数 转换** | `ubfx r2,r1,#0x14,#0xb` = **取 11 位指数**（双精度指数字段）；与 `0x3FF`(1023，偏置) 比较、与 `0x433`(1075 = 1023+52，即 ≥2^52 全为整数) 比较；`ubfx r1,r1,#0,#0x14` + `orr #0x100000` = 取隐含位与尾数 —— 标准 `d2i` 骨架 |

⇒ **这三个都是编译器自带的软浮点（soft-float / libgcc 风格）例行程序**，
不是 Dobot 的业务代码。**这一点很重要**：它们"出现与否"反映的是**编译器如何生成这段浮点运算**，
而不是厂商写了什么。

### 30.2 因此 §29.3 的"`× 0.5`"说法要收紧

§29 我看到 `vldr d0 = 0.5` 就写成"`+0x14 = (int)(double(商) × 0.5)`"。
**读了三段之后，这个说法需要降级**：

* 常量确实加载了 `0.5`（`0x3FE0000000000000`，已复核）；
* 调用序列是：`0x08000720`(f→d) → 载入 `d0` 常量 → `bl 0x08000368`(dadd) 或 `bl 0x080004AA`(dsub) → `bl 0x080006E2`(d2i)；
* **两个站点分别用了 `dadd` 与 `dsub`** —— 若都是"乘 0.5"就不该一个加一个减。

**⇒ 更可能的解释**：这是一个**双精度加减再转整数**的表达式（例如 `(int)(x ± 0.5)`，
即"四舍五入到最近整数"的经典写法，因为 `+0.5` 或 `−0.5` 取整就是 round-half-up/down），
**而 `0x08000368` 只是被 `dsub` 复用的加法例程**。
**但我**没有**证明它是 `±0.5` 取整** —— 也可能常量 `0.5` 只是其中一个操作数。

**⇒ 准确表述（取代 §29.3）：3150 在 `+0x14` 上做的是
「(某些量) 经双精度加减后转整数」的运算，常量表里含 `0.5`。**

其中 2 处（`0x080149E0`、`0x08014A5E`）是：
除法 → **`bl 0x08000720` → 双精度常量运算 → `bl 0x08000368`/`0x080004AA` → `bl 0x080006E2` → 存 `+0x14`**。**

### 28.3 这就是差异的精确位置

| | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| 64 位除法 `0x08000222` | ✅ 有（2 处） | ✅ 有（2 处） |
| **除法之后** | **整数加减/乘加，直接存 `+0x18`/`+0x1C`** | **接一条「双精度浮点子程序链」（3 个子程序）再存 `+0x14`** |
| `+0x14` 写点 | 2 处（整数直存） | **4 处（其中 2 处经浮点链）** |

⇒ **两版共有"64 位整数除法"，但 3150 在它之后多做一条双精度浮点运算链，
D8 没有。** 这条链的三个子程序是 `0x08000720`、`0x08000368`/`0x080004AA`、`0x080006E2`
（**尚未读，下一轮目标**）；`vldr d0, [pc]` 说明带一个**双精度常量**。

### 28.4 变更区与差异点的对应（精确）

`tools/servo_blockdiff.py` 给出的、包含上述站点的变更区：

| 变更区 | 大小 | 含哪些站点 |
|---|---|---|
| **`0x0801530E..0x0801562D`** | **799 B** | D8 的两个 `bl 0x08000222` 站点（`0x080154C0`/`0x0801552A`） |
| `0x080143B4..0x08014592` | 478 B | （同函数族，含位置写入路径的一部分） |
| `0x08015140..0x080152E9` | 425 B | 同上 |
| `0x0801580C..0x08015A64` | 600 B | 3150 状态机分派区（§20） |
| `0x08015BBE..0x08015DD2` | 532 B | 3150 状态机分支区 |

⇒ **位置链上的变更区就是 `0x0801530E..0x0801562D`（799 B）这一个**，
其余两个（`0x080143B4`、`0x08015140`）属同一函数族。
**3150 侧的对应变更区在 `0x080143xx..0x08014Axx` 一带。**

### 28.5 结论（本目标的**最强候选**，仍非证明）

> **两版位置计算链的差异，精确定位在「64 位整数除法之后」这一步：**
> **3.2.D.8 直接取整数商去更新 `+0x18`/`+0x1C`；**
> **3.1.5.0 额外插入一条「双精度浮点子程序链」（`0x08000720` → `0x08000368`/`0x080004AA` → `0x080006E2`），
> 把结果写进 `+0x14`。**

**这条差异的物理意义尚未确定**（`+0x14` 是什么量、那条浮点链算什么），
但**它比 §16/§18/§20 那四组更贴合"位置计算本身"**，因为：
* 它在**位置值写入点所在的变更区**内；
* 它是**算式的结构性差异**，不是开关或状态机；
* 涉及**精度与舍入**（双精度 vs 整数），与"边界时刻归零不干净"的现象形态相符。

## 27. 结构体用量表对照：布局**相同**，只有 `+0x14` 的写次数不同

按 §22 定下的规矩（**先出用量表，再谈语义**），对 §25 涉及的两个结构体各出一张表：

| 偏移 | 3.2.D.8 `0x20003ED4` 读/写 | 3.1.5.0 `0x20003D8C` 读/写 |
|---|---|---|
| `+0x00` | 0 / 1 | 0 / 1 |
| `+0x04` | 4 / 1 | 4 / 1 |
| `+0x08` | 0 / 1 | 0 / 1 |
| `+0x0C` | 4 / 1 | 4 / 1 |
| **`+0x14`** | **2 / 2** | **2 / 4** ← 唯一差异 |
| `+0x18` | 0 / 2 | 0 / 2 |
| `+0x1C` | 1 / 2 | 1 / 2 |
| `+0x20` | 1 / 1 | 1 / 1 |

### 27.1 这张表说明什么

**两张表几乎逐格相同** ⇒

1. **两个结构体是同一个逻辑结构**（只是一版在 `0x20003ED4`、另一版在 `0x20003D8C`）——
   这符合 RAM 重排的预期，**不是不同的对象**；
2. **字段"接线"没变**：谁读谁、读几次，两版一致；
3. **唯一差异是 `+0x14` 多写了 2 次**（2 → 4）。

⇒ **再次印证 §25 的结论：差异在"算式"，不在"数据结构或接线"。**

### 27.2 `+0x14` 多写 2 次意味着什么（**推断，未证明**）

回顾 §25.2 的算式：

* **D8** 在**非正分支**里把浮点取整结果写进 `+0x14`（1 处），另有 1 处写 ⇒ 共 2 次；
* **3150** 多出的 2 次写，对应它那条 `(B × 量 − A) + C` 之后**另有一套写回**。

**最简解释**：3150 在同一个量上**做了两次不同口径的更新**（例如"原始"与"修正后"各写一次），
而 D8 只写一次有效值。

> ⚠️ **这是从"写次数差 2"推出来的解释，没有读通那两处写的具体位置与条件。**
> 按 §22 的规矩，这条**只能算假设**，下一步必须把两处写点都读出来再下结论。

### 27.3 本目标当前最强候选（汇总）

到这里，"两版差异"里**压在位置写入点上的核心算式**是：

> **3.2.D.8：整数加减 + 32 位浮点除法取整（`vcvt`/`vdiv`/`−0.5`/`vcvt`），结果写 `+0x14`/`+0x18`/`+0x10`。**
> **3.1.5.0：整数乘加 + 64 位有符号除法（子程序 `0x08000222`），结果写 `+0x1C` 并送逐轴对象 `+0xA8`；
> 且 `+0x14` 被写两次。**

**两组差异的"精度/取整语义"不同**（32 位浮点 vs 64 位整数），
在边界值上会给出不同结果 —— **这是机制相符的最强解释，但仍未证明。**

## 26. 第十三轮补：`bl 0x08000222` 已识别 = **64 位有符号除法**

§25.5 列的第 1 项做完了。

**3.1.5.0 `0x08000222` 的反汇编：**

```asm
08000222: push.w {r4, r5, r6, r7, r8, lr}
08000226: movs r4, #0
08000228: subs r6, r0, r4
0800022a: mov  r5, r4
0800022c: sbcs r6, r1, #0
08000230: bge  <被除数非负>
08000232: movs r4, #1          ; ★ 记下"被除数为负"
08000234: movs r7, #0
08000236: rsbs r0, r0, r7      ; 取绝对值（低 32 位）
0800023a: sbc.w r1, r7, r1     ; 取绝对值（高 32 位）
0800023e: subs r6, r2, #0
08000240: sbcs r6, r3, #0
08000244: bge  <除数非负>
08000246: movs r7, #0
08000248: rsbs r2, r2, r7      ; ★ 除数也取绝对值
0800024c: movs r5, #1          ; 记下"除数为负"
0800024e: sbc.w r3, r7, r3
08000252: bl   #0x080001C0      ; 无符号 64 位除法
08000256: ...                  ; 用 r4/r5 两个符号位恢复商的符号
0800025e: cmp  r4, r5
08000260: beq  <同号>
08000262: movs r5, #0          ; ★ 异号 → 商取负
08000264: rsbs lr, r0, r5
08000268: sbc.w r6, r5, r1
0800026c: cbz  r4, <…>         ; 被除数为负 → 余数取负
...
```

**⇒ 这是一个标准的 64 位有符号除法**：取两操作数符号 → 各自取绝对值 →
调用无符号除法（`0x080001C0`）→ 按符号规则恢复**商**与**余数**的符号。

### 26.1 合并进 §25 的差异表

| 项 | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| 位置核心算式 | 整数加减 + **一次 32 位浮点除法取整** | 整数乘加 + **64 位有符号除法（子程序）** |
| 精度 | 单精度浮点（32 位） | **64 位整数** |
| 取整 | 浮点 `−0.5` 后 `vcvt`（就近取整） | 整数除法（截断/地板语义） |

**⇒ 两版在位置核心量上用的是"不同精度、不同取整语义"的除法**：
D8 走**32 位浮点**，3150 走**64 位整数**。

### 26.2 这条差异为什么值得重视

1. **它是两条独立的实现在算同一个量**，不是开关差异。
2. **精度与取整语义不同 ⇒ 在边界（正好半格、或大数值）上会给出不同结果。**
3. 位置相关的量若在**重新使能/回零的边界时刻**被这样算一次，
   取整语义差异足以造成"归零不干净"或"回弹"这类**看起来像零点丢失的现象**。
   —— **这是机制相符的解释，但不是证据。**

> ⚠️ 仍然**未证明**。要证明需要：把这两段完整函数读通（含 `0x20003ED4`/`0x20003D8C` 的字段语义），
> 或做运行期对照。**目前它是最强的候选，因为它是位置写入点上的核心算式。**

### 25.2 ★★ 对照读出来：同一个计算，两版算式不同

**3.2.D.8（`0x0801551E`，结构体基址 `0x20003ED4`）**

```asm

ldr  r1, [0x20003ED4 + 0xc]      ; 量B
subs r0, r0, r1                  ; r0 = A - B
adds r0, r0, r6                  ; + 增量
str  r0, [0x20003ED4 + 0x18]     ; ★ 存 +0x18
ldr  r0, [0x20003ED4 + 0x18]
cmp  r0, #0
ble  <走非正分支>
movs r0, #0
str  r0, [0x20003ED4 + 0x14]     ; ★ 正数时 +0x14 直接置 0
b    <出口>
<非正分支>:
vldr      s0, [r0, #0x18]
vcvt.f32.s32 s1, s0              ; 整数→浮点
vldr      s0, [r5, #0xc]
vcvt.f32.s32 s0, s0
vdiv.f32  s2, s1, s0             ; ★ 除法
vstr      s2, [r0, #0x10]        ; 存 +0x10
vldr      s0, [r0, #0x10]
vmov.f32  s1, #5.000000e-01      ; ★ 0.5
vsub.f32  s0, s0, s1             ; ★ 减 0.5（== 四舍五入取整）
vcvt.s32.f32 s0, s0
vstr      s0, [r0, #0x14]        ; 存 +0x14
```

**3.1.5.0（`0x08014A60`，结构体基址 `0x20003D8C`）**

```asm
ldr  r0, [0x20003D8C + 0x14]
ldr  r1, [r4, #0xc]
muls r0, r1, r0                  ; r0 = B * 量
ldr  r1, [0x20003D8C + 4]
subs r0, r0, r1                  ; - A
ldr  r1, [0x20003D8C + 0xc]

str  r0, [0x20003D8C + 0x1c]     ; ★ 存 +0x1c
```

**⇒ 差异（这是本轮的核心）：**

| 项 | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| 结果字段 | `+0x18` / `+0x14` / `+0x10` | `+0x1C`，再送逐轴对象 `+0xA8` |
| 算式 | `(A − B) + 增量` | `(B × 量 − A) + C` |
| **浮点** | **有**：`vcvt`→`vdiv`→`−0.5`→`vcvt`（**除法 + 四舍五入取整**） | 该路径**无浮点** |
| 正负分支 | **有**：`+0x18 > 0` 时 `+0x14` 直接置 0，否则走浮点取整 | 无此分支 |
| **64 位乘法** | 无 | **有**：`smull` + `umull` + 两次 `mla` 的 64 位乘加 |
| 尾部调用 | 无 | **有**：`bl 0x08000222` |

### 25.3 这为什么是重点

1. **它落在位置值写入点上**（§18.1），是位置链的**核心算式**，不是我此前找的那些外围状态机。
2. **两版是"不同实现"，不是"同一实现加个开关"** ——
   D8 用**整数 + 一次浮点除法取整**；3150 用**整数乘加 + 64 位乘 + 一次子程序调用**。
3. D8 多出的 **`+0x18 > 0 → +0x14 = 0`** 分支，与 §16 A 的"条件消差"

   两处独立出现，**指向同一个设计意图**。

### 25.4 ⚠️ 仍然不是证明

**我没有证明这就是零点修复点。** 具体缺什么：

## 22. 第十轮：修掉用量表的一个假象 + 状态机分支的完整算式

### 22.1 ⛔ 用量表本身有过一个假象（已修）

`servo_struct_fields.py` 原来的"向后看若干条指令"没有在**同一寄存器被重新加载**时停止。
后果：

```asm
080157d4: ldr r5,[pc] ; = 0x20003DB0   ← 检测器把它当"我们的基址"
080157d6: ldr r5,[r5]                   ; r5 = [0x20003DB0+0]
...        sdiv/mls                     ; 算出余数
080157e0: ldr r5,[pc] ; = 0x20003DB0   ← 又加载一次（检测器**没有停**）
080157e2: str r3,[r5,#8]                ; ← 被同时算到 0x080157D4 那次头上
```

⇒ **同一条 `str r3,[r5,#8]` 被重复计入多个站点**，于是 `+0x08` / `+0x0C` 的计数虚高，
我还据此说出"读写完全对称的两份副本"。

**已修**：遇到 `ldr rX,[pc]` 重载同一寄存器即**停止**向后看。

**修正后的用量表（3.1.5.0 `0x20003DB0`）：**

| 偏移 | 修前 读/写 | **修后 读/写** |
|---|---|---|
| `+0x00` | 25 / 5 | **12 / 2** |
| `+0x04` | 0 / 4 | **0 / 2** |
| `+0x08` | 17 / 21 | **7 / 11** |
| `+0x0C` | 17 / 23 | **7 / 11** |
| `+0x10` | 3 / 14 | **3 / 12** |
| `+0x14` | 1 / 8 | **1 / 3** |
| `+0x18` | 10 / 15 | **9 / 8** |
| `+0x1C` | 1 / 3 | **1 / 2** |
| `+0x20` | 1 / 2 | **1 / 2** |

**⇒ 结论上的变化**：§21 那些"重度使用"的绝对数字**全部虚高**，已作废。
但 `+0x08` 与 `+0x0C` **仍然逐项完全相等（7/11 vs 7/11）** ——
这个对称性**不是**假象，是真实的（因为修前后两者始终相等）。

### 22.2 状态机分支的完整算式（3150 状态 ==1 分支，`0x08015810`）

```asm
08015816: movs r3, #0xcc
08015818: ldr  r3, [r3, r0]        ; r3 = 取自对象的量（r0 = 轴号*4+0xCC 基址）
0801581a: ldr  r5, [r0, #0xc]      ; r5 = 另一个量
0801581c: sdiv r3, r5, r3          ; r3 = r5 / r3          ← 比例
08015820: ldr  r5, [pc] ; = 0x20003DB0
08015822: ldr  r5, [r5]            ; r5 = 位置（+0x00）
08015824: sdiv r6, r5, r3          ; 商
08015828: mls  r3, r3, r6, r5      ; 余数
0801582c: ldr  r5, [pc] ; = 0x20003DB0
0801582e: str  r3, [r5, #8]        ; ★ 余数 → +0x08

08015830..0801583c:
        sdiv r3, r5, r3            ; 同样的比例
        ldr  r5, [r5, #8]          ; 取回刚存的余数
        add  r5, r3                ; r5 = 余数 + 比例
08015840..0801584c:
        sdiv r3, r6, r3            ; 比例
        movs r6, #6
        sdiv r3, r3, r6            ; ★ 再除以 6
08015850: subs r5, r5, r3          ; r5 = (余数 + 比例) - 比例/6
08015852..0801585c:
        sdiv r3, r6, r3 ; sdiv r6, r5, r3
08015860: mls  r3, r3, r6, r5      ; 再取一次余数
08015864: ldr  r5, [pc] ; = 0x20003DB0
08015866: str  r3, [r5, #8]        ; ★ 余数 → +0x08（覆盖）
08015868: movs r3, #0
0801586a: str  r3, [r5, #0x10]     ; 选择子 = 0
```

**关键算式**：`(余数 + 比例) − 比例/6`，其中那个 **`6`** 是硬编码常量。

> ⚠️ `6` 与"六轴"数字相同，**但这只是巧合级线索，不能当证据**。
> 也可能表示编码器的某种 6 分频/极对数关系。**未验证。**

状态 `==2`（`0x0801586e`）、`==3`（`0x080157ea`）、`==5`（`0x080157c6`）
分支形态相同，只是落到 `+0x08` 或 `+0x0C` 与选择子 0/1 的组合不同。

### 22.3 本轮实质结论

1. **用量表的绝对数字曾虚高 ~2 倍**（检测器假象），已修正 ——
   这是本次调查**第 6 类"工具的静默错误"**，且是我自己刚写的工具。
2. **`+0x08` / `+0x0C` 的真实对称性成立**（各 7读/11写），
   但**它们不是"两份副本"** —— 状态机按状态号在不同的分支里改写其中之一，
   选择子 `+0x10` 记录当前用的是哪个。
3. **状态机做的是"位置 → 圈数(商) / 圈内量(余数)"的反复重算**，
   并带一个 `(余数 + 比例) − 比例/6` 的修正算式。

### 22.4 仍未解 / 诚实边界

* `+0x08` / `+0x0C` 的**消费者在状态机之外一个都没找到**
  （修后 7 个读取点全在状态机内）⇒ **这两个余数算完给谁用，未知**。
  **这是"零点基准怎么生效"的最后一环，而且它指向状态机之外 —— 但静态找不到消费者。**
* 那个硬编码 `6` 的含义未知。
* **「回零定基」机制仍未证明**；D8 缺失整台状态机这一点是四组差异里最硬的一条，
  但"缺失 = 修复"仍是推断，**没有实验对照**。

> **进度声明**：本轮把工具的一个假象修掉、把状态机算式读通，
> 仍**没有**在"零点机制"上取得证明性进展。

## 20. 第八轮：状态机在 D8 里**整体不存在**（可复现的判别式），以及自旋等待标志

### 20.1 ✅ 用可复现的签名证明「D8 没有这个状态机」

上一轮只说"3150 多调用一次 `0x08015778`"。本轮给出**结构性判别**，
而不是靠逐个调用点比对。

**判别式**（`tools/` 里的临时扫描，逻辑已记录在此）：
在 `movw rX,#0x329` 之后的 0x50 字节内，同时出现
`[rX,#0x24]` 访问 **且** `cmp …,#7` **且** 存在 `tbb` —— 即为该状态机。

| 镜像 | 命中 |
|---|---|
| 3.1.5.0 | **1 处**：`0x08015786` |
| 3.2.D.8 | **0 处** |

⇒ **3.2.D.8 里整个状态机不存在**，不是"没被调用"。
（这条比 §19 的"没调用"更强：**函数体也没有**。）

### 20.2 状态机的完整语义（3150 `0x08015778`）

```asm
0801577c: add.w  r3, r2, r2, lsl #2      ; r3 = 轴号*5
08015782: add.w  r1, r5, r3, lsl #4      ; r1 = 0x2000C3BC + 轴号*80   ← 每轴 0x50 字节的状态块
08015786: movw   r3, #0x329
0801578a: muls   r3, r2, r3              ; 轴号*809
0801578e: adds   r4, r3, r5              ; r4 = 0x2000129C + 轴号*809  ← 逐轴对象

; ---- 首次调用初始化 ----
0801579e: ldrh   r3, [r1, #0x24]         ; "已初始化"标志
080157a0: cbnz   r3, <已初始化>
080157a2: ldrh   r3, [r1, #0x20]         ; 当前状态
080157a4: strh   r3, [r1, #0x22]         ; previous = current
080157a6: movs   r3, #1
080157a8: strh   r3, [r1, #0x24]         ; initialised = 1

; ---- 状态变化检测 ----
080157aa: ldrh   r3, [r1, #0x20]         ; current
080157ac: ldrh   r5, [r1, #0x22]         ; previous
080157ae: cmp    r3, r5
080157b0: beq    #0x80158b0              ; 状态没变 → 直接返回 ★
080157b2: ldrh   r3, [r1, #0x20]
080157b4: cmp    r3, #7
080157b6: bhs    #0x801580e              ; 状态 >=7 → 跳过
080157b8: tbb    [pc, r3]                ; 按状态跳转（状态 0..6）
```

**⇒ 它就是"逐轴 CiA402 状态变化检测器"**：
状态块每轴 `0x50` 字节，字段 `+0x20` 当前状态、`+0x22` 上一次状态、`+0x24` 已初始化标志；
**状态没变就什么都不做**。

### 20.3 状态机内部在做什么：**重新做商/余数分解**

状态 `==5` 的分支（`0x080157c6`）：

```asm
080157ca: movs  r3, #0xcc
080157cc: ldr   r3, [r3, r0]             ; 从对象取一个步长量
080157ce: ldr   r5, [r0, #0xc]
080157d0: sdiv  r3, r5, r3               ; 比值
080157d4: ldr   r5, [pc] ; = 0x20003DB0
080157d6: ldr   r5, [r5]                 ; 取 0x20003DB0+0（位置）
080157d8: sdiv  r6, r5, r3               ; 商
080157dc: mls   r3, r3, r6, r5           ; 余数
080157e0: ldr   r5, [pc] ; = 0x20003DB0
080157e2: str   r3, [r5, #8]             ; ★ +8 = 余数
080157e4: movs  r3, #0
080157e6: str   r3, [r5, #0x10]          ; ★ +0x10 = 选择子 0
```

状态 `==3` 的分支（`0x080157ea`）与 `==1` 的分支（`0x08015810`）形态相同，
只是写 `+0xC`、选择子写 **1**。

**⇒ `0x20003DB0` 的结构现在完整了：**

| 偏移 | 含义 |
|---|---|
| `+0x00` | 位置（上一次报告的位置值） |
| `+0x04` | 商（圈数）—— §19 发现 |
| `+0x08` | 状态 5 时算出的余数 |
| `+0x0C` | 状态 3/1 时算出的余数 |
| `+0x10` | **选择子（0 或 1）** —— 表示"当前用哪个余数" |

**⇒ 这是一个"双余数 + 选择子"结构**，即
**两套位置分解并存、用 `+0x10` 选择当前有效的那一套** ——
这正是"切换零点基准"会需要的形态（旧基准/新基准各存一份余数，选择子指向生效的那份）。

> ⚠️ **必须说清**：这是我**从数据布局推断**的语义，**没有验证**。
> `+0x08` / `+0x0C` / `+0x10` 的**消费者尚未追踪**。

### 20.4 自旋等待标志 `0x20000010`

两版的标志门控块都**自旋等待** `[0x20000010] == 1`（不等于 1 就跳回自己）。
它的写入点：

| 镜像 | 写入点 |
|---|---|
| 3.2.D.8 | **`0x080208BC`**（`strb r0,[r1]`，`r1 = 0x20000010`）周围伴随 **`bic/orr #0x200`** 的位操作与一次 `strh [r5,#2]` |
| 3.1.5.0 | 另有其站点（本轮只核实了 D8 侧 2 处加载） |

⇒ **`0x20000010` 是一个"就绪/同步"标志**：位置环在首次进入时自旋等它被置 1。
**这是两版共有的同步点**，不是差异点（差异在"等完之后做什么"）。

### 20.5 差异候选清单（更新后仍是四组，但内容更硬）

| 组 | 3.1.5.0 | 3.2.D.8 | 强度 |
|---|---|---|---|
| §16 A 条件消差 | 无 | `+0xBA` 置位时强制消差步长 0 | 函数体内分支差异 |
| §16 B 一次性位置指令重初始化 | 无 | 有 | 函数体内分支差异 |
| §18 位置写入点商余数 | 有 | **无** | 写入点前后各一段 |
| §19/§20 状态机 | **有整个状态机** | **函数体不存在** | **最强：可复现判别式证明** |

**⇒ 现在最硬的一条是 §20**：3150 有一个 D8 里**根本不存在**的状态机，
它在位置值写入后被调用，作用是**重算位置的双余数并切换选择子 `+0x10`**。

**这条与「零点基准」的形态最吻合** —— 但它到底是修复点还是被移除的旧机制，**仍未证明**。

### 20.6 仍缺的关键一环

`0x20003DB0+0x08 / +0x0C / +0x10` 的**消费者**没找到。
找到它才能知道"两套余数"最终怎么变成上报位置 ——
那是"零点基准怎么生效"的最后一环。

> **注意**：`0x20003DB0` 有 79 处引用（§19），
> 逐个人工读代价大；下一轮应写一个"按结构体字段列消费者"的脚本（类似
> `servo_field_refs.py`，但支持 `base + idx*stride` 基址，见 §18.6 的能力缺口）。

## 19. 第七轮：同一标志**两版都在用，但读的字节位置与判据不同**

### 19.1 先纠正上一轮的两个说法

上一轮我写"**3.1.5.0 在这里多做两步，3.2.D.8 没有**"（§18.2）。
**说对了一半**：3150 确实在位置值写入后多做检查与调用；
但**D8 并不是没有这套逻辑** —— 它有**同构的一块**，只是在**不同的程序点**、
且**读的是同一个 2 字节字段里不同的字节**。

### 19.2 两版同构的「标志门控块」逐条对照

D8 `0x080153E8` 与 3150 `0x080148B4`：

```asm
; 3.2.D.8  0x080153E8                         ; 3.1.5.0  0x080148B4
ldr  r0,[pc] ; = 0x20000020                   ldr  r0,[pc] ; = 0x20000022
ldrb r0,[r0]                                  ldrb r0,[r0]
cmp  r0,#0                                    cmp  r0,#0
bne  <跳过>                                    bne  <跳过>
ldr  r0,[pc] ; = 0x20000010   ← 两版相同        ldr  r0,[pc] ; = 0x20000010
ldrb r0,[r0]                                  ldrb r0,[r0]
cmp  r0,#1                                    cmp  r0,#1
bne  <自循环>                                  bne  <自循环>
strb r0,[r1]   ; 写回 0x20000020  ← D8 在此     (3150 此处无写回)
```

**⇒ 两版的判据结构完全一致**（外层等 0、内层等 1、内层不等于 1 就自旋等待），
**唯一区别是外层读/写的标志字节**：
D8 用 `0x20000020`、3150 用 `0x20000022`。

### 19.3 关键：这是**同一个 2 字节字段的两个字节**

* 3150 的位置值写入点（`0x08014AE2`）做 `strb r0,[0x20000022]`，
  紧接着（`0x08014AE6`）读 `ldrh r0,[0x20000020]` 并 `cmp #1`；
* 也就是说 **`0x20000020` 是一个 u16，高位字节（`+1`）就是 `0x20000022`**；
* **D8 的位置值写入点用 `strh` 读写 `0x20000020` 整个 16 位**（`0x08015236`），
  而**不写 `0x20000022`**。

⇒ **两版对这个字段的"字节粒度"不同**：
3150 单独写高位字节并在写入点之后按"高位字节 == 1"决定是否再调用一次状态机；
D8 只按整个 16 位操作。

### 19.4 ★ 3150 在位置值写入点之后**额外调用**了一次状态机

```asm
; 仅 3.1.5.0  0x08014B66
ldr   r0,[pc] ; = 0x20000022
ldrb  r0,[r0]
cmp   r0,#1
bne   <跳过>
movs  r0,#0xb4
ldr   r0,[r0,r4]
cbnz  r0,<跳过>
movs  r0,#0
bl    #0x08015778
```

调用的 `0x08015778` 是**含 `previous / current / initialised` 三字段的状态变化检测 + 状态机**
（按 `0x329` 步长访问逐轴对象，状态号 `< 7` 走不同分支，见 §18.4）。

**⇒ 合并起来，两版在"位置值写入"这件事上的差异是：**

| | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| 写位置值 `+0x238` | ✅ `0x08015602` | ✅ `0x08014B62` |
| 写入点前的商/余数分解 | 否 | ✅ 写 `0x20003DB0+4`（商）、`+0`（余数） |
| 写入点后按标志再调状态机 | 否 | ✅ `0x08014B76` → `0x08015778` |
| 标志字段粒度 | 整个 u16 `0x20000020` | 高位字节 `0x20000022` |

### 19.5 `0x20003DB0` 的角色已解（商/余数对）

`tools/servo_litrefs.py` 显示 3150 里有 **79 处**加载 `0x20003DB0`，写入点是这样用的：

```asm
; 0x08014B16
sdiv  r0, r0, r1          ; 商 = 位置 / 步长
ldr   r1,[pc] ; = 0x20003DB0
str   r0,[r1, #4]         ; → +4 存商
; 0x08014B24
sdiv  r2, r0, r1
mls   r0, r1, r2, r0      ; 余数
ldr   r1,[pc] ; = 0x20003DB0
str   r0,[r1]             ; → +0 存余数
; 0x08014B0C
cmp   r0, #0
blt   <负分支>            ; 负数时商再减 1
```

⇒ **`0x20003DB0` 是 (余数, 商) 对** —— 典型的**多圈/单圈编码器分解**
（商 = 圈数，余数 = 圈内位置），负值要做借位修正。
**79 处引用说明它是被广泛使用的共享量**，不是局部临时值。

### 19.6 本目标状态更新

| 目标项 | 状态 |
|---|---|
| `0x6064` → 上报位置：读取链 | ✅ 已解（§15.1） |
| `0x6064` → 上报位置：**写入链** | ✅ 已解（§18.1） |
| 两版差异 | ✅ **四组**：§16 A/B、§18（商余数+状态机）、**§19（标志字节粒度 + 状态机调用）** |
| 位置分解量的角色 | ✅ **本轮解出**（商/余数对，多圈/单圈） |
| 「回零定基」的真正机制 | 🟡 仍**未证明** |

> **仍未证明**：这些差异里哪一组真正决定"零点是否保持"。
> 四组差异**都不能排除**，也都**没有实验对照**（控制箱离线）。
> 需要的下一步仍是 RAM 转储：至少要有 `0x20000000` 一带（标志字段 + 函数指针表）
> 与 `0x20003DB0` 的内容，才能判断哪条路径在故障件上真的走了。

## 18. 第六轮：**位置值写入点**上的版本差异（本轮唯一实质发现）

上一轮我说"静态已到边界"。**这个结论下得太早**——我漏查了一个最直接的东西：
**谁写位置对象的位置实际值成员 `+0x238`**。重查后找到了位置值的**写入点**，并且那里**两版有差异**。

### 18.1 写入点的定位

过滤掉 `[sp,#0x238]` 的栈访问后，全镜像里真正写到"位置实际值"的**各只有 1 处**：

| | 写入点 | 读取点 |
|---|---|---|
| 3.2.D.8 | **`0x08015602`** `str.w r1,[r0,#0x238]` | `0x08015344` |
| 3.1.5.0 | **`0x08014B62`** `str.w r0,[sb,#0x238]` | `0x08014824` |

**两版共同的形态**：先写 `+0x234`，再把 `+0x234` 送进**同一个函数指针** `[表+8]`，
结果写回 `+0x238`：

```asm
; 两版共有
ldr.w r1, [rX, #0x234]
ldr   r0, [pc] ; = 函数表
ldr   r2, [r0, #8]
mov   r0, r8            ; 轴号
blx   r2                ; 换算
str.w r?, [rX, #0x238]  ; ★ 写位置实际值
```

### 18.2 ★ 差异：**3.1.5.0 在这里多做两步，3.2.D.8 没有**

```asm
; --- 仅 3.1.5.0  0x08014B42 ---
ldr.w r0, [sb, #0x234]
ldr   r1, [r4, #0xc]
sdiv  r2, r0, r1          ; 商
mls   r0, r1, r2, r0      ; 余数 = r0 - r1*r2   ← 取模
add   r0, r1              ; ★ 余数 + r1
ldr   r1, [pc] ; = 0x20003DB0
str   r0, [r1]            ; ★ 写一个全局

; --- 仅 3.1.5.0  0x08014B66（位置值写回**之后**）---
ldr   r0, [pc] ; = 0x20000022
ldrb  r0, [r0]
cmp   r0, #1
bne   <跳过>
movs  r0, #0xb4
ldr   r0, [r0, r4]
cbnz  r0, <跳过>
movs  r0, #0
bl    #0x08015778         ; ★ 额外的条件调用
```

**3.2.D.8 两段都没有。**

### 18.3 这两步的量化证据

| 项 | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| 全局 `0x20003DB0` 的字面量站点 | **0 处** | **3 处**（`0x08014BB0`、`0x08015B88`、`0x08015DFC`） |
| 位置值写入点前的取模运算 | 无 | 有（`sdiv`+`mls`+`add`） |
| 位置值写入点后的条件调用 | 无 | 有（`[0x20000022]==1 && …` → `bl 0x08015778`） |

⇒ **`0x20003DB0` 这个全局在 D8 里根本不存在**（0 个字面量引用）——
这不是"移位"，是**被去掉了**。

### 18.4 额外的条件调用目标 `0x08015778` 是什么

3.1.5.0 的 `0x08015778` 是**一个以 `0x329` 步长访问逐轴对象的状态机**：

```asm
08015786: movw  r3, #0x329
0801578a: muls  r3, r2, r3            ; 轴号 × 809
0801578c: ldr   r5, [pc] ; = 0x2000129C   (逐轴对象基址)
0801578e: adds  r4, r3, r5
...
0801579e: ldrh  r3, [r1, #0x24]
080157a0: cbnz  r3, ...
080157a2: ldrh  r3, [r1, #0x20]       ; 状态
080157a4: strh  r3, [r1, #0x22]       ; 保存"上一状态"
080157a6: movs  r3, #1
080157a8: strh  r3, [r1, #0x24]       ; 置"已初始化"
080157aa: ldrh  r3, [r1, #0x20]
080157ac: ldrh  r5, [r1, #0x22]
080157ae: cmp   r3, r5
080157b0: beq   <…>                   ; 状态未变则跳过
080157b2: ldrh  r3, [r1, #0x20]
080157b4: cmp   r3, #7                ; 状态 < 7 → 状态机分支
080157b6: bhs   <…>
```

**⇒ 这是一个"状态变化检测 + 状态机"例程**（含 `previous/current/initialised` 三个字段）。
**3.1.5.0 会在写完位置值后按条件调用它，3.2.D.8 不调用。**

### 18.5 这条差异的意义（**解读，未证明**）

D8 相对 3150 在这里是**做减法**：去掉了一个"位置取模 + 写全局"的步骤，
以及一个"位置写回后按条件跑状态机"的步骤。

**与"零点不保持"的关系：方向合理但未证明。**
如果 3150 的那个取模/全局在某条件下把位置值改写掉，那正是"重新上使能后位置跳变"的候选机制；
但**我没有证据**说明那个全局 `0x20003DB0` 被谁消费，也不知道 `0x08015778` 的状态机做什么。

> ⚠️ 与 §16 的差异（消差开关 `+0xBA`、位置指令重初始化）**是不同位置的两组差异**，
> 目前**都只是候选**，无法判断哪一组（或都有）与零点问题相关。

### 18.6 工具能力的诚实交代

`tools/servo_field_refs.py` 本轮**又暴露一个能力缺口**：
对 `*(0x2000138C)+0x238` 返回 0 处，因为该基址是
`r4 = [pc]=0x2000138C + 轴号×0x329` —— **"已知指针 + 动态索引"这种基址它表达不了**。
本节的写入点是**绕过该工具、直接用"全镜像文本搜 `#0x238` 的 `str`"**找到的。

**⇒ 结论：字段检索器只覆盖"基址是常量字面量"的情形；
需要 "基址 = 常量 + 动态索引" 时必须改用直接指令检索，不要依赖它的 0 结果。**

## 17. 第五轮：修好字段检索器 + 两处对上一轮的更正 + 明确静态边界

### 17.1 ✅ 重写字段检索器（旧版是**坏的**，会静默返回 0）

`tools/servo_find_field.py` 对**肉眼可见**的访问都返回 0 —— 这是最危险的一类工具故障
（"找不到"看起来像"不存在"）。查明是**三个 bug 叠加**：

1. 助记符表**缺宽指令形式**（`ldrh.w` / `strh.w` / `ldrsh.w` 等），
   而本项目反汇编里**几乎全是宽形式**；
2. 反向扫描循环会跨过无关指令并在第一次不匹配就 `break`；
3. 它要求了编译器并不保证的指令相邻形态。

**⇒ 已重写为 `tools/servo_field_refs.py`**：改成**前向抽象解释**——
按地址顺序走指令，记录"哪几个寄存器当前持有已知常量"（来自字面量池 / `movw`/`movt`），
在每条 `[rB,#imm]` 访问处判断 `已知值 + imm` 是否命中目标字段；
**并且实现了一步解引用传播**（`ldr rX,[pc]=BASE ; ldr rX,[rX] ; ldrh rX,[rX,#0xB8]`
这种最常见的形态）。

**自检**（这正是新版存在的意义）：对 `*(0x200016B5)+0xB8` 由 **0 处 → 7 处**，
对 `+0xBA` 由 **0 处 → 3 处**。

> ⚠️ **教训（本调查第 5 类静默错误）**：
> **任何"搜索/检测"类工具，必须先用一个已知存在的样本做正例自检**；
> 一个恒返回空的检测器会把"没找到"伪装成"不存在"，从而直接污染结论。

### 17.2 ⛔ 更正上一轮：`+0xB8` 的"读了 3 次"有一半是**字节拷贝**，不是标志逻辑

§16 我写"`+0xB8` 被读 3 次"。新版检索器给出 7 处，其中 4 处集中在 `0x080186D0..0x0801872A`，
读出来是**一个逐字节拷贝/序列化例程**：

```asm
ldr.w sl, [pc, #0x954]     ; sl = 0x200016B5
ldrb.w sl, [sl, #0xb8]     ; 取第 0 字节
ldrh.w sl, [sl, #0xb8]     ; 取第 1 字节（同一地址，靠位宽取不同字节）
lsr.w  sl, sl, #8
ldrsh.w sl, [sl, #0xb8]    ; 第 2 字节
ldrsh.w sl, [sl, #0xb8]    ; 第 3 字节
asr.w  sl, sl, #0x18
strb.w fp, [r1, sl]        ; 逐字节写进输出缓冲
```

⇒ 这是**把结构体某几个字节搬进缓冲区**（大概率是响应/参数序列化），
**与"标志被读 3 次"无关**。

**因此 §16.1 里"`+0xB8` 另有用途"的说法要收紧为：**
* `+0xB8` 的真实用途**仍是未知**；
* 唯一确定参与位置环判断的是 **`+0xBA`**（`0x08010EE2`，消差开关）；
* **两个字段都没有找到写入者**（见 §17.3）。

### 17.3 ⛔ 关键缺口：`+0xB8` / `+0xBA` 的**写入者在静态镜像里找不到**

用修好的检索器全镜像扫描：两个字段**各有若干只读站点，零写入站点**。

⇒ 说明它们的写入者**不在本镜像里**，或者写入时用了**非字面量寻址**
（例如基址来自另一个结构体字段、或经 `add` 动态算出）。
**这是"谁请求消差/重初始化"这条线的断点。**

**⇒ 通向标定/回零的入口，目前被这个断点挡住。**

### 17.4 静态边界再确认：位置值经**运行期填表的函数指针**取得

位置环里两次关键取值都走 RAM 函数指针表：

```
[0x20000078 + 4]    参考位置换算（位置环主路径）
[0x20000100 + 8]    状态判定
[0x20000030] / [0x20000034]   重初始化发布的基准值
```

`tools/servo_ram_region.py` 显示这些表地址只被**读**（`ldr r2,[r0,#off] ; ... ; blx r2`），
**在静态镜像里找不到对它们自身的写入或初始化**。

⇒ **位置值的真正来源（换算函数）在运行期才绑定。**

**这两条合起来给出本目标的静态边界**：
* **位置环的"骨架"（谁读谁、字段是什么）已完全解出**（§15/§16）；
* **但"位置值怎么算出来的"和"消差标志谁置的"两件事，静态镜像里都看不到**
  —— 需要控制箱在线时用 `amrd` 转储 RAM（`HANDOVER_2.md` §2.4），
  或至少 dump 一次 `0x20000000` 一带的函数指针表内容。

### 17.5 顺带一个操作教训（非固件问题）

于是我一度看到"0 处命中"，差点又当成"不存在"。
**⇒ 含逗号的参数一律加引号**（`--offs "0xb8,0xba,0x36"`）。

## 16. ★★★ 第四轮：位置环差异的**完整**枚举（并更正 §15 的不完整描述）

§15 我把这段差异说成"3.2.D.8 多了一段一次性重初始化"。**读完整函数后，这个描述不准确**：
多出来的其实是**两处独立的东西**，而 §15 把第二处（`+0xBA`）也笼统算进了"重初始化"。

这次用 `tools/servo_loopdiff.py` 做**穷尽式字段访问比对**（不靠手读抽样）：

| 度量 | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| 位置环函数入口 | `0x08010E60` | `0x0801079C` |
| 结构字段访问总数 | **107** | **88** |

### 16.1 ★ 差异 A：`+0xB8` 是**条件消差**，不是"清零位置指令"

**两版共有的"三次尝试"收敛逻辑**（逐条同构）：

```asm
ldr   r1, [r4, #0x30]        ; 目标
ldr   r0, [r4, #0x14]        ; 参考
subs  r0, r0, r1
str   r0, [r4, #0x1c]        ; 偏差 = 参考 - 目标
ldrd  r0, r1, [r4, #0x1c]
subs  r0, r0, r1
str   r0, [r4, #0x24]        ; 消差步长
ldr   r0, [pc] ; = 0x200015C5(B)   /  0x200016B5(D8)
ldrh  r0, [r0, #4]           ; ★ 同一个标志！两版都读
cmp   r0, #1
bne   <跳过>
...  abs(偏差) > 阈值 → 回退 + 计数 0x2c
```

**⇒ §15 有一处判断错了**：那个标志（B 基址 `0x200015C5` +4 ≡ D8 基址 `0x200016B5` +4）
**两版都存在、都在读**。它不是"3.2.D.8 新增的触发标志"。

**D8 真正多出来的是紧邻的 `+0xB8` 覆盖**：

```asm
; 仅 3.2.D.8  0x08010EE0
ldrh.w r0, [r0, #0xba]
cbz    r0, <正常算偏差>
movs   r0, #0
str    r0, [r4, #0x24]       ; ★ 直接**强制消差步长 = 0**
b      <继续>
<正常算偏差>:
ldrd   r0, r1, [r4, #0x1c]
subs   r0, r0, r1
str    r0, [r4, #0x24]
```

⇒ `[base+0xBA] != 0` 时，**偏差补偿被强制清零**（该轴锁住跟随/消差）。
**3.1.5.0 没有这个分支** —— 它总是按 `参考 − 目标` 算补偿。
D8 里 `+0xB8` 被读 **3 次**、`+0xBA` 读 **1** 次，B 侧完全没有。

> ⚠️ 注意：`+0xB8` 与 `+0xBA` 是**两个相邻的 u16 字段**；
> D8 读 `+0xB8`（3 次）与 `+0xBA`（1 次），§15 里我把 `+0xB8` 当成那段重初始化的开关，
> **实际上是 `+0xBA` 在当消差开关**，`+0xB8` 另有用途（未查明）。

### 16.2 ★ 差异 B：D8 多一次"位置指令重初始化"（§15 描述的这段，成立）

```asm
; 仅 3.2.D.8  0x08010E78
ldrh   r0, [r4, #0x36]
cmp    r0, #1
bne    <跳过>
ldr.w  r0, [r5, #0x230]
str    r0, [r4, #0x30]        ; 目标位置 <- +0x230
movs   r0, #0
str    r0, [r4, #0x20]        ; 清位置指令
... 重算参考 → 发布到 RAM 全局 0x20000030 / 0x20000034
```
D8 因此多一次读 `+0x230`、多一次写 `+0x020` / `+0x030`。

### 16.3 穷尽比对给出的**差异清单**（这是本层面的事实全集）

### 16.4 对"零点不保持"的意义（**我的解读，未证明**）

D8 多出的 A+B 两件事都在做**同一类事**：
**在特定条件下把"位置指令/消差量"重置/钳住**（A 把消差步长清零，B 把指令清零并把目标对齐到 `+0x230`）。

这与"重新上使能时不要拿陈旧指令去跑"的**方向一致**，因此比 §15 的说法更有说服力。
**但这仍然是机制相符的推断，不是证据** —— 尤其：
* `+0xB8` / `+0xBA` 的**写入者仍未找到**；
* `0x20000030` / `0x20000034` 的**消费者仍未查**；
* 无实验对照（控制箱离线）。

### 16.5 本轮的另一个方法教训：RAM 地址**没有全局位移**

我曾推断"两版 RAM 地址整体偏移 `-0x419`"。`tools/servo_ram_shift.py` 实测**不成立**：

|---|---|

（这也再次说明：**跨构建"某地址不存在 ⇒ 功能不存在"的推断一律无效**。）

## 15. ★★★ 第三轮：差异 ① 已读到语义 —— 3.2.D.8 多了一个**一次性位置指令重初始化**

§6.2 的"差异 ①"此前只能说"步长常量不同、语义未知"。本轮把**两侧整段读通**了。

### 15.1 两版共有的主控制块（逐条对齐）

位置环的**公共部分**在两版里**逐条同构**（只有寄存器号和地址不同）：

```asm
ldr.w r0, [r5, #0x1af]        ; 参考位置 A
ldr.w r3, [r5, #0x31f]        ; 参考位置 B
adds  r1, r0, r3              ; r1 = A + B        <- 位置指令
ldr   r0, [pc]  ; = 0x20000078 / 0x20000074   (函数表)
ldr   r2, [r0, #4]
mov   r0, r6                  ; 轴号
blx   r2                      ; 调用  -> 位置经函数指针换算
str   r0, [r4, #0x14]         ; 存"参考位置"
ldr   r0, [pc]  ; = 0x20000100 / 0x200000fc   (函数表)
ldr   r1, [r4, #0x14]
ldr   r2, [r0, #8]
mov   r0, r6
blx   r2                      ; 调用  -> 状态判定
cmp   r0, #1
bne   ...
ldr   r1, [r4, #0x30]         ; 目标位置
ldr   r0, [r4, #0x14]         ; 参考位置
subs  r0, r0, r1              ; 偏差 = 参考 - 目标
str   r0, [r4, #0x1c]
```

**⇒ 位置环的读写集合是（描述符内偏移）：**
`+0x1AF`、`+0x31F`（参考位置对）、`+0x238`（位置实际值）、`+0x230`（目标位置）、
`+0x018/+0x01C/+0x020/+0x024/+0x028/+0x02C/+0x030/+0x036`（运行时状态）。

### 15.2 ★ 3.2.D.8 **多出的一段**（3.1.5.0 完全没有）

```asm
; --- 仅 3.2.D.8 有：0x08010E78 ---
08010e78: ldrh   r0, [r4, #0x36]        ; 状态字
08010e7a: cmp    r0, #1
08010e7c: bne    #0x8010ea4             ; 不等 1 就跳过
08010e7e: ldr.w  r0, [r5, #0x230]       ; 目标位置
08010e82: str    r0, [r4, #0x30]        ; ★ 把 0x230 拷进 0x30
08010e84: movs   r0, #0
08010e86: str    r0, [r4, #0x20]        ; ★ 清 +0x20（位置指令）
08010e88: ldr.w  r0, [r5, #0x1af]
08010e8c: ldr.w  r3, [r5, #0x31f]
08010e90: adds   r1, r0, r3
08010e92: ldr    r0, [pc] ; = 0x20000078
08010e94: ldr    r2, [r0, #4]
08010e96: mov    r0, r6
08010e98: blx    r2                     ; 换算
08010e9a: ldr    r1, [pc] ; = 0x20000030
08010e9c: str    r0, [r1]               ; ★ 结果写到一个 RAM 全局
08010e9e: ldr    r1, [pc] ; = 0x20000034
08010ea0: ldr    r0, [r4, #0x30]        ; 目标位置
08010ea2: str    r0, [r1]               ; ★ 目标位置也写到 RAM 全局
; --- 两版重新汇合 ---
08010ea4: ldr    r0, [pc] ; = 0x200016b5
08010ea6: ldrh.w r0, [r0, #0xb8]
08010eaa: strh   r0, [r4, #0x36]        ; 两版都有：存一次状态
08010eac: ldr    r0, [pc] ; = 0x200016b5
08010eae: ldrh.w r0, [r0, #0xb8]
08010eb2: cmp    r0, #0
08010eb4: bne    ...
08010eb6: ...                          ; 0 则走下面那段（两版都有）
```

### 15.3 这段在语义上是什么

**它是一个"一次性"的位置指令重初始化，由 `[0x200016B5 + 0xB8]` 这个 16 位标志触发：**

1. 读 `[0x200016B5+0xB8]`；**若等于 0 则跳过整段**（`bne` 跳过，见 §15.2 末）；
2. 把**目标位置 `+0x230` 拷进"当前目标" `+0x30`**；
3. **清零位置指令 `+0x20`**；
4. 用 `A+B` 重新换算一次参考位置，并把**参考值与目标值双双写入两个 RAM 全局**
   （`0x20000030` / `0x20000034`）；
5. 紧接着把该标志**存进 `+0x36`**，并重读它（下一轮就为 0，所以只生效一次）。

⇒ **`[0x200016B5+0xB8]` 是一个"请求标志"**：置位 → 该轴位置指令被重新初始化一次
（目标 ← `+0x230`，指令 ← 0，并对外发布一组基准值）。

### 15.4 ⚠️ 这**不是**"零点修复点"，但它是**机制相符的头号候选**

**支持它是候选：**
* 两版**唯一**在位置环控制块里的结构差异；
* 它做的正是"**清零位置指令 + 用 `+0x230` 重建目标 + 对外发布基准**" ——
  与"驱动器重新定基、上电/使能后位置指令被重建"的**行为特征一致**；
* 触发标志来自**另一处 RAM 全局**（`0x200016B5+0xB8`），说明是**外部/上位请求驱动**，
  与"控制器发一次标定请求、驱动器据此重建"的场景吻合；
* 3.1.5.0 **没有**这段 ⇒ 它的位置指令不会被这样重建。

**为什么还不能定论：**
* 我只读到**这一段**，没有追到 `[0x200016B5+0xB8]` 是**谁置的**、也没读全它所在函数的其余分支；
* `0x20000030` / `0x20000034` 两个 RAM 全局的**消费者未查**；
* **没有**把它与"零点是否保持"做过任何实验对照（无法做：控制箱离线）。

**⇒ 定位等级：从"一处可疑的常量差异"提升到"一段语义清楚、机制相符的一次性重初始化"。**
**仍属候选，不属已证实的修复点。**

## 43. ★★★ 第二十八轮：`mode` 的**写者找到了** —— 并**更正 §42 的错误结论**

### 43.1 完整链路（两版**逐条读码**一致）

```
[0x20009A70 + 轴×0x64 + 0x34]   ← 0x64 步长逐轴对象里的 mode 源字段
        │  ldr  [r6,#0x34]        D8 0x08019EEC
        ▼
   压栈 [sp+0x5c]（函数第 6 个实参）
        │
        ▼  调用「mode 设置器」
   D8  0x0801A9E8 / 3150 0x0801956C
        │  movs r0,#0xCC(D8) / #0xB4(3150)  ; str r1,[r0,r4]
        ▼
[0x2000C6C8 + 轴×0xE4 + 0xCC(D8) / +0xB4(3150)]   ★ mode 最终落点
        │  D8 0x08016986 / 3150 0x080163DC:  movs r0,#0xCC / #0xB4 ; ldr r0,[r0,r4]
        ▼
   上报位置的三来源选择器
```

### 43.2 三个逐轴对象（不同基址、不同步长、**不可混用**）

| 对象 | D8 基址 | 3150 基址 | 步长 | 本轮用途 |
|---|---|---|---|---|
| **A** 0x64 步长对象 | `0x20009A70` | `0x20009580` | **`0x64`** | **mode 的源字段**在此 |
| **B** mode 最终落点 | `0x2000C6C8` | `0x2000C1D8` | **`0xE4`** | 选择器从这里读 mode |
| **C** 复制目标 | `0x20008548` | `0x20008060` | **`0x164`** | 另一处 `mode` 落点（§43.4） |

步长算式（**两版都以 `lsl #2` 结尾，故语义等价**，只是常量编码方式不同）：

* A 对象：D8 `rsb r0,r4,r4,lsl#3` + `add r0,r0,r4,lsl#4` ⇒ `0x19×4 = 0x64`
  3150 `rsb r0,r5,r5,lsl#3` + `rsb r0,r0,r5,lsl#6` ⇒ `0x19×4 = 0x64`（同值）
* B 对象：`rsb r0,r7,r7,lsl#6` + `lsl #2` ⇒ `0x39×4 = 0xE4`
* C 对象：`movs r0,#0x59` + `muls r0,r7,r0` + `lsl #2` ⇒ `0x59×4 = 0x164`

### 43.3 ★ 关键更正：A 对象里的 mode 源字段是 **`+0x34`(D8) / `+0x2C`(3150)**

调用点 D8 `0x08019EE0..0x08019EEE` 与 3150 `0x08018A64..0x08018A72` **逐条相同**：

```
ldr r0,[r6,#0x28] ; str r0,[sp,#0x50]
ldr r0,[r6,#0x2c] ; str r0,[sp,#0x54]
ldr r0,[r6,#0x30] ; str r0,[sp,#0x58]
ldr r0,[r6,#0x34] ; str r0,[sp,#0x5c]   ★ 最后一个 = mode
```

⇒ 两版**读的是同一批结构字段**，只是 A 对象内部布局整体差 **`+8`**
（与 §43.5 在 C 对象上量到的 `+8` **同一个量级**）。
⚠️ 这**不是** §42 说的 `-0x18`。

### 43.4 另有一条独立写链（与选择器**无关**，但值得记下）

D8 `0x080216DC / 0x080216DE` 把一个 6 元组从 **A 对象** `+0x184..+0x1A8`
拷进 **C 对象**（`str r1,[r0,r4]`，`r0=#0xCC`）。
该块在两版**逐条 37 条指令完全一致**，**连源偏移都相同**（`+0x184` 起），
只有**目标偏移整体差 +8**（D8 `+0xCC` ↔ 3150 `+0xD4`）。

`mode` 在此块里的落点是「C 对象基址 − 0xA4 + 0xCC」⇒ **不是** `0xCC` 本身。
§42 把这一块当成了选择器读的那个 `0xCC`，**这就是 §42 出错的直接原因**。

### 43.5 ✅ 两版差异（【逐条读码】级）

| 项 | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| mode 选择器读的偏移 | `+0xCC` | `+0xB4`（**`−0x18`**） |
| B 对象步长 | `0xE4` | `0xE4`（相同） |
| mode 设置器 | `0x0801A9E8` | `0x0801956C` |
| 设置器写入偏移序列 | `0xC8,0xCC,0xD0,…,0xE0` | `0xB0,0xB4,0xB8,…,0xCC` |
| **A 对象 mode 源字段** | **`+0x34`** | **`+0x2C`（`−8`）** |
| A/C 对象 mode 源字段写入点 | `0x0801A06C` / `0x08020702` | `0x08018BF0` / `0x0801F3F6` |

⚠️ **两版在同一逻辑字段上的位移量不一致**：B 对象 `−0x18`、A 对象 `−8`、C 对象 `+8`。
⇒ **不存在单一全局位移**（与 §40 的发现一致）；**任何"按位移换算字段"的做法都必须逐对象验证**。

### 43.6 ⛔ 为什么 §42 会错（方法教训，第 5 次同类）

§42 的推理是：「在 `+0x184` 一带找不到写者 ⇒ 该字段来自固件外部」。
错在两点：

1. **对象张冠李戴**：`+0x184` 是 **A 对象**的偏移，而 `mode` 选择器读的是 **B 对象**的 `+0xCC`。
   两个对象基址不同、步长不同，**偏移不可互相搬运**。
   正确做法是先确定**基址寄存器是谁**（`rsb`/`add`/`lsl` 三步算出基址与步长），再谈偏移。
2. **"找不到写者"的搜索本身不可靠**：本轮首次尝试时，
   工具只要在**基址字面量的 60 条指令窗口内**看到任何 `[rX,#0x18]` 存储就报"写者"，
   却没有校验该存储的**基址寄存器是否真的持有该数组** ——
   结果把 `vstr s0,[r4,#0x18]`（`r4` 属于**另一个**数组）报成了写者。
   改成**跟踪持有基址的寄存器集合**后，结论才稳定。

⇒ **新增红线**：跨对象比较前必须先解析 `基址 + 索引×步长` 三步算式；
**"窗口内出现即算命中"式搜索不得用于否定性结论**。

### 43.7 对本目标的意义

* `mode` 是**固件内部产生的**值（由 A 对象搬运到 B 对象），**不是外部注入**。
  之前"读 `mode` 就能知道驱动器走哪条位置来源分支"的说法**仍然成立**，
  但它**不是**一个"外部配置项"。
* **§41 的"位置三来源选择器"结论不受影响**（那是功能语义，已【逐条读码】）。
* 受影响的只有 §42，**现已作废**。

### 43.8 仍未解

  （`ldrh` ×2 → 改位 → `strh`），其**上游来源**未追。
