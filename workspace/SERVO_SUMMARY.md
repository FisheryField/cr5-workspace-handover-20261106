## 0. 一句话结论

**零点既不在控制器里、也不在 `homeEncoder.json` 里 —— 它由驱动器自己维持。**
`cali home` 时控制器只把每轴目标位置 `0x607A` 置 0，**驱动器**把位置实际值 `0x6064` 重新定基到 0；
控制器随后用 **`关节角 = 0x6064 × 360/(20000×101)`** 上报（**零偏置恒为 0**，见 §3.6 的数值证明）。

- **伺服 3.2.D.8**：驱动器**接受并保持**这次定基（7 ms 内 `0x6064` 跟到 0，且非易失）⇒ 关节值 ≈ 0 ✅
- **伺服 3.1.5.0**：驱动器**不接受**（`0x6064` 纹丝不动），且每次上使能套回旧零点 ⇒ 关节值 = 编码器绝对计数 ❌

> # ⛔ 两条必须优先于本文其他一切结论的更正
>
> **① `3.2.D.8` 不是本机可用的固件。**
> 用户实机确认：**`3.2.D.8` 无法满足机械臂的「运动」条件**，它只是在"静态标零"这一件事上正常。
> ⇒ ~~"修法 = 六轴全刷 3.2.D.8"~~ **作废**。
> ⇒ 真正待解决的问题是：**如何在 3.1.5.0 上让标零正常化。**
>
> **② `homeEncoder.json` 的 `innerEncoder` 不是被减掉的零偏置**（本文 §9 #7，本轮数值证实）。

## 2. 根因（最终版）

### 2.1 全链路时序（总线级，【实测】）

```
POST /calibrate/home 到达 t=0
  +0.006 … +0.697 s  逐轴（站 1003→1008，间隔 0.136 s）
                     邮箱 SDO **读取** 0x607C Home offset（两版都返回 0）
  +0.118 … +0.798 s  逐轴把 RxPDO 的 0x607A 目标位置 **置 0**
  +0.113 … +0.793 s  3.2.D.8：各轴 0x6064 **随之变 0** ✅
                     3.1.5.0：0x6064 **不变** ❌
  +0.9 s             写 homeEncoder.json
```

**3.1.5.0 随后还会丢**：POST+4.5~6 s（下使能）一度降到 ≈0，
**POST+10.85 s（重新上使能）弹回 45877** —— 与控制器日志 `16:31:18.454` / `16:31:24.850`
两次 `/settings/controlMode` 精确对应。

⇒ **回零没有"结果通道"。3.1.5.0 的定零是易失的；3.2.D.8 是非易失的。这就是全部差别。**

### 2.2 用户实机对照（决定性）

| 步骤 | 伺服 `3.1.5.0` | 伺服 `3.2.D.8` |
|---|---|---|
| 零点标定 | 关节归零 | 关节归零 |
| 下使能 | — | **保持 0** |
| **重新上使能** | **> 1°，甚至几十度** | 约 **0.4°**（上使能时机械臂晃动的读数误差） |

### 2.3 单轴 A/B 实验：因果已锁定（唯一变量对照）【实测】

**条件**：J1–J5 = `3.2.D.8`，**J6 = `3.1.5.0`（唯一变量）**。
**方法**：主控本地读 `codesyscontrol` 的 `/proc/374/mem` 偏移 `0x75630BB4`（关节值缓冲），9.2 Hz，**不占网络**。

| 事件 | J1–J5（3.2.D.8） | **J6（3.1.5.0）** |
|---|---|---|
| ① 上使能瞬间 | 完全不变 | **89.0045 → 2.9165（Δ −86.09°）** |
| ② 零点标定 | → 0 | → 0 |
| ③ 下使能 | 保持 ≈0 | 保持 ≈0 |
| ④ **重新上使能** | 仅物理摇晃 **±0.447°** | **0.0082 → 2.9229（Δ +2.91°）** |
| ④ 稳定 60 s 后 | ±0.447° | **2.9229°（比摇晃大 6.5 倍）** |

⇒ **只有 J6 出现离散跳变，两次使能都复现 ⇒ 伺服固件是唯一变量。**
⇒ 同时证明「上使能摇晃」确实存在（±0.447°、等幅交替、渐变），但它与 J6 的跳变是两回事。

## 3. L3 + L2：总线与换算（数值闭环）

### 3.1 换算公式

```
关节角 = 0x6064 位置实际值 × 360/(20000×101)
       scale = 1.782178e-4 °/count
```

### 3.2 六轴数值实证（决定性）【实测】

| 轴 | PDO 计数 | × scale | 实测关节值 | Δ(°) |
|---|---|---|---|---|
| J1 | 45877 | −8.176099 | −8.176508 | 0.000409 |
| J2 | −57977 | +10.332535 | +10.333052 | 0.000517 |
| J3 | 19080 | +3.400396 | +3.400566 | 0.000170 |
| J4 | −12807 | +2.282436 | +2.282550 | 0.000114 |
| J5 | −42461 | +7.567307 | +7.567685 | 0.000378 |
| J6 | −18502 | +3.297386 | +3.297551 | 0.000165 |

**六轴全部吻合到 0.0005° 以内**（≈0.00015 圈电机），残差对应 PDO 在 3 秒窗口内的 ±5 计数抖动。
⇒ **3.1.5.0 上控制器确实是按"零偏置 = 0"在算的。**

### 3.3 `innerEncoder` 是 PDO 的实时快照，不是结果【实测】

在 1111 字节周期帧的固定偏移 `603/660/717/810/879/950` 读 int32：

- `zero32_calibration.pcap`（3.2.D.8）中元组 `[598234, -192592, -580282, 389348, -718959, 576819]`
  出现 **1690 次**，**与 `homeEncoder.json` 15:45:16 记录逐位相同**；
- 标定请求（`15:45:15.448`）**之前**已出现 **1636 次**（最早 `15:45:12.177`，提前 3.27 s），之后仅 56 次。

⇒ **不是"回零后读回一个结果"，而是"把一个一直在流的实时字段抄了下来"。**

### 3.4 标定没有改变伺服上报的位置【实测】

按时间切分 3.1.5.0 抓包：

| 窗口 | PDO 元组 |
|---|---|
| 上使能前（1112 帧） | `[-603293, 202704, 585171, -394376, 709124, -566921]`（陈旧，不刷新） |
| 上使能后、标定前（4044 帧） | `[45882, -59041, 19067, -12875, -42448, -18473]`（实时） |
| 标定后（23718 帧） | `[45877, -57977, 19080, -12807, -42461, -18502]`（几乎没变） |

⇒ 在 3.1.5.0 上**伺服侧没有"把当前位置变成 0"这个动作**。

### 3.5 回零通道：控制器只做一件事

**控制器只把每轴 RxPDO 的 `0x607A 目标位置` 置 0**，然后驱动器自己把 `0x6064` 定基到 0。
开机对伺服的**全部 SDO 写入只有 PDO 配置**（`0x1600/0x1A00/0x1C12/0x1C13`），**没有对 `0x607C` 的写入**。

### 3.6 ★ 数值判定：`innerEncoder` 不作为偏置参与运算（本轮新增证实）

以 §3.2 的同一组数据做两种模型的对照（`sign` 由 J3 是唯一 `inverted:false` 推得）：

| 轴 | PDO×sign×scale（**无偏置**） | Δ | (PDO−inner)×sign×scale（**减法**） | Δ |
|---|---|---|---|---|
| J1 | −8.1761 | **0.0004** | −8.6227 | 0.4463 |
| J3 | +3.4004 | **0.0002** | +3.8499 | 0.4493 |
| J4 | +2.2824 | **0.0001** | +2.7344 | 0.4519 |
| J6 | +3.2974 | **0.0002** | +3.7442 | 0.4467 |
| （J2/J5 符号约定另有定义，两种模型都需换号；不影响结论） | | | | |

**减法模型的残差恒为 ≈0.45°＝ ±2506 counts × scale ＝ `innerEncoder` 自身的量级**
⇒ 减法模型**系统性错一个 `innerEncoder`** ⇒ **该公式不成立。**
**另一项独立反证**：`innerEncoder` 是**全局 RAM 值**，若真做减法，六轴关节角会同时偏 0.45°
—— 而 §2.3 实测六轴是 **0.0005°** 级吻合。

⇒ **结论：`homeEncoder.json` 的 `innerEncoder` 是标定时刻 `0x6064` 的一份记录（用途待查，
可能是诊断或失位修复），不参与关节角运算。**

### 3.7 一个可用的探针

TxPDO 每站带一个 16 位版本字 —— **`0x32D8` = 3.2.D.8，`0x3150` = 3.1.5.0**。
有总线抓包即可逐轴确认实际固件版本，**不必依赖控制器那个版本串**（见 §6.3）。

## 4. L1 + L2：Linux 主控与运行内存

### 4.1 标定链路（日志 + 反汇编）

```
POST /calibrate/home
  → DataSubProcess::caliHome @0xf0428
       · 把 6+6 个 double 从 *(this+0xE20)+0x3110 / +0x3278
         拷进 this+0x20C0(innerEncoder) / this+0x20F0(outEncoder)
       · 调用下层执行回零；置 isRequestCalihome = 1
  → robot_control::updateEncoderData @0x1d9e90
       · 每 300 ms 读 *(this+0xE20)+0xF4，步长 0x4D8（每轴完成标志）
       · 统计 → HomeNumdone : 0→2→4→6
  → 日志 "servo calihome done"
  → DataSubProcess::updateEncoderData @0xf9520
       · 写 settings/function/homeEncoder.json
```

全程 < 1 秒。**`caliHome` 里没有文件写入、没有 SDO 写入**（数值来自运行时结果缓存
`runtime+0x3100 / +0x3240`，由回零回调填充）。

### 4.2 标定时刻只写了 2 个文件

| 文件 | 性质 |
|---|---|
| `settings/function/homeEncoder.json` | **零点相关记录（现场判据用这个）** |
| `settings/function/loadParams.json` | 负载参数，与零点无关 |

### 4.3 内存侧：**没有可抢救的零点单元**（计划 A 已证否）【实测】

- 覆盖 `codesyscontrol` 的 7 个共享段 / 13.4 MB（100%），103 轮 / 92 s。
- 标定瞬间差分：定位到 10 MB 共享段 `/SYSVe901001b` 内 **6 轴 × 40 B 步长的 float32 记录**
  （至少两个实例：`0x73A40E24`、`0x73A84E24`）。
- **静止稳定性测试**：位姿与 f0 完全稳定，第二字段在两值间跳变 ⇒ **实时计算量，不是存储**。
- **写回实验**：对照组（往零区写 `de ad be ef`）能写住并保持 >2 s；
  但把 f1 写回 6 个槽位 ⇒ **立刻被覆盖**（回读既非原值也非写入值）。
- 段基址**不固定**（`0x73A00000` / `0x73900000` 之间变），同偏移处内容每次开机完全不同。

⇒ **控制器里没有一个稳定的"零点存储单元"可以抢救。**

### 4.4 `homeEncoder.json` 历史快照与固件版本对应【实测】

| 日期 时间 | `innerEncoder` | 备注 |
|---|---|---|
| 2026-09-18 19:27:04 | **全 0** | 六轴均 3.1.5.0 |
| 2026-09-22 12:01:40 | 非 0 | 版本未标注，不作结论 |
| 2026-09-22 14:37:00 | **全 0** | 版本未标注，不作结论 |
| 2026-09-22 15:45:16 | 非 0 `[598234, …]` | codex 标注 **3.2.D.8** |
| 2026-09-22 16:31:14 | **全 0** | codex 标注 **3.1.5.0** |

两端有明确标注的两次，与固件版本**完全对应**。

### 4.5 ★ 现场一行判据（整条调查里最实用的一条）

```bash
ssh root@192.168.5.1 "cat /dobot/userdata/project/settings/function/homeEncoder.json"
```

**使能状态下**点完"零点标定"再看 `innerEncoder`：

| 现象 | 判定 |
|---|---|
| 非全 0 | ✅ 正常，偏置记对了 |
| **全 0** | ❌ 就是这个故障 |

不需要抓包、不需要停栈、不需要抢总线。

### 4.6 仍未解：`innerEncoder` 为何在 3.1.5.0 上是 0

两版时序完全相同（都是 POST+0.9 s 写文件），而 3.2.D.8 记的是标定前读数、3.1.5.0 记的是 0。
最可能：`caliHome` 从 `runtime+0x3110` 取的是**回零回调的返回值**而非 PDO 镜像，
3.1.5.0 的驱动器没正确应答 ⇒ 结果缓冲被置 0。**仍是推断，需驱动器侧取证。**

## 5. L0 + `.app`：PC 侧与 CODESYS 应用层

### 5.1 `Application.app` 的"文件偏移 ↔ 运行时地址"映射（B 计划，已交付）

| 项 | 值 |
|---|---|
| 样本 | `data/Application.app`，1,076,068 B，MD5 `8416cf0eee070a640702c077eb904b4e` |
| 运行时镜像 | **`0x75a76000-0x75cb8000`**（maps 里被标成 `[stack:383]` 的匿名 `rwxp` 段，**不是栈**） |
| 主 Δ | **`0x75a95cd0`**（`runtime = file_off + Δ`，池内恒定、跨池跳变；**重启前后一致 ⇒ 可缓存**） |
| 映射规模 | **660 段 / 9 个 Δ 池**，`app_resolve.py --check` → **0/660 失败** |
| 覆盖率 | 文件 **29.2%**（314,171 B） |

**`.app` 的本质（已量化）**：**归档 + 加载时重定位** —— 文件里是低位占位值
（`0x0000aaaa` → 运行时 `0x75bc2a2a`），且**载荷被抽取**（每条记录丢 20/23/27/31 字节的头）
⇒ 运行时镜像比文件**小约 3.3%** ⇒ **必须分段，单一基址无解**。

```powershell
python tools\app_resolve.py --to-runtime 0x0e9f08      # → 0x75b5d58c
python tools\app_resolve.py --to-file    0x75a9da88    # → 0x00008000
python tools\app_resolve.py --check                    # 逐段复验，应 0 失败
```

### 5.2 ★ 顺手拿到的最高实用价值产出：842 个 PLC 符号名解析调用点

运行时镜像里 **842 处「内联符号名 + `bl` 解析服务」调用点、789 个 PLC 符号名**
（`data/appmap/name_calls.txt` 全表）。六轴轴参数通道每个都有确切地址：

```
Device.Application.IoConfig_Globals.a1.config.write   0x75b5d588   ← ★ α1 的入口
Device.Application.IoConfig_Globals.a1.config.read    0x75b5f398
Device.Application.IoConfig_Globals.a1.read/.write    0x75b600a2 / 0x75b5e2e0
Device.Application.IoConfig_Globals.a1.DSP402_State…  0x75b603cc / 0x75b5e5ec / 0x75b61156
a2..a6 同构各一份
```

调用形态：`bl <*+0x1a>` 紧跟 `"符号名\0"`，
桩体 `subw r4, lr, #1; mov lr, r5; ldr r6, [pc,#0x918]`（ARM↔Thumb 互调用）。

**另一条线索**：`.app` 自己就引用了 **`/tmp/ServoParamsWrite`**（`0x75b09362`）。

### 5.3 关键技术突破：`libdataSvr.so` 的 PLT 表已解开

- `.rel.plt` **2933 项**，`.plt` 35816 B。桩**不是均匀栅格**：
  2781 个 12 字节（纯 ARM）、150 个 16 字节（带 `bx pc; nop` 的 Thumb 互通桩）。
- 做法：在 `.plt` 内按 2 字节对齐扫 `add ip,pc,#imm` / `add ip,ip,#imm` / `ldr pc,[ip,#imm]!`
  三连，算出 GOT 槽再回查 `.rel.plt` ⇒ **2932/2933 命中**（`tools/plt_map.json`）。

> ⚠️ **踩过的坑**：`symtab` 的 `Value` 是**绝对地址**，**不要再加 section 基址**。
> `parseAndReqGetServoParams` 的 `Value=0xec03d` 直接就是绝对地址；
> 加 `.text` 基址 `0xbc7f0` 得到 `0x1a882d` 是**错的**（按错误的 `0x1a81fc` 反汇编 `readSDO`，
> 得到的是完全无关的 JSON 解析代码）。

### 5.4 HTTP 伺服参数读通道的协议（完全解开）

**端点**：`POST http://192.168.5.1:22000/settings/readServoParams`（**无需认证**）

```json
{"body":[{"key":"addr200117","servoNum":"J6"}]}
```

| 字段 | 规则 |
|---|---|
| `servoNum` | **必须是字符串 `"J1"`…`"J6"`**；数字直接类型检查失败。命中后写入 `3+r3 … 8+r3` ⇒ **EtherCAT 站号 3~8** |
| `key` | `"addr" + hex(0x2000+H组号) + 两位十进制(子索引)` |

日志唯一确定 key 格式：

```
[k] the key H01.17 is error.                    ← 解析失败，index/sub 归 0
[✓] start read sdo from codesys.
[✓] sdo read,slave=8,index=8193,subIndex=17,value=0.   ← 没有 fail 行
```

### 5.5 ★ 这条路在本机**从来没工作过**（决定性负面结果）

`DataSubProcess::readSDO`（`0xeba0c`，232 B）的邮箱握手：

```
if (this == 0) return -1
st = *(this + 0xe20)                      // 共享内存/状态块
if (st->[0x4c4] != 3 && st->[0x4c4] != 6) return -1      // 入口门禁
log("sdo read,slave=%d,index=%d,sub=%d,val=%d")
st->[0x4c8]=slave; st->[0x4cc]=index; st->[0x4d0]=sub
st->[0x4c4] = 1                           // 写请求
usleep(250000)                            // 250 ms
if (st->[0x4c4] != 3) return -1           // ← 失败在这里（无日志）
value = st->[0x4d4]; valid = (st->[0x4dc]==1); return 0
```

- 实测：写请求后**连续轮询 5 秒，`[0x4c4]` 永远不回到 3** ⇒ **CODESYS 侧从不服务那块共享内存邮箱**。
- **全日志历史（522,607 行）里 `sdo read,slave` 仅出现 9 次，全部是本会话的探测**。
- 所有读（H00/H01 组 × J1/J6，40+ 次）返回 `status:false, value:0`。

**`mToolServer` 也没有这条路**：`/mToolServer/mToolServer`（2,302,802 B，SOEM + libevent evhttp）
的全部 HttpServer 处理器只有升级 / 故障 / 网络类端点，**没有任何伺服参数/SDO 端点**
—— 它链 SOEM 的 CoE 只是为 FoE 固件下载服务。

### 5.6 总线层：两版固件下**控制器做的事逐字节相同**（【逐条读码】级）

| 抓包 | 总帧 | 非周期帧 | 邮箱交换 |
|---|---|---|---|
| `zero32_calibration.pcap`（3.2.D.8） | 73042 | 48 | 有 |
| `capture315_ethercat.pcap0`（3.1.5.0） | 56788 | **0** | 无（该窗口没标定） |
| `capture315_ethercat.pcap1`（3.1.5.0） | 28898 | 48 | 有 |

两组 48 帧的载荷**逐字节相同**。每站一次的邮箱事务是：

```
请求 (FPWR st=0x03eb…0x03f0 ado=0x1800):  00 20 | 40 | 7c 60 | 00 | 00000000
响应 (FPRD st=0x03eb…0x03f0 ado=0x1a30):  00 30 | 43 | 7c 60 | 00 | 00000000
```

`40`=CoE SDO Upload Request，`43`=带 4 字节数据的 Upload Response，
对象 **`0x607C:00 Home offset`**，六站**全部返回 0**。之后跟随 OD 名称表枚举。
**控制器只读不写 `0x607C`。**

⇒ **控制器对两版伺服发的命令完全相同，差异 100% 在驱动器内部。**

> ⚠️ **一处必须澄清的误读风险**：codex 的 `sdo_structured_audit.json` 里有对 `0x607C` 的 SDO 写
> （目标站 1003–1008，时间戳约 09-22 18:20）—— 那是 **codex 自己的 `ecat_zero` 工具发的**，
> 不是控制器发的。**不能据此推翻「控制器从不写 `0x607C`」。**

### 6.3 ⚠️ 附带的重要发现：控制器显示的伺服版本不可靠

### 6.4 ⚠️ 一处仍未解的矛盾：厂商参数地址

- **维护工具日志**里有 **259 项参数**，地址串 `200001 … 200E13`
  ⇒ 推出 `SDO 索引 = 0x2000 + 组号`、`子索引 = 组内序号+1`。
  该编码与现场抓包 `addr200C01` → `H0C.00`、`addr200117` → `H01.17` **逐字吻合**。
- 但**照这个地址去读，两版都全部 FAIL**（§6.2）。

**两者不可能同时成立。** 可能解释（**均未验证**）：

1. 那份维护工具日志**不是本机产生的**（是别的设备/别的版本）；
2. 维护工具**不走 EtherCAT SDO**，而是走驱动器的串口/调试口；
3. 地址编码不是"索引:子索引"，而是某种私有寻址。

⇒ **在解开这个矛盾之前，`H01.17 / H01.18 / H0C.02` 那组"编码器校零参数"的地址
不能被当成可靠结论。**

## 8. 伺服固件：`0x6064` 的完整生产链（已闭环）

### 8.1 基本参数

| 项 | 值 |
|---|---|
| D8 镜像 | `data/servo_fw_samples/elf/v328d8.bin`，338,072 B |
| 3150 镜像 | `data/servo_fw_samples/elf/v3150.bin`，328,860 B |
| flash 映射 | `0x08000000`；**两包 payload 起点不同**（D8 从 `0x08000000`、3.1.5.0 从 `0x08010000`） |
| OD 寻址公式 | **`base + subIndex × 0x329 + 字段偏移`**，`0x6064` 字段偏移 **`+0x238`** |
| 逐轴对象基址指针 | **`0x2000138C`**（D8）/ `0x2000129C`（3150 在别处），记录步长 **`0x329`** |

> ⚠️ **两包 payload 起点不同**是最大的坑：拿 payload 直接逐字节比对会得出"94% 不同"的**错**结论。

### 8.2 ⛔ 关键否定：零点逻辑**不走** CiA402 索引通道

**`0x607C`(Home offset) / `0x6098`(Homing method) / `0x6063` 在镜像里完全不存在**
⇒ 改从 CiA402 索引入手是**死路**。

### 8.3 ★★★★ 完整链条（逐条反汇编得出，全部有地址）

```
驱动器 0x6064 → +0xA8（逐轴基准）+ sl + 0x20000·fp
             → × sb ÷ 20000        ★ 归一化（常量 20000 在此）
             → 逐轴对象 +0xB0
             → ＋ [sp+0x18]+0x10
             → 逐轴对象 +0x234
             → 经函数指针 [0x20000078+8] 换算
             → 逐轴对象 +0x238  ★★★ 位置实际值
```

★ **两个 `0x20000` 成对出现、可约去**（`× 0x20000` 后 `÷ 0x20000`）
⇒ 有效除数就是 **`20000`**，即文档 `360/(20000×101)` 里的那个。

**核心算式（D8，分支甲乙结构相同、符号相反）**：

```
x = A(+0x04) − B(+0x0C) + C        → +0x18
比例 = float(x) / float(D=[rX,#0xc]) → +0x10   （单精度 vdiv.f32）
q  = (int)(比例 + 0.5)              → +0x14   ★ 就近取整，两版实现不同
余 = q·D − A + B                    → +0x1C
余 − (+0x20)                        → 逐轴对象 +0xB0
… 随后是含 20000 / 0x20000 的 64 位乘加换算段
```

### 8.4 两版在该链路上的差异（【逐条读码】级）

| # | 环节 | 3.2.D.8 | 3.1.5.0 |
|---|---|---|---|
| ① | 位置分解（x → 商/余） | **就地**写在逐轴对象 `+0x10/+0x14/+0x18/+0x1C` | **集中**结构 `0x20003DB0`（商 `+4` / 余 `+0`）+ 一台状态机 |
| ② | **取整 `q = round(x/D)`** | **硬件单精度**：`vadd.f32 #0.5` → `vcvt.s32.f32`（**2 条指令**） | **软件 IEEE 双精度**：f→d 提升 → 软加/减 `0.5` → d→int（**3 次调用**） |
| ③ | `20000` 归一化站点 | 位置链段内 **有**（`movw #0x4E20 @0x080155A6`） | 位置链段内 **无** |
| ④ | 位置值写入点 | `0x08015602` | `0x08014B62` |

**精确到指令级的差异（本目标最细粒度）**：

| 项 | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| 前段（算 `+0x10`） | `vldr +0x18`→`vcvt`→`vldr [r5,#0xc]`→`vcvt`→`vdiv.f32`→`vstr +0x10` | **逐条相同** |
| **后段（取整）** | **`vadd.f32 #0.5` → `vcvt.s32.f32`** | **`bl 0x08000720`(f→d) → 双精度加/减(0.5) → `bl 0x080006E2`(d→int)** |

⇒ 两版都想要"把 `+0x10` 取整成整数"；**D8 是 `(int)(x+0.5)` 就近取整**，
3150 走**更高精度但符号处理不同**的路径（两站点分别用软加 / 软减）
⇒ **在边界值与负值上结果会不同**。

> ⚠️ **④ 状态机（仅 3150 有）已降级为「未证实」**：原判别式
> （`movw #0x329` + `[rX,#0x24]` + `cmp #7` + `tbb`）**收紧时假阴性、放宽时假阳性**，
> 整体不可用。改用"整段形态滑窗匹配"也未找到 D8 对应物，但该否定**偏弱**
> ⇒ 只能说"**用现有手段找不到对应物**"，**不是"已证明不存在"**。

### 8.5 `mode` 的完整写入链（已解）

`mode` 决定"上报位置从哪来"（三来源选择器），**是固件自己写的，不是外部注入**：

```
[0x20009A70 + 轴×0x64 + 0x34]        ← mode 的源字段（0x64 步长逐轴对象）
   │ D8 0x08019EEC  ldr [r6,#0x34] → 压栈 [sp+0x5c]（第 6 实参）
   ▼ mode 设置器  D8 0x0801A9E8 / 3150 0x0801956C
   │ movs r0,#0xCC(D8)/#0xB4(3150) ; str r1,[r0,r4]
   ▼ [0x2000C6C8 + 轴×0xE4 + 0xCC(D8)/+0xB4(3150)]   ★ mode 最终落点
   │ D8 0x08016986 / 3150 0x080163DC
   ▼ 上报位置的三来源选择器
```

**三来源选择器语义（两版共有，不是差异）**：

```
if (mode==1 && flag==0)  位置 = +0x4C + sgn·(对)
elif (mode==0)           位置 = +0x60..+0x68 对
else                     位置 = 第三支(+0x48/+0x50 对)
```

### 8.6 ⚠️ 三个逐轴对象**基址/步长都不同，偏移不可互相搬运**

| 对象 | D8 | 3150 | 步长 |
|---|---|---|---|
| A（mode 源字段） | `0x20009A70` | `0x20009580` | `0x64` |
| B（mode 落点 / 选择器读取处） | `0x2000C6C8` | `0x2000C1D8` | `0xE4` |
| C（另一处 mode 落点） | `0x20008548` | `0x20008060` | `0x164` |

**同一逻辑字段在两版上的位移量并不一致**：B 对象 `−0x18`、A 对象 `−8`、C 对象 `+8`
⇒ **不存在单一全局位移**；按位移换算字段必须逐对象验证。

### 8.7 静态可达边界（诚实标注）

| 类别 | 内容 |
|---|---|
| **已建立** | 位置环读取链 / 写入链、OD 寻址公式、两版差异（含指令级）、`mode` 写入链、`0x20003DB0` 自闭环 |
| **被挡住（纯静态不可达）** | 零点定基的**真正机制**（差异无法排除、无实验对照）、位置换算函数（函数指针表在 RAM、静态无初始化）、**RAM 里的对象描述符内容**、`+0xB8`/`+0xBA` 写入者（全镜像零写入） |

### 9.1 本次调查最反复的教训（方法论）

**这个调查里最贵的错误全部来自"用间接指标替代直接读码"，以及工具本身的静默假象。**

1. **把"没观测到 X"当成"X 不存在"** —— 连错三次的共同原因（#1/#2/#4）。
2. **跨版本比较上连续错 5 次**（§15→16、§18→19、§20→21、§21→22、§39→40）
   ⇒ 现已强制**证据等级制度**（见文首）。**【计数/普查】不得用于结论。**
3. **工具的"静默空结果"共 6 类**：
   - 缺宽指令形式（`ldrh.w` 等）⇒ 对肉眼可见的访问返回 0 处；
   - `struct.unpack_from('<H')` 半字序错 ⇒ 恒返回空且不报错；
   - **`md.disasm()` 在第一个无法解码字节处静默停止** ⇒ 实测只走完 **151248 条里的 1058 条（0.7%）**，
     此前所有"全镜像线性反汇编搜索"返回的 0 处**全是假否定**；
   - **固件包带 ~0x20 字节厂商头** ⇒ 按 `addr-0x08000000` 切片会解出错位垃圾（能"成功"解码，所以不报错）；
   - 检测器漏 `vldr`/`vstr` ⇒ 全部浮点内存访问不可见；
   - 检测器在同一寄存器被重新加载时未停止 ⇒ 用量表绝对值虚高约 2 倍。
4. **固定做法（现已强制执行）**：
   - **任何搜索/检测类工具必须先用一个已知存在的样本做正例自检**
     （本轮正是靠它抓到上述第 3、4 类，否则结论整个是错的）；
   - **跨对象比偏移之前，必须先解析 `基址 + 索引×步长` 三步算式**（`rsb`/`add`/`lsl`）；
   - **"窗口内出现即算命中"式搜索不得用于否定性结论**；
   - **跨构建绝不能用 RAM 绝对地址判定"有无"**（链接器会移动 RAM 全局）；
   - **给代码安语义前先做"可行性约束检查"**（该 MCU/该构建是否支持该特性？该指令在整镜像里出现几次？）。

### 12.1 ⛔ 更正：`0x607C` 等索引**并非不存在**（本文 §6.2 的表述需修正）

主文档（`FINDINGS.md` §五 D）与本文 §6.1 曾记：
> ~~"`0x607C`(Home offset) / `0x6098`(Homing method) / `0x6063` / `0x6060` 在镜像里完全不存在"~~

**该结论是被工具缺陷误导的，现更正。** 真相是：**它们不存在于 `movw` 直接比较里，但全部通过跳表映射到真实处理器。**

**为什么会误判**：`movw` 立即数扫描器的两个 bug（本轮由**正例自检**抓出）——
① 我把 `i` 位当成必须为 0（Thumb-2 `movw` 里它是 **1**）；
② `imm3` 掩码写成 `0x7`，实际在 `w2` 的位 **14–12**（应为 `0x7000`）。
两个 bug 叠加使**所有** 32 位常量都解成很小的数 ⇒ 恒不命中。
**是正例对照 `movw r1,#0x4e20 @0x080155A6`（已知存在）返回 0 处才暴露的。**

**修正后的实测**（工具 `tools/servo_imm_dump.py`、`servo_idx_hunt.py`，正例全部通过）：

| 立即数 | D8 | 3150 |
|---|---|---|
| `0x4E20`(=20000) | 2 处（`0x080155A6`、`0x0801A6C4`）✅ | 1 处（`0x08019248`）✅ |
| `0x329`（描述符步长） | **142 处** ✅ | **143 处** ✅ |
| `0x6041` | 1（枢轴） | 1（枢轴） |
| `0x605C` / `0x6064` / `0x6072` / `0x608E` | 各 1（枢轴） | 各 1（枢轴） |
| `0x60FB` | 2 | 2 |
| `0x607C` / `0x607E` / `0x6098` / `0x6063` / `0x6060` | **0（不在直接比较里）** | **0** |

⇒ **它们走跳表**。分派器是「**稀疏二分枢轴 + 区间内 `tbb`/`tbh` 跳表**」，不是稠密比较链。

### 12.2 ✅ OD 索引分派器已完整解出

**入口**：D8 `0x0800289C` / 3150 `0x080027B8`（两版**逐条同构**）

```
idx = (uint16)(arg1 − 0x800·arg2)          ; mls r3, r3, r2, r1
```

**5 个稀疏二分枢轴**（测试顺序）：`0x608E` → `0x6072` → `0x6064` → `0x605C` → `0x6041`
**区间解析**：`cmp r3,#imm` 对 + `tbb`/`tbh` 跳表
（`tbb` 基址 = 该指令地址 + 4；`tbh` 同，条目为半字）

**`0x6072..0x6095` 的 `tbh` 表**（36 项，两版**结构完全相同**）：

| k（idx − 0x6072） | D8 handler | 3150 handler | 说明 |
|---|---|---|---|
| 0 | `0x08002AC4` | `0x080029E0` | **默认/未实现** |
| 1..12 | `0x08002EC8` … `0x08002F8E` | `0x08002DE4` … `0x08002EAA` | **真实处理器**（含 **k=10 → `0x607C`**、k=12 → `0x607E`） |
| 13..20 | `0x08002AC4` | `0x080029E0` | 默认 |
| 21, 22 | `0x08002FA0`、`0x08002FB2` | `0x08002EBC`、`0x08002ECE` | 真实（`0x6087`、`0x6088`） |
| 23..35 | 默认 | 默认 | |

⇒ **`0x607C` 有处理器**：D8 `0x08002F6A` / 3150 `0x08002E86`。
⇒ `0x6098` 落在 `0x608E` 分支的「偏移 10 < 0x36」⇒ 处理器 `0x08002A38`。

### 12.3 ★★ 关键发现：每个 handler 就是「暴露逐轴对象的一个字节」

**统一形态**（整张表都长这样）：

```
movw r3,#0x329 ; muls r3,r2,r3      ; r2 = 轴号
ldr  r4,=<描述符数组基址>
add  r3,r4 ; addw r3,r3,#<off>       ; r3 = &descriptor[轴].field
str  r3,[r0,#0x18]                   ; 把字段地址交给核心
b    <公共尾>
```

⇒ **每个 OD 对象 = 逐轴对象里的一个字段**，分派器就是「索引 → 结构偏移」映射。
⇒ 这也**最终解释了 §6.1 的那个"矛盾"**：OD 表不含索引，但**分派器提供索引→偏移**，两者靠**顺序**对应。

**实测规模**：每版 **98 个 stub / 97 个 `(基址, 偏移)` 对** —— 与 OD 元数据表的 **97 条记录一一对应**。

### 12.4 ★★★ 决定性对比：两版 OD 访问层**逐项完全相同**

| 项 | 结果 |
|---|---|
| 描述符数组基址 | D8 `0x2000138C` / 3150 `0x2000129C`（**唯一差别**） |
| **97 个描述符偏移** | **逐项完全相同，0 处差异**（delta 直方图 `{0: 97}`） |
| 分派器结构（枢轴 + 跳表 + 区间判定） | 逐条同构 |
| OD 元数据表 97 条（名字/类型/位宽/属性/顺序） | 完全相同（早前已实证） |

⇒ **OD 访问层是"纯重定位"关系，两版在此层的唯一差异就是描述符数组基址那 4 个字节。**
⇒ 这把「版本差异不在 OD 层」从**推测**升级为**三重实证**

### 12.5 ⚠️ handler 有两种形态（读码时别踩）

不是所有 handler 都带 `movw #0x329` 那段（这正是 §12.4 的 98 个 stub 比 97 条记录多 1 的原因）：

* **形态 A（多数）**：完整 `movw #0x329 / muls / ldr <基址> / addw #off / str [r0,#0x18]`
  ⇒ 离线一次就能解出 `(基址, 偏移)`。
* **形态 B（少数）**：**只有一条 `b <公共处理器>`**，不带偏移算式。
  例：**`0x6098`(Homing method)** 的 handler 是 D8 `0x08002A38` / 3150 `0x08002954`，
  内容只有 **`b 0x080030AE`**；而 `0x080030AE` 恰好就是偏移表里 **`0x2A4`** 的那块处理器
  ⇒ 反推出 `0x6098 → 0x2A4`。

⇒ **方法**：先用形态 A 建偏移表，再用「形态 B 的跳转目标地址」去偏移表里**按地址反查**，
即可把其余索引补齐。**只看形态 A 会漏掉一批对象。**

### 12.6 ★ 函数指针表穷尽性否定（本轮把这条路走到头）

位置链最后一环是 `+0x234 → call table[+8] → +0x238`，其中
`table` = **`0x20000078`**(D8) / **`0x20000074`**(3150)。本轮用**四种独立方法**确认：

| 方法 | D8 | 3150 |
|---|---|---|
| 字面量基址 + **直接** `str` | 0 写 / 35 读 | 0 写 / 32 读 |
| **有效地址**（基址+偏移，覆盖 `0x20000064+0x14` 这类别名） | **0 写** / 40 读 | **0 写** / 36 读 |
| 从 flash 拷入的**块拷贝循环**（含 flash 源 + 该目标） | 无 | 无 |
| flash 里的代码指针数组（启动拷贝的源） | 有 4 处，但**无一被引用/拷贝** | 同 |

⇒ **【结论·可判定】这张表在整个应用镜像里从未被写入，只被读取 40/36 次。**

**这排除了三种解释**：
* ❌ 不是"被某个我没找到的 `str` 写入"（有效地址也算了，0 写）；
* ❌ 不是"从 flash 初始化数组整体拷入"（无这样的拷贝循环）；
* ❌ 不是"别名基址 + 大偏移"（已把 `0x20000000..0x20020000` 全部字面量的
  有效地址算了一遍）。

**⇒ 剩下两种，都不在本镜像内**：
* bootloader 区（flash `0x08000000..0x08002897`，独立于 FoE 应用区）负责初始化；**或**
* 该 RAM 被**应用镜像之外**的机制预置（调试器/另一核/厂商工具）。
  ⚠️ 无论哪种 ⇒ **纯静态分析到此为止，必须运行期 RAM 转储**。

**读取方的偏移集合**（全是 4 的倍数，佐证"函数指针数组"判断）：
`0x18 0x1c 0x24 0x2c 0x38 0x44 0x4c 0x54 0x58`（另有一处基址 `0x2000004c` 用 `+0xc`）。

### 12.7 ⚠️ 附带发现的独立异常：向量表里挂的 Reset 不是函数入口

两版向量表 `[1]`（Reset）**都是 `0x0801019D`** ⇒ 真实地址 `0x0801019C`。
但在 `0x0801019C` 反汇编得到的是**一条 `ble` 的中间**；`0x080101B6`
（`Default_Handler`，填充用的 `0x080101B7`）同样落在 `ble` 中间。

* 该区域在 **2 字节网格上完全自洽**（`f1 ee 10 fa` = `vmrs` 是 4 字节指令，边界对得上）
  ⇒ **不是解码偏移问题**。
* ⇒ **向量表里挂的 Reset 指向的不是一个函数入口** ⇒
  说明**启动路径可能不经过这张表**（例如 bootloader 直接跳到应用入口，
  或该表在别处被改写）。

⚠️ **这条只影响"从 Reset 往下追启动代码"这一种方法**，不影响本轮其它结论
（分派器/偏移表/函数指针表都是从**各处调用点**反查的，不依赖启动路径）。

### 12.9 ★★★★ 归零链条的核心函数已读通（D8 `0x08010E60`）—— 并解决 `+0xB8` 三个悬案

这是**周期性逐轴位置更新函数**（每周期每轴调用一次；`r0`=轴号，`r1`=轴运行时结构 `r4`）。
**逐条读码全文如下**（D8；`r5 = 0x2000138C + 轴×0x329`）：

```asm
08010E60  push {r4,r5,r6,lr}
08010E66  movw r0,#0x329 ; muls r0,r6,r0      ; 轴号 × 步长
08010E6E  adds r5,r0,r1                        ; r5 = &描述符[轴]
08010E72  ldrh.w r0,[0x200016B5 + 0xB8]        ; ★ G1 = 全局门控
08010E76  cbnz r0, SKIP                        ; ★★ G1≠0 ⇒ 整个重初始化块被跳过
08010E78  ldrh r0,[r4,#0x36]                   ; ★ 描述符锁存位
08010E7A  cmp  r0,#1 ; bne SKIP
08010E7E  ldr.w r0,[r5,#0x230]                 ; 参考位置
08010E82  str  r0,[r4,#0x30]                   ; ★ 目标位置 := 参考位置
08010E84  movs r0,#0
08010E86  str  r0,[r4,#0x20]                   ; ★ 步长 := 0
08010E88  ldr.w r0,[r5,#0x1AF]                 ; 位置实际值
08010E8C  ldr.w r3,[r5,#0x31F]                 ; + 修正
08010E90  adds r1,r0,r3
08010E92  ldr  r0,=0x20000078
08010E94  ldr  r2,[r0,#4]                      ; 函数指针表 slot 1
08010E96  mov  r0,r6 ; blx r2                  ; 换算(轴, 参考)
08010E9A  str  r0,[0x20000030]                 ; 发布全局
08010E9E  ldr  r1,=0x20000034
08010EA0  ldr  r0,[r4,#0x30] ; str r0,[r1]     ; 发布全局
08010EA4  ldrh.w r0,[0x200016B5 + 0xB8]        ; SKIP:
08010EAA  strh r0,[r4,#0x36]                   ; ★★★ 锁存 := 当前 G1
08010EAE  ldrh.w r0,[0x200016B5 + 0xB8]
08010EB2  cmp  r0,#0 ; bne return0             ; G1≠0 ⇒ 本周期不发布
08010EB6  ldr.w r0,[r5,#0x1AF] ; ldr.w r3,[r5,#0x31F] ; adds r1,r0,r3
08010EC0  ldr  r0,=0x20000078 ; ldr r2,[r0,#4] ; mov r0,r6 ; blx r2
08010EC8  str  r0,[r4,#0x14]                   ; 参考位置 := 换算(...)
08010ECA  ldr  r0,=0x20000100 ; ldr r1,[r4,#0x14] ; ldr r2,[r0,#8]
08010ED0  mov  r0,r6 ; blx r2                  ; 使能/就绪查询
08010ED4  cmp  r0,#1 ; bne return0
08010ED8  ldr  r1,[r4,#0x30]                   ; 目标
08010EDA  ldr  r0,[r4,#0x14]                   ; 参考
08010EDC  subs r0,r0,r1 ; str r0,[r4,#0x1C]    ; 偏差 := 参考 − 目标
08010EE0  ldrh.w r0,[0x200016B5 + 0xBA]        ; ★ G2
08010EE6  cbz  r0,USE_DIFF
08010EE8  movs r0,#0 ; str r0,[r4,#0x24]       ; ★ G2≠0 ⇒ 强制消差步长 = 0
08010EEE  ldrd r0,r1,[r4,#0x1C] ; subs r0,r0,r1 ; str r0,[r4,#0x24]  ; 否则 偏差−偏差2
08010EF6  ldrh r1,[r4,#0x34] ; cbnz r1,TAKE_STEP
08010EFA  ldr  r0,[r4,#0x24] ; cmp r0,#0
08010EFE  blt  NEG ; mov r1,r0 ; b CMP
08010F04  rsbs r1,r0,#0                        ; NEG:
08010F06  ldr  r2,[r4,#0x28] ; cmp r1,r2 ; ble STORE   ; |步长| ≤ +0x28 ⇒ 直接存
08010F0C  ldr  r0,[r4,#0x20] ; str r0,[r4,#0x1C]  ; TAKE_STEP: 回退到上一步
08010F10  ldr  r0,[r4,#0x2C] ; cmp r0,#3 ; bge SET_FLAG
08010F16  adds r0,r0,#1 ; str r0,[r4,#0x2C]     ; 计数器 +1
08010F1E  movs r0,#1 ; strh r0,[r4,#0x10]       ; ★ 达 4 次 ⇒ 置位 +0x10，清计数器
08010F28  movs r0,#0 ; str r0,[r4,#0x2C]        ; STORE: 清计数器
08010F2C  ldr  r0,[r4,#0x1C] ; str r0,[r4,#0x20] ; 保存上一步
08010F30  ldr r0,=0x20000100 ; add.w r1,r4,#0x1c ; ldr r2,[r0,#4]
08010F38  mov r0,r6 ; blx r2                    ; 另一个钩子
08010F3C  ldrb.w r0,[r5,#0x1AE]                ; ★ 控制字
08010F40  and r0,r0,#0x80 ; cmp r0,#0x80 ; bne POS
08010F48  ldr r0,[r4,#0x1C] ; rsbs r0,r0,#0     ; bit7 ⇒ 取负
08010F50  str r0,[r4,#0x18]
08010F52  ldrh r0,[r4,#8] ; cmp r0,#1 ; bne C2
08010F58  ldr r0,[r4,#0x18] ; cmp r0,#0 ; bgt CLAMP_MIN
08010F5E  ldrh r0,[r4,#0xa] ; cmp r0,#1 ; bne CLAMP_MAX
08010F64  ldr r0,[r4,#0x18] ; cmp r0,#0 ; bge CLAMP_MAX
08010F6A  ldrh.w r0,[r5,#0x140] ; bic r1,r0,#0x1000 ; strh r1,[r5,#0x140]  ; 上限钳位
08010F7C  ldrh.w r0,[r5,#0x140] ; orr r1,r0,#0x1000 ; strh r1,[r5,#0x140]  ; 下限钳位
08010F8C  ldr r0,[r4,#0x18] ; str r0,[r4,#0xc]      ; 有效步长
08010F90  ldr r1,[r4,#0x1C] ; ldr r0,[r4,#0x30] ; add r0,r1
08010F96  str r0,[r4,#0x30]                         ; ★ 目标位置 += 有效步长
08010F98  movs r0,#1 ; pop {r4,r5,r6,pc}            ; 返回 1（已更新）
08010F9C  movs r0,#0 ; b ...                        ; 返回 0（未更新）
```

#### ✅ 这解决了文档里关于 `+0xB8` 的**三个悬案**

| 悬案 | 答案 |
|---|---|
| 「`+0xB8` 全镜像零写入站点」 | **它不需要被写入** —— `+0xB8` 是**全局 `0x200016B5 + 0xB8`**（`ldrh.w` 读，**不在描述符里**）。之前找的是描述符字段，找错了对象。 |
| 「`+0xB8` 用途未知」 | 它是**全局门控 G1**：`G1 ≠ 0` ⇒ 跳过整个重初始化块，且本周期不发布参考位置。 |
| 「§16 B 的"一次性重初始化"为何是一次性」 | **靠 `+0x36` 锁存实现**：`+0x36 := G1` 在**每次调用**都执行（`0x08010EA4`，在 `blx` 之后**无条件**）⇒ G1 一旦变为非 0，`+0x36` 就被写成非 0，`cmp #1` 从此不再成立 ⇒ **只触发一次**。文档记的「`+0x36 == 1` 触发」是对的，但**机制**（锁存回写）此前没找到。 |

#### ⚠️ 同时纠正一个方法学盲点

`+0x36` 在 D8 里有 **16 处 `strh`** 写入点、`+0x06` 有多处读取 ——
**这个函数是被每个周期调用的**，所以它内部的写操作在我之前的"写入者普查"里**根本不可见**（普查只看了少数几个字段）。
⇒ **`§18/§19` 里那张"字段写入点"清单是严重不完备的**，后续凡是要判定"两版某字段行为差异"，
**必须先把这种每周期调用的大函数读通**，否则普查会给出假阴性。

#### 3150 的对应物（⚠️ 见 §12.11：**不是同构平移**）

初次尝试按"地址平移"估计为 `0x080115F0` 一带 —— **该估计是错的**，见 §12.11 的实际定位结果。
`0x0801160E/0x08011628` 那对 `[r4,#0x36]` 在 3150 里是**进度计数器**（`cmp #0xc` 阈值），
**不是本函数的锁存位**。

### 12.10 ★★ 3150 的对应函数**已定位**，并发现一处**结构性差异**

**3150 对应函数入口 = `0x080146EC`**（D8 是 `0x08010E60`）。定位依据**不是地址算术**，而是：
两版都读描述符 `+0x31F`，且 3150 的 `0x0801474C / 0x080147B0` 与 D8 的 `0x08010E8C / 0x08010EBA`
**差值相同**（−0xC740）；该处也是 slot `+0x4C` 的唯一调用点。

⚠️ **但两版这个函数并不同构**：

| | D8 `0x08010E60` | 3150 `0x080146EC` |
|---|---|---|
| 序言 | `push {r4,r5,r6,lr}` | **`push.w {r4,r5,r6,r7,r8,lr}`** |
| 结构基址数 | 1 个（`0x2000138C`） | **4 个**（`0x20003D44` / `0x2000129C` / `0x20003CB0` / `0x20003D20`） |
| 额外初始化 | 无 | **有**：写 `+0x2E3`/`+0x2E5`/`+0x2E9`（`muls #0x64` 换算） |
| 重初始化块 | **有**（`0x08010E7E..0x08010EA2`） | **未见** |

#### 判别式与强度说明（诚实标注）

我用的判别式是「**同一函数内**同时出现 `[x,#0xB8]` 读、`[y,#0x36]` 写、以及 `cmp #1`」：

| 版本 | 命中 |
|---|---|
| **D8**（正例自检） | **2 处** —— `0x08010E7A` 与 `0x08010ED4`，正是逐条读码确认的那两个 `cmp #1` ✅ |
| **3150** | **0 处** |

⇒ 两版**都**有 `+0x36` 的读/写点（D8 在 `0x08010E78/0x08010EAA`，3150 在 `0x0801160E/0x08011628`），
所以这个 0 **不是**"指令不存在"造成的。

⚠️ **但这个判别式的强度是【计数/普查】级，不是【逐条读码】级** —— 它依赖 `cmp #1` 这个 C 层表达式没被编译器改写。
**⇒ 只能作为"两版在此处确有差异"的强线索，不能单独作为结论。**
（另注：我试过用「`ldr/str/movs#0/str` 四连」做形状判别式，**失败** ——
两版各有 7/10 处命中，那是通用寄存器回退代码，**该形状不是判别式**。）

#### ⇒ 结论（限定表述）

**D8 的「一次性位置指令重初始化」在 3150 里没有找到对应物，且两版这个函数在结构上明显不同**
（3150 版本更大、初始化更多结构）。
⚠️ **这仍属「用现有手段找不到」，不是「已证明不存在」** ——
与 §41 对状态机的结论同级。要定论需**运行期对照**。

### 12.11 ⛔ 决定性的负面结果：**这版固件没有 CiA402 Profile Homing 状态机**
两版**完全一致**：

| 对象 | 计算它地址的站点数 | 结论 |
|---|---|---|
| `+0x1AE` 控制字（`0x6040`） | **只有 2 处读取**，且测的是 **bit7 / bit6** | 位置环方向/钳位 —— **不是回零** |
| `+0x2A4` Homing method（`0x6098`） | **只有 1 处**（= 分派器 handler，仅发布字段地址） | **无任何消费者** |
| `+0x22C` Modes of operation（`0x6060`） | **只有 1 处**（= 分派器 handler） | **无任何消费者** |

⇒ **`0x6098` / `0x6060` 只被 OD 层暴露，核心逻辑从不读它们。**
⇒ **CiA402 Profile Homing（模式 6 / 控制字 bit4 / 方法 35）在这版伺服固件里不存在。**

**这解释了为什么"零点逻辑不走 CiA402 索引通道"** —— 不是走别的通道，而是
**`0x6064` 的重新定基不是由 homing 状态机做的**。

⇒ **真正的定基机制只能是「目标位置 `0x607A` 的累加 / 偏移更新」那条路**（本函数的 `+0x30 += 步长`）。
⚠️ **但"哪一行决定定不定基"仍未定位** —— 这是现在最聚焦的下一个目标。

### 12.12 ★ `+0xA8` 群组已澄清：它们是**每轴比例**，不是零点基准

上一轮把 `+0xA8` 当成「基准位置」，据此推「谁写 `+0xA8` 就是定基点」。**本轮读到实际代码后否证了该假设。**

`+0xA8` 在全镜像里**只有一个写入点**（D8 `0x0801CC84` / 3150 `0x0801B7B0`），
所在块 `0x0801CC5C..0x0801CCD4` 是一组**纯比例计算**，只依赖配置字段：

```
+0xA4 = +0x08 × +0x18 ÷ (+0x24 × C × +0x34)
+0xA8 = +0x08 × +0x18 ÷ (+0x24 × C × +0x34)
+0xAC = +0x2C × +0x18 ÷ +0x30
+0xB0 = +0x2C × +0x18 ÷ +0x34
+0xB4 = +0xDC × +0x18 × +0x34 ÷ +0x30
```

⇒ **两版这块逐条同构**（纯重定位）⇒ 这些是**单位/齿轮换算比例**，配置一次、运行中不变。
**它们是"常量"，不是"偏移量"。**

#### ⇒ 一个重要的解释性结论（限定表述）

**位置链里没有任何"当前零点偏移"变量。** `0x6064` 是「原始计数 × 常量比例」的纯函数。

⇒ 这**恰好解释了为什么这版固件没有 homing 状态机**（§12.11）：
**软件侧根本不参与定基** —— 定基必然发生在**编码器原始读数**那一层
（硬件/编码器接口，或读计数时的固件最内层处理）。

⚠️ **这是推论，不是已证结论**：我没有在软件里找到任何偏移变量，但**"找不到"不等于"不存在"**
（该链的输入来自编码器外设，可能由硬件寄存器组管理）。

#### 一条不成立的普查（留档以免重踩）

我做过一次「逐字段写/读次数两版对比」普查，报出 33/91 对字段有差异 —— **该结果不可用**：
`+0x020`/`+0x024` 这类偏移在镜像里出现数百次（**绝大多数是 `[sp,#0x20]` 栈访问**），
我的过滤没能把它们区分开 ⇒ **噪音淹没信号，不得引用**。

### 12.13 ★★ 关键澄清：链条字段分布在**两个不同结构**上（之前混为一谈）

**这是本轮最重要的结构性澄清**，也解释了为什么之前几次"字段写入点"调查都失败：

| 基址 | 来源 | 承载的字段 |
|---|---|---|
| **描述符数组**（OD 字段存储） | D8 `0x2000138C` / 3150 `0x2000129C`，步长 `0x329` | `+0x1AF` 位置实际值、`+0x230` 参考、`+0x234` 中间量、`+0x238` 位置实际值、**`+0x2xx` 全部 OD 字段** |
| **轴运行时结构** | `0x08010E60` 的**第 2 个参数 `r4`** | **`+0x14` 参考位置**、**`+0x1C` 偏差**、`+0x20` 步长、`+0x24` 修正步长、`+0x30` 目标位置、`+0x36` 锁存位、`+0x10` 标志、`+0x28` 容差 |

⇒ **`+0x14` / `+0x1C` / `+0x20` / `+0x30` / `+0x36` 不在描述符上**，
**按描述符基址去扫它们必然全部返回 0** —— 这正是前面几轮"0 命中"的原因。

⇒ 所以 A 项（`+0x14`/`+0x1C` 两条线）**必须按轴运行时结构来查**，而它的基址是**函数参数**（运行时才知道）。

### 12.14 ★★ 两版对应函数的职责划分**根本不同**（逐条读码）

把 D8 `0x08010E60`（0x13E 字节）与 3150 `0x080146EC`（0x14C 字节）**并排读完**后：

| | D8 `0x08010E60` | 3150 `0x080146EC` |
|---|---|---|
| 序言 | `push {r4,r5,r6,lr}` | `push.w {r4,r5,r6,r7,r8,lr}` |
| 结构基址 | 1 个（描述符 `0x2000138C`） | **4 个**（`0x20003D44`/`0x2000129C`/`0x20003CB0`/`0x20003D20`） |
| 全局门控 / `+0x36` 锁存 | **有** | **无** |
| 一次性重初始化 | **有** | **无** |
| 比例换算 | 无 | **有**：`[r4,#0x2E5] = 0x64 × [r8+8]`、`[r4,#0x2E9] = [r8+0xC]` |
| 16 位计数器 | 无 | **有**：`[r5,#0x20]++` 并分发到全局 `0x200015C5+6/8/a/c` |
| 配置有效性检查 | 无 | **有**：`[r7]≠0 && [r7+2]==2 && [r7+3]==0` ⇒ 才算 `+0x1AF+0x31F−+0x238` |
| **`+0x1AF`/`+0x31F`/`+0x238` 的读取** | **在另一个函数里**（`0x080153xx`） | **就在本函数里**（`0x0801481A..0x08014828`） |

#### ⇒ 结论（限定表述）

**3.1.5.0 把这套逻辑放进了「配置/状态更新」函数**（比例换算 + 计数器 + 有效性门控），
**3.2.D.8 把它拆成了「每周期位置更新」+ 独立的初始/校验函数**。

⇒ **两版不是同一个函数的两份实现，而是职责划分不同** ⇒
**不能用"字段偏移平移"去对齐**（§12.13 已证明字段还跨两个结构）。

⚠️ **这解释了为什么前面所有基于"找对应偏移"的对比都失败**：
对比的前提（同一结构 + 同一职责）在两版之间**不成立**。

### 12.15 ★★★★ 3150 位置链补完：`+0x234` 上多了一个**状态机修正项**（最强差异线索）

上一轮只把 **D8** 的位置链闭到指令级；**3150 那条一直缺一段**。本轮补齐，并发现一处**算法级差异**。

#### 两版 `+0x234`（归一化位置）的构造，逐条对照

**D8**（`0x080155E0..0x08015602`）：

```asm
080155e0  ldr  r0,[sp,#0x18] ; ldr r0,[r0,#0x10]    ; 换算基准
080155e4  ldr.w r1,[r4,#0xB0] ; add r1,r0           ; + 归一化结果
080155ec  str.w r1,[r0,#0x234]                      ; ★ = f(基准) + normalize(...)
080155f6  ldr  r0,=0x20000078 ; ldr r2,[r0,#8] ; blx r2
08015602  str.w r1,[r0,#0x238]                      ; 位置实际值
```

**3150**（`0x08014AF4..0x08014B04`）：

```asm
08014af4  ldr  r0,[sp,#0x14] ; ldr r0,[r0,#0x10]    ; 换算基准
08014af8  ldr.w r1,[r5,#0xA8] ; add r0,r1
08014afe  ldr  r1,=0x20003DB0 ; ldr r1,[r1,#0x18]   ; ★★ 状态机修正项
08014b02  add  r1,r0                                 ; ★★ 相加
08014b04  str.w r1,[sb,#0x234]                      ; ★ = f(基准)+normalize(...)+修正项
08014b5c  ldr  r2,[r0,#8] ; blx r2
08014b62  str.w r0,[sb,#0x238]                      ; 位置实际值
```

⇒ **3150 在归一化位置之上，多加了一个由状态机提供的 `[0x20003DB0 + 0x18]`；D8 在这条语句上没有第三项**
（§13.3 逐条读码实证：D8 `0x080255E0..0x080255EC` 只有 `ldr r0` / `ldr r0` / `ldr.w r1` / `add r1,r0` / `str.w r1`，
没有任何 `ldr r1,[r1,#0x18]` 形态的第三加数）。
⚠️ **但原文引用的"§23 已证：该结构在 D8 里 0 个字面量引用"这个论据是错的** ——
那是在拿 `0x20003DB0` 与 D8 的**另一个**全局比。见 §13.3：D8 的 `0x20003EF8` 是**逐轴系数数组**（步长 0x34），
与 `0x20003DB0` 只是**地址相邻**，不是对应物。**结论靠的是逐条读码，不是计数。**

#### `+0x18` 是什么（读到指令级）

**写入方**（3150 状态机，`0x08015BF0..0x08015DEC`，共 8 处，全在 `0x080157xx..0x08015Dxx`）：

```asm
08015ce4  ldr.w r3,[r3,#0x170]        ; 某个锁存值（逐轴对象）
08015cea  ldr   r5,[r5,#8]            ; 0x20003DB0+8
08015cec  subs  r3,r3,r5              ; ★ 差值
08015cf0  str   r3,[r5,#0x18]         ; ★★ 写进修正项
```

**清零方**（位置链内，`0x08014AF2`）：

```asm
08014ae6  ldr  r0,=0x20000020 ; ldrh r0,[r0] ; cmp r0,#1 ; bne skip
08014af2  str  r0,[r1,#0x18]          ; ★ 当 [0x20000020]==1 时把修正项清零（写的是 r0=0）
```

⇒ **`+0x18` = 「逐轴对象里某个锁存值（`+0x170`）」−「`0x20003DB0+8`」**，
即一个**差值修正项**，由状态机维护，被位置链作为**加数**并入 `+0x234`。

#### ⇒ 这一环为什么重要（**假说，未证**）

**这是整条链上唯一一个"两版一个有、一个没有"的算术项。**

⚠️ 一个**数值上衔接得住**的读法（**仅为假说**）：
若"锁存值"是**零点基准**、"`+8`"是当前值，则
**基准正确 ⇒ 差值为 0 ⇒ 位置正确**；
**基准没跟上 ⇒ 差值非零 ⇒ 位置被偏移恰好这个差值**。

这与实机现象**在量级上吻合**：3.1.5.0 上使能瞬间 J6 跳 **2.91°**，
而 `homeEncoder.json` 记录的 `innerEncoder` 量级（±2500 counts ≈ **0.45°**）正是"基准"类量的量级。

⛔ **但这仍是假说**：`+0x170` 与 `0x20003DB0+8` 的**物理含义未定名**，
无法从静态判断该加项是"零点修正"还是别的（例如多圈补偿、齿轮间隙补偿）。
**要定论必须有运行期数据**（看该值在标定前后是否变化）。

### 12.17 ★★★★ 补丁方案：三项验证全部通过，补丁已生成（**未刷写**）

针对 §12.15 那个多出来的修正项，产出了一份**字节级补丁**。**默认 dry-run，不写文件。**

#### 补丁点（字节级，3150）

```
08014AF4  05 98        ldr   r0,[sp,#0x14]
08014AF6  00 69        ldr   r0,[r0,#0x10]        ; r0 = 换算基准
08014AF8  d5 f8 a8 10  ldr.w r1,[r5,#0xa8]        ; r1 = 归一化结果
08014AFC  08 44        add   r0,r1                ; r0 = 基准 + 归一化
08014AFE  2c 49        ldr   r1,[pc,#0xb0]        ┐
08014B00  89 69        ldr   r1,[r1,#0x18]        │ ★ 修正项
08014B02  01 44        add   r1,r0                ┘
08014B04  c9 f8 34 12  str.w r1,[sb,#0x234]
```

**改法**（6 字节 → 6 字节）：

```
08014AFE  01 46        mov   r1,r0        ; r1 = r0 = 基准+归一化   ★★ 方向
08014B00  00 bf        nop
08014B02  00 bf        nop
```

> ⛔⛔ **本节原写的是 `08 46`（`mov r0,r1`），那是错的，已于 §13.2 更正为 `01 46`。**
> `08 46` 会把 **r0 覆盖成修正项**、而存储用的是 r1，结果 `+0x234` 变成**只剩修正项**——
> 一个"字节确实变了、但语义完全错"的坏补丁。**下面 ① 的原文同样要按此读。**

#### ① 寄存器语义验证 ✅

`r0` 在 `0x08014AFC` 后 = **基准 + 归一化**；`r1` 在 `0x08014AFC` 后**已死**（被补丁窗口覆盖）。
⇒ 换成 `mov r1,r0` **精确复现** D8 存入 `+0x234` 的值。
⚠️ 方向必须是 **`mov r1, r0`**（把 r0 搬进 r1），因为 `0x08014B04` 的 `str.w` **存的是 r1**。

#### ② 分支目标验证 ✅

全镜像 **5480 个**分支目标中，落在补丁窗口内的是 **0 个**。
（顺带：D8 镜像在 `0x08014B00` 有 1 个目标，但那是**不同包里的地址**，与 3150 无关。）

#### ③ 副作用验证 ✅（读取点数已按 §13.4 更正）

`[0x20003DB0 + 0x18]` 全镜像共有 **9 个读取点 + 7 个写入点**（原写"只有 2 个读取点"，是【计数】级误差）：

| 读取点 | 归属 | 补丁影响 |
|---|---|---|
| `0x08024B00` | **位置结果**（我们要绕过的） | **被 NOP 掉 —— 正是目的** |
| `0x08025CFE`、`0x08025D16`、`0x08025D2E`、`0x08025D4A`、`0x08025D9E`、`0x08025DB6`、`0x08025DCE`、`0x08025DE6`（8 处） | **状态机自身反馈** | **不受影响** |

**唯一一个落在状态机之外的写入点**是 `0x08024AF2`（位置链内的条件清零，位于补丁窗口**之前**）⇒ **生产者完全不动**。

⇒ **补丁只切断「位置结果」这一个消费者，状态机的 `+0x18` 逻辑保持完整。**

#### 补丁后反汇编（实测，非推断）

```

08014AF6  ldr    r0,[r0,#0x10]
08014AF8  ldr.w  r1,[r5,#0xa8]
08014AFC  add    r0,r1
```

#### ⛔ 过程中被我自己的正例自检抓出的错误（必须留档）

**第一版补丁我把 NOP 写成 `bf 00`，那是错的** —— Thumb 16 位 NOP 的半字是 `0xBF00`，
**小端字节序下是 `00 BF`，不是 `BF 00`**。写 `bf00` 会被解成 **`lsls r7,r7,#2`**（真实指令，破坏 r7）。
另一个诱人的写法 `46 C0`（`mov r8,r8`）在这个位置被解成 **`stm r0!,{r1,r2,r6}`**（破坏内存）。

**⇒ 新红线：任何字节级补丁必须反汇编验证解码结果，不能凭"我记得编码是这样"就下手。**

#### ⛔ 本条作废（原文：manifest 的 `0x08010000` 是错的）

原文说"自制 3.1.5.0 的 manifest 写 `start_address=0x08010000` 是错的 —— payload 首字 SP+次字 Reset
证明它从 `0x08000000` 加载"。**这个判断本身就是错的，已于 §13.1 用三重实证推翻：**

**两个 payload 都加载到 `0x08010000`。manifest 是对的。**

错了的原因值得留档：**拿"payload 前两个字像 SP 和 Reset"去反推加载地址，是假设而不是测量** ——
向量表在**任何**基址上都会长得一样。用**与 1 MiB 全片 hex 的逐字节重合率**一测就清楚了
（`0x08010000` 处 **100.0000%**、`0x08000000` 处 3.97%）。

⚠️ 后果：本文所有 `0801xxxx` 形式的**反汇编地址标签实际都要 `+0x10000`**（§13.1）。
**补丁的 payload 偏移 `0x14AFE` 不受影响**（它是按字节模式定位的），只是它的 flash 地址应写作 `0x08024AFE`。

### 13.1 ★★★ 加载地址 = `0x08010000`（三重实证；原文档写反）

| 测量 | 方法 | 结论 |
|---|---|---|
| **M1 全片重合率** | 两 payload 分别叠加到 **1 MiB 全片 hex**（`3.1.5.hex`）与 **D8 应用区 hex** 的同名地址 | 3150 在 `0x08010000` = **328,860/328,860 = 100.0000%**；在 `0x08000000` = 3.97%。D8 在 `0x08010000` = **338,072/338,072 = 100.0000%** |
| **M2 区域规则** | FoE 只写应用区 | 载荷长 0x52898 / 0x5049C；若基址 `0x08000000` 会**覆盖 bootloader**（`0x08000000..0x08002897`）⇒ 不可能 |
| **M3 Reset 向量解码** | 向量表就在 payload 偏移 0，其 Reset 目标必须在**恰好一个**基址上解成真代码 | `0x08010000` → 偏移 `0x19C`，`ldr r0,[pc,#0x18] / blx r0 / ldr r0,[pc,#0x18] / bx r0`（干净，0 条不可解码）；`0x08000000` → D8 起点是 `ble`、3150 起点直接 `.byte 0xfc,0xf8` |

工具 `tools/pkg_load_verdict.py`，输出留档 `data/servo_fw_samples/LOAD_ADDR_VERDICT.txt`。

⇒ **manifest 的 `start_address=0x08010000` 是对的**；§12.17 末尾那句"manifest 是错的"**作废**。
⇒ **本文所有 `0801xxxx` / `0800xxxx` 反汇编地址标签都要 `+0x10000`**（旧工具统一用 `FLASH_BASE=0x08000000`
做合成基址，内部自洽但标签偏低 `0x10000`）。
⇒ 补丁点的**载荷偏移 `0x14AFE` 不变**（按字节模式定位），flash 地址 = `0x08010000 + 0x14AFE` = **`0x08024AFE`**。

⚠️ **方法教训**：**"payload 前两个字像 SP 和 Reset"不能用来反推加载地址** ——
向量表在**任何**基址上都长那样。**地址类结论必须用"与已知镜像的重合率"这类可证伪的测量**，
不能用"结构看起来像"。

### 13.2 ⛔⛔ 抓出的坏补丁：`08 46` 是 `mov r0,r1`，方向反了

补丁要对齐的目标是：让 `+0x234` 等于 **r0**（= 基准 + 归一化）。而 `0x08024B04` 的
`str.w r1,[sb,#0x234]` **存的是 r1**。所以补丁必须是 **`mov r1, r0`**。

| 字节 | 半字 | 解码 | 结果 |
|---|---|---|---|
| `01 46` | 0x4601 | `mov r1, r0` | r1 = r0 ✅ **正确** |
| `08 46` | 0x4608 | `mov r0, r1` | r0 = r1 = **修正项**；r1 仍是修正项 ⇒ `+0x234` **只剩修正项** ❌ |

**§12.17 原文写的是 `08 46`（`mov r0,r1`），是错的。** 它不是一个"刷不进去"的补丁 ——
它是一个**字节确实变了、MD5 也自洽、却把位置值换成修正项**的补丁，属于最危险的一类错误。

**为什么上一轮的"三项验证"没抓住它**：三项验证全部在检查**补丁点周围**（寄存器活跃性、分支目标、副作用），
**没有一条在检查"补丁后 r1 到底等于什么"**。⇒ **新红线：字节级补丁的验收断言必须包含
「补丁后目标寄存器的值 = 期望表达式」，而不只是"原指令被清掉了"。**

`tools/servo_patch_review.py`（第 3 节把三个候选一起解码对照）与
`tools/servo_patch_verify3.py`（V1 从代码重新推导方向，不信任任何常量）已把这条固化。

#### 为什么"把该项置零"不是 hack，而是厂商自己写下的一个模式

紧接补丁点**之前**（`0x08024AE0..0x08024AF2`）固件自己就有一条把修正项清零的路径：

```asm
08024AE6  ldr   r0,[pc,#0xc4]     ; = 0x20000020
08024AE8  ldrh  r0,[r0]
08024AEA  cmp   r0,#1
08024AEC  bne   0x08024af4
08024AEE  movs  r0,#0
08024AF0  ldr   r1,[pc,#0xbc]     ; = 0x20003db0
08024AF2  str   r0,[r1,#0x18]     ; ★ 修正项 := 0
```

⇒ **"修正项 = 0"是厂商自己实现的一个运行模式。**
补丁做的事情，就是让位置链**永久停留在该模式**，而**不去动产生该项的状态机**。
这比"凭空删掉一段代码"在工程上更容易辩护。

#### ⚠️ 附带发现（**未验证的根因候选，值得现场顺手一测**）：门控标志的可能性错位

两版这条门控判据**读的字节宽度不同、写的位置也不同**：

| | 读 | 写 |
|---|---|---|
| **3.2.D.8**（`0x080253E8..0x080253FA`） | `ldrb` **`0x20000020`**，`cmp #0` | `strb 1 →` **`0x20000020`** |
| **3.1.5.0**（`0x08024AE6`、`0x08024AE2`） | `ldrh` **`0x20000020`**（字节 0x20–0x21） | `strb 1 →` **`0x20000022`** |

⇒ 3150 的门控要求 `*(u16*)0x20000020 == 1`，**但它自己把 `1` 写到了 `0x20000022`**（另一个 u16 的低字节）。
**如果没有任何模块给 `0x20000020` 那个 u16 写 1，则 3150 上"修正项清零"这条路径永远不会被走到**，
修正项就一直生效 ⇒ **这正是"3.1.5.0 零点不保持、D8 保持"的一个自然解释。**

⛔ **这仍是假说，本轮没有验证**：需要确认 ① `0x20000020` 那个 u16 的写入者是谁（全镜像 5 个站点，
本轮未逐个读）② 该值在标定前后是否变化。
**验证方法（零风险、只读）**：控制箱在线时用 `amrd` 转储 `0x20000000..0x20000040`，
在**标定前 / 标定后 / 重新上使能后**各读一次，看 `+0x20` 处的半字是否曾变成 1。
**若该值恒不为 1，则"改门控"是一个比改位置链更贴根的修法**（而且只需改 1 个半字）。

## 14. 第 34 轮：从 USART3 入手查外设层——三个阴性结果，一个新线索

本轮**未动机器人、未碰总线**，全部离线反汇编。起点：既然位置链里没有零点变量、
且那个修正项已被实验排除，那么差异必在**原始计数被产生的那一层**——于是从外设层入手。

### 14.1 外设清点（先修了自己的一个坑：浮点污染）

第一版把 `0x40000000..0x50000000` 当作"外设地址段"扫，得到一堆 `0x41000000`/`0x42000000`——
**那是单精度浮点常量**（`0x41A00000`=20.0f、`0x42000000`=32.0f）。收窄到真正的 STM32F4 基址段后：

| | D8 | 3150 |
|---|---|---|
| 外设段字面量总数 | 372 | 362 |
| 逐块计数 | **几乎完全一致** | 同 |

存在的块：`TIM2-8 / TIM10 / TIM11`、**`USART1`、`USART3`**、`ADC`、`GPIOA-G`、`EXTI`、`DMA1`、`FLASH-IF`、`RCC`、`PWR`、`SYSCFG`。

⏔⏔ **本块固件根本没用 SPI** —— `0x40013000`(SPI1) / `0x40003800`(SPI2) / `0x40003C00`(SPI3) **一处都没有**。
⇒ **编码器不是 SPI/SSI/BiSS 接口**。而序列绝对编码器（Tamagawa/Nikon 那类半双工 RS-485）**走 USART**。
⏔ **整块固件真正在用的串口只有 USART3**：`0x40004800` 有 6 处引用，
而 `0x40011000`(USART1) 那**唯一一处**实际上就在**通用 init 里**（用来选 APB 时钟常数）⇒ **USART1 没有任何人驱动**。

### 14.2 ⏔ \u7ed3论：USART3 的使用方式两版**逐条相同**，这条线不含版本差异

* 两版各 6 处 USART3 引用，**全在同一个函数里**（D8 `0x0802CF50` / 3150 `0x0802BA7C`），
  且**函数内相对偏移完全相同**：`+0x196 / +0x1C6 / +0x1EA / +0x220 / +0x256 / +0x25E`。
* 那个函数两版**都是 351 条指令 / 940 字节**，规范化 diff **96.0% 相同**。
* 11 处差异全是：**逐轴数组元素步长 `0x170`(D8) → `0xB0`(3150)**，以及**结构内偏移整体 −0x10**
  （`[r5,#0x20]→#0x10`、`#0xa0→#0x90`、`#0x110→#0x100`）—— **就是已知的 RAM 布局重排**。
* **没有任何一处差异落在 USART3 引用点上。**

⏔ **顺手把 USART 驱动层读出来了**（都是通用函数，base 通过 `r0` 传入，所以除了那个 init 之外**全库找不到 USART3 字面量**）：

| 地址(D8) | 语义 |
|---|---|
| `0x0801B778` | `usart_init(base, cfg)`：从 cfg 写 CR2/CR1/CR3，并处理 USART1/USART6 的 APB 时钟常数 |
| `0x0801B74C` | 使能/禁能（CR1 的 `0x2000` = UE） |
| `0x0801B764` | CR3 位集/位清 |
| `0x0801B73A` | 清 SR 标志 |

### 14.3 ★ 本轮**唯一的“一版有、另一版没有”信号**（值得下一步追）

| 寄存器 | D8 | 3150 |
|---|---|---|
| `0x40014424` = **TIM10_CNT** | **5 处** | **0 处** |
| `0x40014824` = TIM11_CNT | 5 | 3 |
| `0x50000000` = USB-OTG-FS | 3 | 0 |

整个外设层里只有这几处是“有/无”差异，其余全是计数相同。
⏔ 尚未用严格方法（字面量加载）复核 TIM10/TIM11 这两行——它们来自第一版的对齐 dword 统计，**应当先复核再当结论**。

### 14.4 ⏔ CSV 锚点：一个很好的想法，**实测失败**（三次尝试三种陷阱，全部留档在工具里）

想法：那个函数按逐轴数组索引（`r4 = base + 轴号×0x28`）——为什么一个驱动器固件里有逐轴数组？
因为官方 `servoCSV/CR/CR5/J1~J6.csv` 就是**每关节参数表**。如果它们被编进固件，就能用手上的 CSV 值**定位数据区**，而且带来一个**有名字的锚点**。

| 尝试 | 方法 | 命中 | 陷阱 |
|---|---|---|---|
| v1 | 单个参数值 | 7,418 | 小整数到处都是，零信息量 |
| v2 | 连续 3 个值 | 790,841 | **`f32(0.0)` = 全零字节**，匹配任何零区（所以在 0x1c/0x1d/0x1e 连续命中） |
| **v3** | 过滤掉退化值后的值对 | **0 / 84 个模式** | — |

⏔ **负例对照**（同量随机非整数浮点对）也是 **0 命中** ⇒ **v3 的检出力是真的**，
不是“工具坏了”。⇒ **V3 固件里没有编入这套参数表**。
与之一致：`readme重要.txt` 说该表适用 **CR 伺服 V4.1.3.3**，而 `H0.00 MCU软件版本号 = 16691 = 0x4133` 正是“4.1.3.3”。
⇒ **这条路关闭**。（工具：`tools/csv_anchor.py`、`csv_anchor_strict.py`、`csv_anchor_strict2.py`）

### 14.5 ⏔ 顺手作废上一轮的一个建议：“写厂商参数（SDO）”

那 97 个可达的 OD 对象**全是标准 CiA402/ETG**（`std_index` = 0x6040 / 0x6060 / 0x6064 / 0x607A / 0x607C / 0x6098 …），
**没有任何 0x2xxx 厂商对象**。而 `H01.17 / H0C.02 / H01.18` 按 `hparam_map.json` 落在 `0x2000+组:子+1` 空间
⇒ **不在 EtherCAT OD 里**，**标准 SDO 写不到它们**，厂商参数只能走厂商自己的工具/另一个通道。
（反过来，标准零点对象**是**可达的：`0x607C` / `0x6098` / `Position Offset`(i32,rw) 都在表里，
但 §12/§30 已证明它们**只有分派器在算地址、核心从不读**，写它们无效。）

### 14.6 本轮后的候选空间（已被收窄到哪里）

已排除：位置链（无零点变量 + 那个修正项实验排除）、OD 访问层（97 对象逐项相同）、
**外设层（本轮：逐块计数几乎相同，USART3 逐条相同）**、厂商参数 SDO 通道、CSV 锚点。

剩下的可疑点（按我的排序）：

1. **★ `TIM10_CNT` / `TIM11_CNT` 的“有/无”差异**（§14.3）——**先用严格方法复核**，属于“一版有、另一版没有”这类最强信号。
2. **持久化子系统“存什么”而不是“怎么存”**：§12 已证存储例程两版逐条同构（126 vs 126），
   但 **它被要求存的变量清单/参数块可能不同**（API `0x080045A8` → 持久化 `0x08001708`，magic `0xA1B2C3D4`）。
   而“定基非易失”强烈暗示**差异就在“哪些量被标为需保存”上**。
3. `0x170` vs `0xB0` 那个逐轴数组的布局差异（本轮顺手量到，未追）。

### 14.7 第 34 轮后半：三条结构方法全部走到尽头，结论是一个**重大的认知转折**

本轮把“不靠指令级 diff、改靠结构定位”这个方向**走到尽头**。三条方法全部失败，而失败本身给出了一个结论。

#### ① 功能级 diff（字符串集 + 中断向量表）—— 阴性

先修了两次自己的过滤器（都是“代码字节冒充字符串”：第一版 948 条假“D8 独有”），
最终过滤器 = **字符集限定 `[A-Za-z0-9 ._/-]` + 长度≥8 + 字母中小写占比≥50%**，正例对照 `TxPDO assign` / `Position Actual Value` 全部 PASS。

| 测量 | D8 | 3150 |
|---|---|---|
| 真实短语串总数 | 208 | 210 |
| **只在 D8 出现的短语串** | **0** | — |
| 只在 3150 出现 | — | 2（残余噪声） |
| 中断向量表“一版有、另一版无”的项 | **0** | **0** |

实际用到的 IRQ 只有 **6/7/9（EXTI0/1/3）、23（EXTI9_5）、30（TIM4）**；
**没有 USART IRQ**（说明 USART3 是**轮询**的，与 §14.2 一致）、没有 DMA IRQ、没有 TIM1/2/3/5 IRQ。

⇒ **D8 没有新增任何模块 / 错误信息 / 中断处理器。** 这个修复**不是“加了一个功能”**。

#### ② 代码窗口剖面（哪里是 D8 多出来的 9 KB？）—— 阴性

D8 payload 比 3150 大 **9,212 字节**，那就把它找出来：

| | D8 | 3150 |
|---|---|---|
| payload | 338,072 B | 328,860 B |
| 指令总数 | 149,896 | 147,119（**差 +2,777**） |
| 函数总数（`bl` 目标） | 1,312 | 1,321 |

逐 0x1000 窗口计数无**任何“一整块 D8 独有代码”**（每窗口 Δ 都只有几十条指令）。
⇒ **D8 不是“加了模块”，而是既有函数内部被改**（函数数几乎一样，指令更多）。

#### ③ 变更区按大小排序—— 得出了本轮最重要的结论

用“16 字节块索引 + 最大精确匹配”重做了 §25 的块差分析（正例对照：版本串必须落在变更区内，PASS）：

```
738 个相等跑 / 126,744 B 相等  =  37.5%
739 个变更区      / 211,328 B
```

前 25 大变更区里，**最大的四块（28,710 / 27,686 / 18,723 / 17,562 B）全是数据段**
（反汇编出来是 `.byte` 与乱码），地址均在 **0x0803xxxx–0x0806xxxx 上半区**；
而**代码区的变更全部只有 600–1,100 B 量级、且有几百处**（§27 曾细看的位置链那一块 799 B 只排第 20）。

⇒ **没有任何一处能被单独定位为“修复点”。**

#### ★★ 结论（改变判断）：**3.2.D.8 不是“3.1.5.0 + 一个修复”，而是一条不同的开发分支**

把三条方法的数字放在一起，图像很清楚：

| 指标 | 值 | 读法 |
|---|---|---|
| 逐字节相等率 | **37.5%** | 若是同一代码基 + 小修复，应 ≥95% |
| 变更区数 | **739** | 普遍变化，不是局部修复 |
| 函数总数 | 1,312 vs 1,321 | **没有增删模块** |
| 新增字符串 / ISR / 外设块 | 几乎全 0 | 也**没有增功能** |

（唯一的功能级差异：**USB-OTG-FS 外设在 D8 有 3 处引用、3150 完全没有**；以及 **TIM10_CNT 读取 D8 5 处 vs 3150 1 处**。
两者都已用严格方法核实，但**都不能解释零点为什么能持久**。）

⇒ 两版是**同一个程序的不同开发线产物**：结构一样、内容普遍不同。
**⇒ “找出那一个差异”在离线条件下不成立** —— 不是因为难找，而是因为**它不存在为一个可定位的差异**。

#### ⇒ 因此：离线路线已到天花板

回顾已经被排除的：
位置链（无零点变量 + **实验排除**）、OD 访问层（97 对象逐项相同）、
**外设层**（逐块计数几乎相同，USART3 逐条相同）、**功能层**（无新模块/字符串/ISR）、
厂商参数 SDO 通道、CSV 锚点。

而剩下的两条“可疑”（USB-OTG、TIM10_CNT 读数）**不具备因果可能性**：它们和“零点持久化”之间没有任何可说通的路径。

⇒ **纯静态反汇编到此到了天苑板。** 再往下只有两条路：

1. **换目标**：不再追“为什么 D8 能持久”，改做**主控侧补偿**（不需要知道徽机制）。
   主控是 Linux、有 shell、有备份、有官方升级包 ⇒ 风险与可达性都优于改伺服固件。
   （但需先确认主控侧那个计算点是否可改、以及改完不影响其他五轴。）
2. **停止静态，取运行期数据**（需硬件通道：驱动器侧 SWD 已知不可用）。
