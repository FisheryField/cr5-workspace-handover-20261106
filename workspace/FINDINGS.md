## 一、原始问题

CR5 在使能状态下执行"零点标定"（`POST /calibrate/home`）后关节值确实变成 0，
但**重新上使能后关节值又变成非 0**。

**用户实机对照（最直接的判据）**：

| 步骤 | 伺服 `3.1.5.0` | 伺服 `3.2.D.8` |
|---|---|---|
| 零点标定 | 关节值归零 | 关节值归零 |
| 下使能 | — | **保持 0** |
| **重新上使能** | **> 1°，甚至几十度** | 约 **0.4°**（上使能时机械臂晃动的读数误差，不是零点丢失） |

## 二、根因（最终版，已由 EtherCAT 总线抓包证实）

### 2.1 换算公式

```
关节角 = 驱动器 0x6064 位置实际值 × 360/(20000×101)        ↑ = 1.782178e-4 °/count
```

**零点完全由驱动器自己维持**：`cali home` 让驱动器把 `0x6064` 重新定基到 0，关节随之读 0。

> ⚠️ **2026-09-23 晚修正**：早先写的"关节角 = (0x6064 − innerEncoder) × scale"**是错的**。
> 反证来自在线设备：最新一条 `innerEncoder = [-2506, 8, -2522, 2536, 2508, 2507]`（≈±0.45°），
> 而**标定刚做完时关节读数是 0** —— 若做减法就该读出 −0.45°。
> ⇒ **`innerEncoder` 只是标定时刻 0x6064 的一份记录，不作为偏置参与运算**（用途待查，可能是诊断或失位修复）。

### 2.2 两版固件的差别，就一个数

| | 伺服 `3.2.D.8` | 伺服 `3.1.5.0` |
|---|---|---|
| 标定后驱动器 `0x6064` | **被定基到 0**，且**非易失** | **不做定基**（总线实测：主站把 `0x607A` 置 0 后 7 ms 内 3.2.D.8 跟到 0，3.1.5.0 纹丝不动） |
| 重新使能后的关节角 | ≈ 0 | **= 编码器原始绝对计数 × scale**（几十度） |
| `homeEncoder.json` 的 `innerEncoder` | 记录标定时刻读数 | **全 0**（成因仍未解，见 §七） |

### 2.3 数值实证（决定性）

用 3.1.5.0 的总线抓包 PDO 值与同一时刻实测关节值对账：

| 轴 | PDO 计数 | × scale | 实测关节值 | Δ(°) |
|---|---|---|---|---|
| J1 | 45877 | -8.176099 | -8.176508 | 0.000409 |
| J2 | -57977 | 10.332535 | 10.333052 | 0.000517 |
| J3 | 19080 | 3.400396 | 3.400566 | 0.000170 |
| J4 | -12807 | 2.282436 | 2.282550 | 0.000114 |
| J5 | -42461 | 7.567307 | 7.567685 | 0.000378 |
| J6 | -18502 | 3.297386 | 3.297551 | 0.000165 |

**六轴全部吻合到 0.0005° 以内**（≈0.00015 圈电机），符号也与已知方向约定一致（只有 J3 是 `inverted:false`）。
⇒ **3.1.5.0 上控制器确实是按"零偏置 = 0"在算的。**

### 2.4 "零点不保持"的准确说法

- 零点**不存在控制器里**，也不存在 `homeEncoder.json` 里 —— 它由**驱动器自己**维持。
- `cali home` = 控制器把目标位置清零，**驱动器把 `0x6064` 重新定基到 0**。
- **3.1.5.0 的驱动器不接受/不保持这个定基** ⇒ 关节值 = 编码器原始绝对计数 × scale。
- **3.2.D.8 的驱动器接受且非易失** ⇒ 关节值 ≈ 0。

⇒ ~~修法：六轴全刷 `3.2.D.8`~~ ⛔ **已作废**：3.2.D.8 **不能用于运动**（用户实测）。
⇒ 正确的问题表述：**3.1.5.0 的驱动器无法被 calihome 改写零点，且每次上使能都恢复旧零点；而 3.2.D.8 虽能改写，却动不了。** 见 §十。

### 2.5 一行命令就能现场判定

```bash
ssh root@192.168.5.1 "cat /dobot/userdata/project/settings/function/homeEncoder.json"
```

使能状态下点完"零点标定"再看：

| 现象 | 判定 |
|---|---|
| `innerEncoder` 非全 0 | ✅ 正常，偏置记对了 |
| `innerEncoder` **全 0** | ❌ 就是这个故障，偏置没记上 |

**这是整个调查里最好用的一条现场判据**，不需要抓包、不需要停栈、不需要抢总线。

## 三、关键新证据：EtherCAT 总线抓包

（由 codex 于 2026-09-22 采集，本会话用其原始 pcap 复核。归集见 `data/codex_b/`）

### 3.1 抓包确为 EtherCAT

```
linktype = 1 (Ethernet)    ethertype = 0x88a4 (EtherCAT)
zero32_calibration.pcap        : 73042 帧，1111 字节周期帧 72994 个
capture315_ethercat.pcap0/1    : 85686 帧，同样以 1111 字节帧为主
```

**这填掉了此前最大的空白：L2 的"标零下发从来没有被观测过"。**

### 3.2 `innerEncoder` 是 PDO 里持续流动的字段，标定只是"快照"

在 1111 字节帧的固定偏移 `603/660/717/810/879/950` 读 int32：

- `zero32_calibration.pcap`（3.2.D.8）：元组 `[598234, -192592, -580282, 389348, -718959, 576819]` 出现 **1690 次**，**与 JSON 记录逐位相同**。
- 时间切分：该元组在标定请求（`15:45:15.448`）**之前**已出现 **1636 次**（最早 `15:45:12.177`），之后仅 **56 次**。

⇒ **不是"回零后读回一个结果"，而是"把一个一直在流的实时字段抄了下来"。**

### 3.3 标定**没有**改变伺服上报的位置

按时间切分 3.1.5.0 的抓包：

| 窗口 | PDO 元组 |
|---|---|
| 上使能前（1112 帧） | `[-603293, 202704, 585171, -394376, 709124, -566921]`（陈旧，不刷新） |
| 上使能后、标定前（4044 帧） | `[45882, -59041, 19067, -12875, -42448, -18473]`（实时） |
| 标定后（23718 帧） | `[45877, -57977, 19080, -12807, -42461, -18502]`（几乎没变） |

⇒ **归零完全发生在控制器侧**（记下当前计数当偏置，之后做减法），伺服侧没有"把当前位置变成 0"这个动作。

### 3.4 `homeEncoder.json` 的历史快照（codex 采集）

|---|---|---|
| 2026-09-18 19:27:04 | **全 0** | 六轴均 3.1.5.0 |
| 2026-09-22 12:01:40 | 非 0 `[588340, -180525, -580249, 389412, -729378, 586714]` | |

## 五、控制器侧证据链（仍然成立的部分）

### A. 标定链路（日志 + 反汇编）

```
POST /calibrate/home
  → DataSubProcess::caliHome @0xf0428
       · 把 6+6 个 double 从 *(this+0xE20)+0x3110 / +0x3278
         拷进 this+0x20C0(innerEncoder) / this+0x20F0(outEncoder)
       · 调用下层执行回零；置 isRequestCalihome = 1
  → robot_control::updateEncoderData @0x1d9e90
       · 按 0x4D8 步长读 *(this+0xE20)+0xF4 的每轴"calihome 完成"标志
       · 统计 → HomeNumdone : 0→2→4→6
  → 日志 "servo calihome done"
  → DataSubProcess::updateEncoderData @0xf9520
       · 写 settings/function/homeEncoder.json
```

全程 < 1 秒。**`caliHome` 里没有文件写入、没有 SDO 写入**（数值来自运行时结果缓存
`runtime+0x3100/+0x3240`，由回零回调填充）。

### B. 标定时刻只写了 2 个文件

| 文件 | 性质 |
|---|---|
| `settings/function/homeEncoder.json` | **零点偏置记录（= §2 的关键）** |
| `settings/function/loadParams.json` | 负载参数，与零点无关 |

### C. 开机 SDO 写入只有 PDO 配置

`0x1600 / 0x1A00 / 0x1C12 / 0x1C13`，**没有对 `0x607C` 的写入**。
（`data/codex_b/analyses/sdo_structured_audit.json` 里那批 `0x607C` 写是 **codex 自己的工具发的**，勿误读。）

### D. 驱动器对象字典

138 条目 / 121 索引；无 `0x1010`；`0x607C` 可写但不改变 `0x6064`；`0x6063 == 0x6064`；
`0x5001~0x5007` 全 0；`0x6098 Homing method = 35`。
六轴升到 `3.2.d.8` 后重测，`0x2000–0x200F` 与 `0x1010` **仍全部 FAIL**。

### E. 控制器读数 = 编码器计数 × 固定比例

比值 = `1.78227e-4 = 360/(20000×101)`，J3 反向对应它是唯一 `inverted:false` 的轴。
**这一条与 §2.3 完全一致**——当时的"零偏置恒为 0"正是"偏置被记成了 0"。

### F. 内存侧（计划 A 已否决）

覆盖 `codesyscontrol` 的 7 个共享段 / 13.4 MB：静止稳定性测试证明那块 6×40 结构是**实时计算量**，
写回会被立刻覆盖。**控制器里没有一个可抢救的"零点存储单元"——因为根本不需要抢救，`homeEncoder.json` 就是。**

## 五点五、★ 单轴 A/B 实验：因果已锁定（2026-09-23 15:55）

> 详版见 `data/ab_test/AB_RESULT.md`。**这是整个调查里第一次做到"单变量"对照。**

**条件**：J1–J5 = `3.2.D.8`，**J6 = `3.1.5.0`（唯一变量）**。
**方法**：在主控本地读 `codesyscontrol` 的 `/proc/374/mem` 偏移 `0x75630BB4`（关节值缓冲），9.2 Hz，**不占网络**。

| 事件 | J1–J5（3.2.D.8） | **J6（3.1.5.0）** |
|---|---|---|
| ① 上使能瞬间 | 完全不变 | **89.0045 → 2.9165（Δ −86.09°）** |
| ② 零点标定 | → 0 | → 0 |
| ③ 下使能 | 保持 ≈0 | 保持 ≈0 |
| ④ **重新上使能** | 仅物理摇晃 ±0.447° | **0.0082 → 2.9229（Δ +2.91°）** |
| ④ 稳定 60 s 后 | ±0.447° | **2.9229°（比摇晃大 6.5 倍）** |

**⇒ 只有 J6 出现离散跳变，且两次使能都复现。伺服固件是唯一变量——因果锁定。**
⇒ 3.1.5.0 的驱动器在上使能时会把自己保存的零点重新套上，覆盖掉控制器刚做的标定。
⇒ 同时证实：「上使能时的摇晃」确实存在（J1–J5 的 ±0.447°，等幅交替、渐变），但它和 J6 的跳变是两回事。

## 六、回零通道已解剖（2026-09-23，总线级）

> 详版见 `ZERO_CHANNEL_3.2.D.8.md`。

**回零没有"结果通道"。** 控制器做的就一件事：**把每轴 RxPDO 里的 `0x607A 目标位置` 置 0**，
然后**驱动器自己**把 `0x6064 位置实际值` 重新定基到 0。

```
POST /calibrate/home 到达时刻 t=0
  +0.006 … +0.697 s  逐轴（站 1003→1008，间隔 0.136 s）邮箱 SDO **读取** 0x607C Home offset（两版都返回 0）
  +0.118 … +0.798 s  逐轴把 RxPDO 的 0x607A 目标位置 置 0
  +0.113 … +0.793 s  **3.2.D.8：各轴 0x6064 随之变 0** ✅
  同上                **3.1.5.0：0x6064 不变** ❌
  +0.9 s             写 homeEncoder.json
```

**3.1.5.0 随后还会丢**：POST+4.5~6 s（下使能）时它一度降到 ≈0，
到 **POST+10.85 s（重新上使能）弹回 45877** —— 与控制器日志 `16:31:18.454` / `16:31:24.850` 两次 `/settings/controlMode` 精确对应。

⇒ **3.1.5.0 的定零是易失的；3.2.D.8 的定零是非易失的。** 这就是全部差别。

**附带得到一个可用的探针**：TxPDO 里每站带一个 16 位版本字
—— `0x32D8` = 3.2.D.8，`0x3150` = 3.1.5.0。
**以后有总线抓包就能逐轴确认实际固件版本**，不必依赖控制器那个（来自 EEPROM/ESI、已被证明不可靠的）版本串。

## 七、还没解决的

1. **`innerEncoder` 为何在 3.1.5.0 上是 0？** 两版时序完全相同（都是 POST+0.9 s 写文件），
   而 3.2.D.8 记的是标定前读数、3.1.5.0 记的是 0。
   最可能：`caliHome` 从 `runtime+0x3110` 取的是**回零回调的返回值**而非 PDO 镜像，
   3.1.5.0 的驱动器没正确应答 → 结果缓冲被置 0。**仍是推断，需驱动器侧取证。**
2. **驱动器内部为什么两版行为不同**：对象字典在探测范围内逐项一致（40 索引 0 差异），
   差异在固件内部逻辑。**用 SDO 探测这条路到此为止；要看就得读驱动器 Flash 或反汇编。**
3. 9/22 那 4 条历史记录里中间两条（12:01 / 14:37）当时是哪版固件，未标注。

## 七、干净复验协议（排除上使能摇晃）

```
1) 使能状态下标定 → 下使能 → 上使能
2) 等机械臂完全静止（≥30 秒）
3) 记 6 个关节值  V1
4) 整柜断电，等 30 秒，再上电
5) 上使能后同样等完全静止
6) 记 6 个关节值  V2
7) |V1 - V2| 应 ≲ 0.05°
```

**两次都必须在完全静止后读数**，不要在上电刚使能时读。
若无仪器，退而求其次：每次标定后直接看 `homeEncoder.json` 的 `innerEncoder` 是否非 0（§2.5）。

## 十、★ 位置实际值 `0x6064` 的完整生产链（2026-09-23 第二轮伺服逆向，静态闭环）

> 详见 `SERVO_POSCHAIN_FINDING.md`（40 节）。本节只放结论。

### 10.1 闭环链条（逐条反汇编得出，全部有地址）

```
驱动器 0x6064 位置实际值
        │
        ├─ 逐轴对象 +0xA8  "基准位置"
        │     ← 由 +0xBA 在两个被减数间选择（D8 独有，见 §10.2）
        │     ← 再用 +0x10(上下界) 与 +0x0C(整圈量) 做回绕钳位
        │
        ├─ + sl + 0x20000·fp
        │
        ├─ × sb ÷ 20000          ★ 归一化（常量 20000 = 文档 360/(20000×101) 里的那个）
        │     （两个 0x20000 成对出现、可约去）
        ├─ → 逐轴对象 +0xB0
        │
        ├─ ＋ [sp+0x18]+0x10
        ├─ → 逐轴对象 +0x234
        │
        ├─ 经函数指针 [0x20000078+8] 换算
        └─ → 逐轴对象 +0x238   ★★★ 位置实际值 = 0x6064
```

**相关地址**：逐轴对象基址指针 `0x2000138C`（D8）/ `0x2000129C`（3150），记录步长 **`0x329`**。

### 10.2 两版在该链路上的**三个**差异（全部钉到指令级）

| # | 环节 | 3.2.D.8 | 3.1.5.0 |
|---|---|---|---|
| ① | 位置分解（x → 商/余） | **就地**写在逐轴对象 `+0x10/+0x14/+0x18/+0x1C` | **集中**结构 `0x20003DB0`（商 `+4` / 余 `+0`）+ **一台状态机** |
| ② | 取整 `q = round(x/D)` | **硬件单精度**：`vadd.f32 #0.5` → `vcvt.s32.f32`（2 条指令） | **软件 IEEE 双精度**：f→d 提升 → 软加/减 0.5 → d→int（3 次调用） |
| ③ | `20000` 归一化站点 | 位置链段内 **有**（`movw #0x4E20 @0x080155A6`） | 位置链段内 **无** |


> ⛔ **曾写过的第 ④ 项 `+0xBA`（D8=10 / 3150=0）已作废**：那是"字段整体平移"造成的假象 ——
> 3150 里该字段在 **`+0xA2`**，两段代码**逐条同构**。详见 `SERVO_POSCHAIN_FINDING.md` §40。

### 10.3 状态机（仅 3150 有，D8 连函数体都不存在）

判别式：`movw rX,#0x329` 后 0x50 字节内同时出现 `[rX,#0x24]` 访问 + `cmp …,#7` + `tbb`
→ 3150 命中 1 处（`0x08015786`）、D8 命中 **0 处**。

语义：**逐轴 CiA402 状态变化检测器**（每轴 `0x50` 字节状态块；`+0x20` 当前状态 / `+0x22` 上次 / `+0x24` 已初始化；
**状态没变就直接返回**），状态 `0..6` 经 `tbb` 分派，分支里重做位置商/余分解。

### 10.4 ⚠️ 这些差异**没有**证明是零点修复点

三种情形在纯静态下**无法区分**：
① 3150 本就无"双基准选择"需求（功能整体移除，与零点无关）；
② 3150 用别的字段做了同一件事（与零点无关）；③ 它正是"零点基准是否生效"的开关（相关）。

**⇒ 需要运行期数据做因果对照**（RAM 转储 / 单轴 A-B 差分）。最小采集集合见
`SERVO_POSCHAIN_FINDING.md` §23.4 与 §38.5。

## 十一、★ `mode` 是谁写的 —— 已解（2026-09-23 第二十八轮）

**结论：`mode` 是固件自己写的，不是外部注入。**
（此前 `SERVO_POSCHAIN_FINDING.md` §42 说"源字段在两版镜像里从未被写入 ⇒ 来自外部"——⛔ **该结论已作废**。）

### 11.1 完整链路（两版【逐条读码】一致）

```
[0x20009A70 + 轴×0x64 + 0x34]        ← mode 的源字段（0x64 步长逐轴对象）
   │ D8 0x08019EEC  ldr [r6,#0x34] → 压栈 [sp+0x5c]（第 6 实参）
   ▼
   mode 设置器  D8 0x0801A9E8 / 3150 0x0801956C
   │ movs r0,#0xCC(D8)/#0xB4(3150) ; str r1,[r0,r4]
   ▼
[0x2000C6C8 + 轴×0xE4 + 0xCC(D8)/+0xB4(3150)]   ★ mode 最终落点
   │ D8 0x08016986 / 3150 0x080163DC
   ▼
   上报位置三来源选择器
```

### 11.2 ⚠️ 三个逐轴对象**基址/步长都不同，偏移不可互相搬运**

| 对象 | D8 | 3150 | 步长 |
|---|---|---|---|
| A（mode 源字段） | `0x20009A70` | `0x20009580` | `0x64` |
| B（mode 落点 / 选择器读取处） | `0x2000C6C8` | `0x2000C1D8` | `0xE4` |
| C（另一处 mode 落点） | `0x20008548` | `0x20008060` | `0x164` |

**同一逻辑字段在两版上的位移量并不一致**：B 对象 `−0x18`、A 对象 `−8`、C 对象 `+8`
⇒ **不存在单一全局位移**；按位移换算字段必须逐对象验证。

### 12.1 ⛔ 更正：`0x607C` / `0x6098` 等索引**并非不存在**

本文 §五 D 曾记 ~~"`0x607C` / `0x6098` / `0x6063` 在镜像里完全不存在 ⇒ 零点逻辑不走 CiA402 索引通道"~~。

**该结论被工具缺陷误导，现更正。** 真相：**它们不在 `movw` 直接比较里，但通过 `tbb`/`tbh` 跳表映射到真实处理器。**

* 分派器是「**5 个稀疏二分枢轴**（`0x608E`/`0x6072`/`0x6064`/`0x605C`/`0x6041`）**+ 区间内跳表**」，不是稠密比较链。
* `0x607C` → D8 `0x08002F6A` / 3150 `0x08002E86`；
  `0x6098` → `0x08002A38`（走 `0x608E` 分支的「偏移 10 < 0x36」）。
* **误判原因**：`movw` 立即数扫描器两个 bug —— ① 把 `i` 位当成为 0（Thumb-2 `movw` 里它是 **1**）；
  ② `imm3` 掩码写成 `0x7`，实际在 `w2` 位 **14–12**（`0x7000`）。
  两者叠加使所有 32 位常量解成小值 ⇒ 恒不命中。
  **是正例对照 `movw r1,#0x4e20 @0x080155A6`（已知存在）返回 0 处才暴露的。**

### 12.2 ★★ 每个 handler 就是「暴露逐轴对象的一个字节」

统一形态（整张表都一样）：

```
movw r3,#0x329 ; muls r3,r2,r3   ; r2 = 轴号
ldr  r4,=<描述符数组基址>
add  r3,r4 ; addw r3,r3,#<off>    ; &descriptor[轴].field
str  r3,[r0,#0x18]                ; 把字段地址交给核心
```

⇒ **每个 OD 对象 = 逐轴对象里的一个字段**；分派器提供「索引 → 结构偏移」。
⇒ 每版 **97 个 `(基址, 偏移)` 对**，与 OD 元数据表 **97 条记录一一对应**（OD 表本身不含索引，靠顺序对应）。

### 12.3 ★★★ 两版 OD 访问层**逐项完全相同**（三重实证）

| 项 | 结果 |
|---|---|
| 描述符数组基址 | D8 `0x2000138C` / 3150 `0x2000129C`（**唯一差别**） |
| **97 个描述符偏移** | **逐项相同，0 处差异**（delta 直方图 `{0: 97}`） |
| 分派器结构 | 逐条同构 |
| OD 元数据表 97 条 | 完全相同（早前已实证） |

⇒ 差异**不在 OD 访问层**（由推测升为实证），**进一步逼向运算/状态逻辑本身**。

### 12.4 仍未解
