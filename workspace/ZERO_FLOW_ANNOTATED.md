## 3. 链路里三处空白 / 一处矛盾（⚠️ 已由 §6 的 codex 抓包改写，保留以记教训）

### ❓ 空白 1（最黑的一段）：**L2 的"标零下发"从来没被观测过**

我们知道 L1 里 `isRequestCalihome` 置起来了、`HomeNumdone` 也 0→2→4→6 地涨，
但我们**从没看到过控制器到底往伺服发了什么**。

这正是我 9/23 判断失误的根源：我查到"日志里 `sdo read/write` = 0 次"，
就以为"控制器没跟伺服打交道"。**但如果走的是 PDO，就一条日志都不会有。**

### ❓ 空白 2：**L3 的零点参考存在哪里，完全没观测**

OD 里没有（E10/E13/E15）。那它必然在**驱动器 Flash 的某个非 OD 区域**。
——"OD 里没有" ≠ "驱动器没存"。这是 E15 之后最容易读错的一步。

### ❓ 空白 3：**3.2.D.8 与 3.1.5.0 的差异在 OD 之外**

E15 是**同一根总线上的天然对照组**，40 个索引逐项一致、0 处不同。
⇒ 差异**不在对象字典**，只在别处（Flash 内容 / 内部逻辑 / EEPROM/ESI）。
⇒ 也就说：**用 SDO 探测永远查不出这个修复**，这条路（E13/E15 那套方法）到此为止。

### ⚠️ 矛盾点：E12 的参数地址推导 vs E13 的实测结果

- E12：维护工具日志里有 **259 项参数**，地址串是 `200001 … 200E13`
  ⇒ 推出 `SDO 索引 = 0x2000 + 组号`、`子索引 = 组内序号+1`。
- E13：我们照这个地址去读，**3.1.5.0 上全部 FAIL**；E15 在 3.2.D.8 上**也全部 FAIL**。

两者不可能同时对。可能解释（**未验证**）：

1. **那份维护工具日志不是本机产生的**——是别的设备/别的版本；
2. 维护工具**不走 EtherCAT SDO**，而是走驱动器的串口/调试口；
3. 地址编码不是 `索引:子索引`，而是一个私有寻址方式。

**⇒ 在把这个矛盾解开之前，`H01.17 / H01.18 / H0C.02` 那组"编码器校零参数"的地址不能被当成可靠结论。**

## 4. 一个可证伪的新假设（值得做一次）

**假设**：3.1.5.0 丢的是**多圈计数**，不是单圈角度。

依据：
- `H01.14 编码器单圈分辨率 = 23`（单圈绝对）、**`H01.15 编码器多圈分辨率 = 0`**（无多圈信息）
- 关节转一圈 = 电机转 **101** 圈 ⇒ **电机丢 1 圈 = 关节差 360/101 = 3.5644°**
- 用户实测 3.1.5.0 上使能后偏差是 **" >1°，甚至几十度"**

**可证伪的预言**：
> 3.1.5.0 下，上使能后每个关节的偏差应当**接近 3.5644° 的整数倍**。

**验证方法**（现在的机器上就能做，无需改任何东西）：

1. 记录断电前 6 个关节值 V1（完全静止后读）
2. 整柜断电 → 上电 → 上使能 → 完全静止 → 记 V2
3. 算 `(V2-V1) / 3.5644`，看是不是接近整数

**三种结果的含义**：

| 结果 | 含义 |
|---|---|
| 接近整数 | **多圈计数丢失**被证实 —— 根因清楚，且能解释"为什么 3.2.D.8 修好了"（它把多圈计数持久化了） |
| 明显不是整数 | 假设否证，偏差另有来源 |
| 偏差 ≈ 0（3.2.D.8 下） | 零点保持成立，闭环 |

**附带价值**：这个实验**完全不需要碰固件、不需要停栈、不需要抢总线**，只要读数。
而且它把 L3 那个"完全没观测过"的空白（空白 2）从"不可观测"变成"可间接观测"。

## 5. 一句话总结标记结果

| 链路层 | 观测状况 |
|---|---|
| **L0 操作层** | ✅ 已实测（E6） |
| **L1 控制器 DataSvr** | ✅ 挖得很透（E6/E7/E17–E21 + 反汇编），**结论：无任何持久化路径** |
| **L2 EtherCAT** | ✅ **codex 抓到了（E23–E25）**：已证实 innerEncoder 是 PDO 快照、标定不改伺服位置、3.1.5.0 的零偏置被算成 0 |
| **L3 驱动器内部** | ✅ OD 结构清楚（E10）；❓ **零点参考的实际存放位置完全未知（空白 2）**；❌ SDO 探测对区分两版固件无效（空白 3） |
| **L4 持久化** | ★ **只有 E22（用户实机）直接测到了结果**，而它证明 3.2.D.8 是有效的 |

**最该补的一刀**（原判断，已被 §6 取代）：不是继续挖 L1（已经挖穿了），而是解开 E12/E13 的矛盾。

## 6. codex 的抓包如何改写全图（2026-09-23 汇入）

### 6.2 机制全图（修正版）

```
伺服绝对编码器计数 ──(周期 PDO，两版都正常)──► 控制器实时位置
                                                    │
标定时刻：控制器把"当前计数"记为偏置 ──► homeEncoder.json 的 innerEncoder
                                                    │
重新使能后：关节角 = (当前计数 − 记录偏置) × 360/(20000×101)

3.2.D.8 ：记录偏置 = 真实计数   ⇒ 关节角 ≈ 0          ✅
3.1.5.0 ：记录偏置 = 0          ⇒ 关节角 = 绝对位置    ❌
```

**关键更正**：先前写的"控制器没有零点持久化路径"是**错的**。
`homeEncoder.json` 就是持久化路径，它掉电不丢；错的是 **3.1.5.0 让它记了个 0**。

### 6.3 一处必须澄清的误读风险

codex 的 `sdo_structured_audit.json` 里有对 `0x607C` 的 SDO 写（目标站 1003–1008）。
其时间戳换算约在 **09-22 18:20**，对应 `sdo_trace_now.pcap`（18:29）——
那是 **codex 自己的 `ecat_zero` 工具发的，不是控制器发的**。
⇒ 不能据此推翻「控制器从不写 `0x607C`」（E9 的抓取仍成立）。
