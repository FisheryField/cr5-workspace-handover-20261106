# 标零 SOP —— 伺服固件刷回 3.1.5.0 之后怎么做（CR5）

> 依据：**2026-09-28 / 10-10 / 10-12 三次现场实测**（10-12 是最干净的一次：标零后六轴最大偏差 **0.0116°**）
> 结论先行：**标零必须在【原版主控】下做** ✗ —— 补丁版会死在 `HomeNumdone : 2`

---

## 0. 一句话流程

```
刷完固件 → 整柜断电重启 → 回退原版主控 → 重启 → 机械对齐 → 上使能 → 标零
        → 确认走完 0→2→4→6 → 装回六轴补丁 → 重启 → 验收（六轴 ≈0）
```

**共两次重启**（① 固件生效 ② 原版生效）+（③ 补丁生效）= 三次整柜/控制器重启

## 1. 前置检查（不满足就先解决，否则必然失败）

| # | 检查 | 命令/位置 | 要求 |
|---|---|---|---|
| 1 | **伺服固件** | `grep -a settVersion .../logs/all/log \| tail -14` | `servo1..6 : 3.1.5.0` ✓ |
| 2 | **已整柜断电重启** | — | FoE 只写应用区，**不重启不生效** ✗ |
| 3 | **主控是原版** | `md5sum .../codesys/allST/Application.app` | **`8416cf0eee070a640702c077eb904b4e`** ✓ ← ★ 最关键 |
| 4 | **驱动器无故障** | `grep -a logServoError .../logs/all/log \| tail` | 各轴 `error ID` 均为 **0** ✓ |
| 5 | **机械对齐** | 目视/示教器 | 六轴在**机械零点**（未使能时可手动拖动）✓ |
| 6 | **手臂不在异常姿态** | `PoseTrace` | 不要在"越界/奇怪"姿态下标零 ✗ |

### 3 与 4 的常见坑

* **主控若是补丁版（`9a808cd9…`）** ✗ ⇒ **标零 100% 失败**（`HomeNumdone` 恒 2）
  ⇒ 先执行**回退原版**（见 §2）
* **某轴有驱动器故障**（如 J1 的 `0x8612 位置给定超限保护`）✗ ⇒ **使能与标零都会被拦**
  ⇒ **必须整柜断电**清掉（`clearAlarms` **不清**驱动器故障 ✗）
  ⇒ 实测：2026-10-10 15:22 J1 报 34322 ⇒ 标零停在 2；断电重启后 15:31 一次通过 ✓

## 2. 回退原版主控（只在这一步动文件，全程可回退 ✓）

```bash
C=/dobot/userdata/codesys
TS=$(date +%Y%m%d_%H%M%S)

# ① 备份当前（补丁版）
mkdir -p $C/BACKUP_patch_$TS
cp $C/allST/Application.app $C/allST/Application.crc $C/BACKUP_patch_$TS/

# ② 回退成原版
cp $C/BACKUP_ORIGINAL/Application.app $C/allST/Application.app
cp $C/BACKUP_ORIGINAL/Application.crc $C/allST/Application.crc
sync

# ③ 校验（必须是 8416cf0e…）
md5sum $C/allST/Application.app
```

**md5 对照表**

| 版本 | `Application.app` md5 |
|---|---|
| **原版（可标零 ✓）** | `8416cf0eee070a640702c077eb904b4e` |
| **六轴补丁（标零会失败 ✗）** | `9a808cd9dd8f3aa6adaa4de1a34eb9b3` |

> `Application.crc` 是 CODESYS 包壳 + `CRC32(app)` 小端，**必须成对替换** ✓

## 3. 重启 → 上使能 → 标零

```bash
# ① 重启控制器（或整柜断电 30 s 再上电）
# ② 上使能（示教器上点"使能"，或 API EnableRobot()）
# ③ 标零：
curl -X POST http://192.168.5.1:22000/calibrate/home      # 走 HTTP 22000，不占 30003 ✓
#   或在示教器/HMI 里点"标零"
```

**标零的机理（已解剖 ✓）**：控制器只把每轴 RxPDO 的 `0x607A 目标位置` 置 0（逐轴错开 ~0.136 s），
**驱动器自己**把 `0x6064 位置实际值` 重新定基到 0 —— **没有结果通道**，所以只能靠日志判读 ✓

## 4. ★ 判据：成功 / 失败怎么分（本次两次都实测过）

### ✅ 成功

```
[updateEncoderData#507] HomeNumdone : 0
[updateEncoderData#507] HomeNumdone : 2
[updateEncoderData#507] HomeNumdone : 4
[updateEncoderData#507] HomeNumdone : 6        ← ★ 四个台阶一路涨到 6
[updateEncoderData#509] servo calihome done ...   ← ★ 这一行是关键
```
**再验一层**（最有说服力 ✓）：
```
grep -a "PoseTrace: gActualPosition" .../logs/all/log | tail -1
# 六值应全部 ≈ 0   例：-0.001426, -0.060775, -0.016219, -0.014615, -0.000000, 0.009802  ✓
```

### ❌ 失败（**三种**典型，2026-10-10 三种都实测过 ✓）

| 现象 | 含义 | 处置 |
|---|---|---|
| **`HomeNumdone` 恒为 `2`** | **主控是补丁版** ✗（或该轴驱动故障） | 回退原版 + 重启；查 `logServoError` |
| **`HomeNumdone` 恒为 `0`**（`count` 从 9 递减到 0） | **★ 机器人没有使能** ✗ —— 最常见于"重启后没让示教器/DobotStudio 重连" | 见下方 §3a |
| **HTTP 返回 `{"status":false}`** | 控制器**拒绝**标零（状态不允许，例如"主控认为的位置"与"驱动器实际"不自洽） | 先使能、让两者一致，再重试 |

> **★ 停在 2 与停在 0 的区别很重要** ✓：
> * **停在 2 ⇒ 版本问题**（`controlMode` 正常、已使能，但主控读的位置对象不对）
> * **停在 0 ⇒ 没使能 / `controlMode = 0`**（与版本无关）

> **注意**：`homeEncoder.json` 的 `innerEncoder` **全 0 并不代表失败** ✓
> （2026-10-10 两次标零成功时，该文件里也都是全 0）—— **别用这条判据** ✗

## 3a. ★ 重启之后必须做的一步（2026-10-10 新增，关键 ✗）

**控制器重启后 `controlMode` 会变成 `0`** ✗ ⇒ 后果：

```
bfist controlMode=0                                     ← 日志里的证据
⇒ 29999/30003 全部返回 "Control mode is not TCP please change mode" ✗
⇒ EnableRobot() 发不出去 ⇒ 机器人未使能 ⇒ 标零卡在 HomeNumdone : 0 ✗
```

**⇒ 处置**（任一 ✓）：
* **在示教器 / DobotStudio 上连一下**（把控制模式带到 TCP）；
* **或直接在示教器上按【使能】** —— **标零只需要"已使能"** ✓，不必非得是 TCP ✓

**⇒ 日志判据**（看到这行就说明可以标零了 ✓）：
```
[monitorServoUptime#527] robot enabled ,begin to record enable robot time ...
```

> ⚠️ 手写 `POST /settings/controlMode {"controlMode":1}` **无效** ✗ ——
> 日志会回 `settControlMode#4458] Receive invalid control mode, set to default`，
> 那个路由只认示教器/DobotStudio 的格式 ✓

## 5. 装回六轴补丁 → 重启 → 验收

```bash
C=/dobot/userdata/codesys
cp $C/BACKUP_patch_*/Application.app $C/allST/Application.app     # 用 §2 备份的那个目录
cp $C/BACKUP_patch_*/Application.crc $C/allST/Application.crc
sync
md5sum $C/allST/Application.app        # 应为 9a808cd9dd8f3aa6adaa4de1a34eb9b3
```

**重启后验收**：
1. **三列一致** ✓：`nextPos` = `(PDO0x6062)` = `gActualPosition`
   （原版下 `nextPos`/`0x6062` 会显示**编码器绝对角** 8~21° ✗，**装补丁后才变 0** ✓）
2. **六轴 ≈ 0** ✓
3. **无新报警** ✓

## 6. 常见问题

| Q | A |
|---|---|
| **为什么必须原版？** | 标零的"逐轴完成"判据依赖原版读的那个位置对象；补丁把它换成了 `0x6064` ⇒ 判据失配 ⇒ 恒死在 2 ✓ |
| **标零会不会让手臂转一整圈？** | **不会** ✓。主控下发的物理量（`0x607A`/`0x6062`）一直是**正确的小角度**；"显示 365°"只是**显示层**的错 ✓（实测标零时只走 ~6°）|
| **3.1.5.0 下驱动器接受定基吗？** | **标零成功时接受** ✓（本次六轴 `gActual` 变成 ≈0）—— 但**断电后能否保持**仍需验证（3.1.5.0 的老毛病 ✗）|
| **标零后还需要做什么？** | ① 装补丁 + 重启；② **整柜断电 ≥30 s 再上电，复验六轴是否仍 ≈0**（持久性验收）✓ |
| **能跳过"回退原版"吗？** | **不能** ✗ —— 已复现多次（09-28 停在 2、10-10 15:22 又停在 2）|

## 7a. ★★ 2026-10-12：最干净的一次成功（含两条新经验）

### ★★★ 2026-11-03 追加：**"静止 30 秒"是精度的决定性因素**（实测对比）

| 标零时机 | 六轴 `gActual` | 最大偏差 |
|---|---|---|
| 11-03 10:05（**使能后立即标**） | `+0.0002, -0.0191, -0.0002, -0.0080, +0.0052, +0.0135` | **0.0190°** ✗ 且 `nextPos` 残余 -0.13/+0.31/+0.30/-0.36（示教器显示 0.1 级）|
| **11-03 10:21（★静止 30 秒后标★）** | `+0.0005, -0.0119, -0.0007, +0.0011, +0.0029, +0.0062` | **0.0119°** ✓✓ 且 `nextPos` 也 ≈0（示教器显示 0.00 级）|

**⇒ 结论** ✓：**标零是"抓一瞬间的位置"**✗ ⇒ **⇒ 使能后必须让手臂完全静止 ≥30 秒（手离开、别碰示教器）再标** ✓
**⇒ 一次就达标（0.0121°），不需要标多次** ✓ —— **⇒ 再标只会重新采样，可能更差** ✗

**⇒ 3.1.5.0 的精度下限 ≈ 0.011°（约 62 counts，1 count = 0.000178°）** ⇒ 压不到 0.001° ✗

### 结果

```

标零    16:02:29.388 → 16:02:30.288   HomeNumdone 0→2→4→6 + servo calihome done   ✓

        (PDO0x6062)      = 14.96, 10.43, 4.80, 2.32, 7.48, -19.80   （原版读编码器绝对角 ✓ 预期）
        gActualPosition  = -0.0000, -0.0116, -0.0016, -0.0007, -0.0000, -0.0012
```

### 新经验 ①：**J2 出现"假读数 + 负向限位"时，光放宽限位治不了根** ✗

现象：**J2 读数 −224° → −263°（越走越负）** ✗，同时报 `0x43 关节2负向限位` ✗，示教器点不动 ✗

* **临时手段**：把 `structure.json` 的 J2 限位放宽（`±178 → ±235 → ±280`）✓ —— **能让它暂时不越限** ✓
* **但读数会继续跑** ✗ ⇒ **放宽永远追不上** ✗
* **★ 真正的解法是标零** ✓：**10-12 标零后 J2 从 −263° 直接变成 −0.0116°** ✓✓

> **⚠️ 结构提醒**：`limits` 在 `structure.json` 的 **`/structure/limits`**（不是顶层 ✗），
> 6 个元素依次是 J1~J6；改它建议**行级定位**（JSON 解析后写回会改格式 ✓）。
> **改完必须重启**控制器才生效 ✓。

### 新经验 ②：**D8 与 3.1.5.0 的行为差异（又一次确认）**

| | 伺服 3.2.D.8 | 伺服 3.1.5.0 |
|---|---|---|
| 刷完后 `gActual` | 需要标零才归 0，但**驱动器接受定基** ✓ | **必须标零**；不标零就停在编码器原始系 ✗ |
| 界面显示 | 需要补丁才显示 0 ✓ | **必须补丁**（`nextPos` 读的是编码器绝对角 ✗，`gActual` 才是 0 ✓）|
| 标零前提 | 仍建议原版（与上一致 ✓）| **必须原版** ✗ |

**⇒ 关键观察（3.1.5.0 + 补丁）**：标零后 **`gActual` ≈0 ✓ 但 `nextPos` = 14.96/10.43/… ✗**
⇒ **界面/规划读的是 `nextPos`** ⇒ **⇒ 所以不装补丁的话，界面上看到的仍不是 0** ✗ ✓

## 8. 控制器上的现成工具（2026-10-10 新增）

```bash
sh /dobot/userdata/zero_cycle.sh status     # 只读：当前版本 + 上次标零 + 六轴 + 故障码
sh /dobot/userdata/zero_cycle.sh to-stock   # 备份当前 + 回退原版（之后需重启）
sh /dobot/userdata/zero_cycle.sh zero       # 发标零（自带"必须原版"防呆，不是原版就拒绝）
sh /dobot/userdata/zero_cycle.sh to-patch   # 装回六轴补丁（之后需重启）
```
> 版本 md5：**原版 `8416cf0eee070a640702c077eb904b4e`** / **补丁 `9a808cd9dd8f3aa6adaa4de1a34eb9b3`**
> ⚠️ `zero` 走 HTTP 22000 ✓，但**前提仍是机器人已使能**（`controlMode≠0`）✓
