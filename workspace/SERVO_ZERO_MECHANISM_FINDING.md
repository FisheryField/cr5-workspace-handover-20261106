## 0. 地址约定（**读本文件前必读，否则地址全部错位 0x10000**）

本轮开头花了大量时间纠正一个**系统性地址偏移**，它同时影响用户给的 Ghidra 工程和我自己早期的命令：

| 坐标系 | 定义 | 证据 |
|---|---|---|
| **真·flash（本文件全部使用）** | `真地址 = 0x08010000 + 文件偏移` | `LOAD_ADDR_VERDICT.txt` 三重实证：payload 对 `3.1.5.hex` 在 `0x08010000` 处 **100.0000%** 逐字节相等；`0x08000000` 会覆盖 bootloader；reset 向量只在 `0x08010000` 能干净解码 |
| **Ghidra 工程坐标** | 用户给的 `ghproj_servo_a/b` 是从 **ELF** 导入的，而该 ELF 的 `.text` 节头写着 `sh_addr = 0x08000000`（`mkelf.py` 生成）⇒ Ghidra 里所有地址**比真值低 0x10000** | 实测：Ghidra `mem 0x08005610` 的字节 == 真地址 `0x08015610` 的字节；而真 `0x08025610` 的字节是另一处 |
| **`.bin` 内部** | vector table 就在**文件偏移 0**（SP=`0x20017a40`/`0x20017f70`，Reset=`0x0801019d`）；**没有 0x20 字节头**（`mkelf.py` 注释里那个"0x20 字节厂商头"是它从**文件尾部**取的 0x20 字节） | 本文件 §6 正例自检 |

**本文件里凡是与旧文档对照的地方，旧文档地址 = 本文件地址 − 0x10000。**
（例：旧文档的真实写入点 `0x08015344/0x08014824`，本文件为 `0x08025344/0x08024824`；旧文档的 `0x20003DB0`，本文件为 `0x20013DB0`。）

### 0.1 正例自检（强制，本轮新增工具全部内置）

| 正例 | 期望 | 实测 |
|---|---|---|
| 版本串 `DS.3.1.5.0` | 真 `0x08027DCC` | ✅ `0x08027dcc` |
| 版本串 `DS.3.2.D.8` | 真 `0x08029250` | ✅ `0x08029250` |
| reset 向量 | `0x0801019c` 解出 `ldr r0,[pc,#0x18]` | ✅ 两版均如此 |
| `movw #0x4e20`（旧笔记已证存在） | D8 两处 | ✅ `0x080255A6`、`0x0802A6C4`（旧笔记 `0x080155A6/0x0801A6C4` +0x10000） |
| 双精度 `0.5` = `0x3FE0000000000000` | 3150 字面量池 | ✅ `0x08024BA4..0x08024BAB` |
| 真·flash 指令总数 | 旧笔记 147,119(3150) / 149,896(D8) | ✅ **148,648 / 151,248**（skipdata 线性扫描） |

> ⚠️ 本轮我自己**又踩了两次同类坑**，都靠正例自检抓出，留档：
> ① `movw` 解码器连续写错 **4 版**：把 `i` 位（bit10）当 0、`imm3` 掩码取错位，
> 导致"所有 32 位常量都不存在"的**静默假阴性**（正例 `0x4e20` 命中 0 处才暴露）。
> 最终可用判据：`((w1>>6) & 0x3DF) in (0x3D9, 0x3DB)`，正例 `0xF644 → 0x3D9`。
> ② 16 位 load/store 的 **imm5 在 bit10..6**，第一版写成 bit5..0，
> 于是 `ldrh r0,[r5,#2]`（真存在）报 0 处；改正后同一搜索返回 1229 处。

## 1. 结论摘要

### 1.1 【逐条读码 / 可证实】

**(A) 直接结论：参数 #38 / #189 / #39 在本轮搜索范围内**没有**以"槽号立即数"的形式进入位置计算链。**

- `ParaMapIndex = 38 / 189 / 39` 只来自厂商 CSV（`data/official/servoCSV/param.csv` 第 11 列），
  CSV 里 **`H01.17 编码器位置角=38`、`H01.18 编码器校零电流=39`、`H0C.02 编码器校零使能=189`** —— 已独立复核（§2.1）。
- 固件里**搜不到**这三个数作为位置链的立即数或字面量（§2.2 有正例对照）。
- 与既有结论一致：**厂商参数地址 `0x2000..0x200F` 在整个镜像里一处都没有**（作指令立即数 0 处、作字面量池 dword 0 处）。

**(B) 但参数**值**的存放位置找到了：逐轴参数块 `0x200073A0 + 轴号×0x60`（3150）。**
- 已实测：该基址被 **14 个字面量池**引用，加载点全部在 `0x0802xxxx`（编码器/位置子系统）。
- 同族块（同一段代码连续加载）：`+0x60` 步长的 `0x200073A0`、`+0x25C` 步长的 `0x20007400`、`+0x160` 步长的 `0x20007660`。
- `enc_type = (*(u8*)(0x200073A0 + 轴号*0x60) >> 4) & 7` —— **就是 `H01.13 编码器类型`**（默认 2 = 松下）。
  读到指令级：`0x08021606 ldrb r0,[r4,#0x32] ` / `0x08021758 ldrb.w r0,[r8]` → `ubfx r0,r0,#4,#3`。
- `0x200073A0 + 轴号*0x60 + 0x26` —— `0x26 = 38 = H01.17 的槽号`。**这是"槽号即结构偏移"这一形态的唯一实测吻合点，但是候选，不是结论（见 §1.2）。**

**(C) `0x6064`（位置实际值）生产链已在**真地址空间**闭环，两版共同形态（逐条读码）：**

```
D8  0x08025598  ldr.w r0,[r4,#0xa8]        ; 基准
    0x0802559e  mov.w r1,#0x20000
    0x080255a2  mla   r0,r1,fp,r0           ; + 0x20000*fp
    0x080255a6  movw  r1,#0x4e20            ; 20000
    0x080255aa  smull ...                   ; ×20000 的 64 位乘
    ...
    0x080255cc  bl    0x08010222            ; 64 位有符号除法（两版都有）
    0x080255d2  str.w r6,[r4,#0xb0]         ; 归一化结果
    0x080255e0  0698  ldr r0,[sp,#0x18]
    0x080255e2  0069  ldr r0,[r0,#0x10]     ; ★ 加一个来自另一对象的 +0x10
    0x080255e8  0144  add r1,r0
    0x080255ec  str.w r1,[r0,#0x234]        ; → 逐轴对象 +0x234
    0x080255f6  ldr r0,[pc,#0x34]           ; = 0x20000078（函数指针表）
    0x080255f8  ldr r2,[r0,#8]
    0x080255fc  blx r2                      ; 换算
    0x08025602  str.w r1,[r0,#0x238]        ; ★★★ 位置实际值 0x6064
```

⇒ **`+0x234` 的构造里有一项 `(*(char*)([sp+0x18])) + 0x10`，它来自另一个结构 —— 这是两版之间唯一一处"位置值多/少一个加项"的位置**（3150 的对应形态见 §4.2）。**该项的语义未定（候选）。**

**(D) 完成"取整"的那一步，两版**确为不同实现**（逐条读码，这是本轮最硬的差异）：**

| | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| 取整前 | `0x08025556 vldr s0,[r0,#0x10]` | `0x080249ba vldr s0,[r0,#0x10]` → `0x080249c2 vmov r0,s0` |
| **0.5 的形态** | **指令内立即数**：`0x0802555A vmov.f32 s1,0x3f000000` | **内存里的 8 字节双精度**：`0x080249CC vldr d0,[pc,#0x1d4]` → 真地址 `0x08024BA4 = 00 00 00 00 00 00 E0 3F` = `0x3FE0000000000000` = **double 0.5** |
| 运算 | `0x0802555E vsub.f32 s0,s0,s1`（硬件单精度） | `0x080249C4 bl 0x08010720`（f32→f64）→ `0x080249D4 bl 0x08010368`（软双精度加法） |
| 收敛 | `0x08025562 vcvt.s32.f32 s0,s0`（硬件） | `0x080249DC bl 0x080106e2`（软双精度→整数） |
| 存回 | `0x08025566 vstr s0,[r0,#0x14]` | `0x080249E2 str r0,[r1,#0x14]` |

- 独立佐证（字面量普查）：**双精度 `0.5` 的字面量池站点 —— 3150 = 2 处、D8 = 0 处**；
  **单精度 `0.5` 的字面量池站点 —— 3150 = 11 处、D8 = 4 处**。
  注意 D8 那处 0.5 **不在字面量池里**（是 `vmov.f32` 立即数），所以这里必须靠**逐条读码**才能得到结论 —— 普查单独会误导。

**(E) 3150 在位置链上多一个"商/余数分解"，D8 没有（逐条读码）。**

| | 3.2.D.8 | 3.1.5.0 |
|---|---|---|
| 该步 | 无（直接 `bl 0x08010222` 做 64 位除法后写 `+0xB0`） | `0x08024b48 sdiv r2,r0,r1` / `0x08024b4c mls r0,r1,r2,r0`（= `0x234 % 0xC`） |
| 结果去处 | — | `0x08024b52 ldr r1,[pc,#0x5c]` → `0x08024b54 str r0,[r1]`；**真地址 `0x20013DB0`** |
| 消费者 | — | 全部在 `0x08024bxx..0x08025bxx` 的**状态机内部**（既有结论 §12.23；本轮未改） |

> ⚠️ 这一条**不是**"零点差异"，因为现场实验（旧文档 §13.6）已**否证**"把 3150 那一项置零就能修好"。

### 1.2 【只是候选 / 未证】

| # | 候选 | 强度 | 缺什么 |
|---|---|---|---|
| C1 | `0x200073A0 + 轴×0x60 + 0x26` 就是 `H01.17 编码器位置角`（槽号 38 = 字节偏移 0x26） | **中**：数值吻合 + 该基址确实被编码器子系统大量引用 | 没有逐条读码证明"这个 +0x26 就是 H01.17"；也没有证明它参与位置计算 |
| C2 | `0x200073A0 + 轴×0x60` 字段组的 `+4 = Type`、`+0x34 = Value`（**与 EtherCAT SDO 条目布局同构，偏移逐项相同**） | 中 | 未把该结构与 SDO 写路径对起来 |
| C3 | `+0x234` 里那一项 `(*(obj+0x18?))+0x10` 就是"重新定基"的加项 | 中 | 该对象的基址与语义未定；两版该项都在，差异在别处 |
| C4 | D8 的零点来自**编码器预置/非易失参数**（不在位置链里） | 中（与旧结论同向） | 需要运行期 RAM 转储或编码器读寄存器 |
| C5 | 74.909° 由"3150 忽略某零偏、D8 应用它"造成 | 低（只是算术自洽） | 见 §5 |

### 1.3 【本轮新增的否定结论（同样有价值）】

- **N1**：Ghidra 工程（`ghproj_servo_a/b`）的地址**整体低 0x10000**；直接拿工程地址与旧笔记混用会得出完全错误的字节/指令。
  本轮由此产生的**一次真实误判**留档：我曾按 Ghidra 的 `mem 0x08025610` 读出 `8c 13 00 20 ...`
  并据此以为"位置链字面量池在 D8 与 3150 不同"——那其实是 `0x08015610` 的字节；真 `0x08025610`
  是 `8c 13 00 20 24 3d ...`。**只有 capstone（真地址）与正例自检能同时约束两边。**
- **N2**：`ghproj_*` 的**函数覆盖是不完整的**：Ghidra 只对部分区域建了指令。
  实例：真 `0x08022390` 有真实函数（我读到反汇编并成功反编译），
  但 Ghidra 在该处的"已有函数"是 `FUN_08012390`（真 `0x08022390` 的函数体＋一个内嵌函数），
  `funcs`/`refs` 常常返回 0；必须 `forcefn`（强制反汇编＋建函数）再用。
- **N3**（**本轮自己纠正过两次，最终版如下**）：参数槽号 38/189/39 **不是**"结构字节偏移"之外的可搜索量。
  * 第一版我用 `z_disp.py`（**只认 16 位 imm5 位移，imm<0x20**）搜 `0x26`，得到"0 处"，
    并据此写下"没有 `[rX,#0x26]` 这种访问形态"——**这是假的**：`0x26 ≥ 0x20`，压根不在 imm5 范围内，
    该扫描器对它**结构性看不见**。这正是本项目反复出现的"静默空结果"。
  * 改用 **`z_disp32.py`**（补上 32 位 `ldr.w/str.w/ldrsh.w` 的 imm12 形式，正例 `0x234` = 16 处 PASS）后：
    **`+0x26` 是真实存在的读取点** —— 3150 有 5 处、D8 有 6 处（清单见 §7.1）。
  * **但它们的基址都不是块 A**，而且**两版逐条读码后结论是"完全相同"**（§7.1）⇒
    "槽号 38 = 块 A + 0x26"**仍然只是数字巧合，未证实**。
  * `0xBD`(189) 只有 7 处 `adds rX,[rX,#0xbd]`（指针自增，与参数无关）。

## 2. 每条结论的证据

### 2.1 参数 #38 / #39 / #189 的来源（可复现）

工具：`tools/hparam_map.py` 的原始数据在 `data/servo_fw_samples/hparam_map.json`（259 条）。
独立复核命令：

```
python -c "d=open(r'data/official/servoCSV/param.csv','rb').read();t=d.decode('gbk',errors='replace');
import csv,io;rd=csv.reader(io.StringIO(t));hdr=next(rd);
[print(r[3],'map=',r[10],'def=',r[4],'name=',r[9]) for r in rd if len(r)>10 and r[3] in ('H01.13','H01.14','H01.15','H01.17','H01.18','H0C.02','H0A.12','H0A.14')]"
```

实测输出（GBK 解码后中文名）：

| ParaIndex | ParaMapIndex | 默认 | min/max | 名称 |
|---|---|---|---|---|
| H01.13 | 34 | 2 (松下) | 0–10 | 编码器类型 |
| H01.14 | 35 | 23 | 0–25 | 编码器单圈分辨率 |
| H01.15 | 36 | 16 | 0–99 | 编码器多圈分辨率 |
| **H01.17** | **38** | 90 | 0–360 | **编码器位置角** |
| **H01.18** | **39** | 100 | 0–200 | **编码器校零电流** |
| **H0C.02** | **189** | 0 | 0–1 | **编码器校零使能** |
| H0A.12 | 169 | 1 | 0–1 | 编码器电池故障使能 |
| H0A.14 | 171 | 0 | 0–1 | 多圈溢出处理选择 |

⇒ **`ParaMapIndex` 是厂商 CSV 自带的列，不是固件里的东西。** 要用它做固件证据，必须先证明固件按槽号索引。

### 2.2 固件里搜槽号（带正例对照）

工具：`tools/z_imm.py`（movw/movt/movs 立即数）、`tools/z_disp.py`（位移）、`tools/z_xref.py`（字面量池）。

```
python tools\z_imm.py 3150 d8 -- ctl=0x4e20 38 39 189 0x2001 0x200C 259
```

结果（关键行）：

```
3150  movw/movt decoded: 280  movs rD,#imm8: 13725
  [movw] 38   -> 0      [movw] 39 -> 0      [movw] 189 -> 0
  [movw] 0x2001 -> 0    [movw] 0x200C -> 0  [movw] 259 -> 0
  [movw] ctl=0x4e20 -> 0   ← 正例也 0 ⇒ 当时解码器还没修好（见 §0.1 陷阱①）
```

修好解码器后（`((w1>>6)&0x3DF)` 判据）：

```
3150  movw/movt decoded: 280      ← 仍偏低（真实约 459），故 movw 结论只用"正例 PASS 的那些"
  [movw] 0x4e20 -> 1  ✅ 正例 PASS（0x08029248）
```

⇒ **可用结论**：以 `0x4e20` 正例为闸门的那一版扫描器给出的 `#0x26/#0x27/#0xBD` 命中
（`z_disp.py`，位移路径，闸门 `#0x2 → 1229`）为：

```
python tools\z_disp.py 3150 0x26 0x27 0xbd
  16-bit imm5 forms: 0 / 0 / 0     (0xbd 超出 imm5 范围，本就为 0)
  add.w immediate  : 0 / 0 / 0
```

⇒ **没有** `[rX,#0x26]` / `[rX,#0xbd]` 形态。这不是"参数不存在"，而是"参数是通过**预计算基址指针**访问的"。

### 2.3 位置链的完整读码（两版对照）

工具+命令：

```
python tools\z_dis.py d8   0x08025550 60
python tools\z_dis.py 3150 0x08024980 60
python tools\z_dis.py 3150 0x08024b20 40
python tools\z_pool.py d8 0x08025618 0x0802561c 0x08025620 0x08025624 0x08025628 0x0802562c
```

**D8 位置链（真地址，节选）**

```
08025552  80 ed 04 1a   vstr.32 s2,[r0,#0x10]
08025556  90 ed 04 0a   vldr.32 s0,[r0,#0x10]
0802555a  f6 ee 00 0a   vmov.f32 s1,0x3f000000     ; 0.5f
0802555e  30 ee 60 0a   vsub.f32 s0,s0,s1
08025562  bd ee c0 0a   vcvt.s32.f32 s0,s0
08025566  80 ed 05 0a   vstr.32 s0,[r0,#0x14]
0802556a  2f 48         ldr r0,[pc,#0xbc]          ; ★ 池=0x08025628 -> 0x20003ED4
0802556c  40 69         ldr r0,[r0,#0x14]          ; [0x20003ED4+0x14]
0802556e  e9 68         ldr r1,[r5,#0xc]
08025570  48 43         muls r0,r1,r0
08025572  2d 49         ldr r1,[pc,#0xb4]          ; ★ 同一个池 0x08025628 -> 0x20003ED4
08025574  49 68         ldr r1,[r1,#4]             ; [0x20003ED4+0x04]
08025576  40 1a         subs r0,r0,r1
08025578  2b 49         ldr r1,[pc,#0xac]          ; ★ 同一个池 -> 0x20003ED4
0802557a  c9 68         ldr r1,[r1,#0xc]           ; [0x20003ED4+0x0C]
0802557c  08 44         add r0,r1
0802557e  2a 49         ldr r1,[pc,#0xa8]          ; ★ 同一个池 -> 0x20003ED4
08025580  c8 61         str r0,[r1,#0x1c]          ; [0x20003ED4+0x1C] := r0
08025582  29 48         ldr r0,[pc,#0xa4]          ; ★ 同一个池 -> 0x20003ED4
08025584  c0 69         ldr r0,[r0,#0x1c]
08025586  28 49         ldr r1,[pc,#0xa0]          ; ★ 同一个池 -> 0x20003ED4
08025588  09 6a         ldr r1,[r1,#0x20]          ; [0x20003ED4+0x20]
0802558a  40 1a         subs r0,r0,r1
0802558c  c4 f8 b0 00   str.w r0,[r4,#0xb0]        ; → 逐轴对象 +0xB0
```

> ⛔ **本节第一版写错了，已更正**：那 6 条 `ldr rX,[pc,#imm]` **全部指向同一个字面量池 dword**
> `0x08025628 = 0x20003ED4`（用 6 次 `((addr+4)&~3)+imm` 逐条算出来验证，见 §7.1 的
> `z_dis`/`z_pool` 命令）。所以它们是**同一个全局结构体 `0x20003ED4` 的不同字段**，
> **不是**六个不同的 RAM 全局；`0x20000078` 在这个函数里**只出现一次**（`0x080255F6`，取 `+8` 当函数指针），
> 旧稿里"`subs` 掉 `[0x20000078+0x20]`"**是错的，作废**。

⇒ 更正后的算式（真地址）：
```
x  = [r5+0xC] * [0x20003ED4+0x14] - [0x20003ED4+0x04] + [0x20003ED4+0x0C]   -> [0x20003ED4+0x1C]
```

* 块 A 是 **RAM**，不是 flash；**静态镜像里看不到它的内容**，

⇒ **本节结论（降级为候选）**：块 A `0x200073A0 + 轴×0x60` 确实被**编码器子系统大量引用**

> ★ 真正可搜的形态（§7.1 已用）：
> `z_disp32.py` 覆盖**32 位** `ldr.w/str.w/ldrsh.w` 的 imm12 位移 ——

## 4. 74.909° 能不能被解释？

### 4.1 算术自洽（**只是自洽，不是证据**）

```
scale = 360/(20000×101) = 1.7821782e-4 °/count
3.1.5.0 报 +55.692°  ⇒ 原始绝对计数 ≈ 312,493
D8      报 −19.217°  ⇒ 312,493 − 19.217/scale = 312,493 − 107,836 = 204,657？
```
⇒ **不对**：`(55.692 − (−19.217)) = 74.909° = 420,300 counts`，
而 `420300 / 20000 = 21.015` —— 不是干净的整数比，也不是 `2^n`。
**⇒ 这两个读数之间不存在简单的"整数计数平移 × 20000×101 比例"关系。**
（若两者是同一物理姿态的同一原始计数，则差必须落在**同一比例**上；
74.909° 落在比例上 ⇒ 计数差 420,300，超出单圈 2^23 的三分之一 ⇒ 除非两版的**多圈/单圈拼接方式**不同，否则只能解释为**读数时刻的姿态本来就不同**。）

**⇒ 结论：仅凭这两个数字，无法把 74.909° 归因到任何一处代码。**
用户给的"同一物理姿态、手臂完全没动"与"读数差 74.909°"要成立，
必须先排除一件事：**两次读数之间机械臂是否被下/上使能过**（旧文档已证：3150 **一下使能就丢定基**）。
J2 在旧实验里正是"D8"轴，D8 本应保持 —— 所以更可能是**3150 那一侧**在该姿态下报的是
**未定基的原始计数**，而两个读数并非同一基准。

### 4.2 与读码结果的一致性

读码结果表明：**位置链里没有任何"当前零点偏移"变量**（§2.3：链条是
`0x6064 → +0xA8/+fp/+sl → ×20000 ÷20000 → +0xB0 → + ([sp+0x18]+0x10) → +0x234 → 函数指针 → +0x238`，
全部是**比例与分解**，没有"减零点"这一步）。
⇒ **与"74.909° 不可能由位置链里的某个偏置造成"一致**，
⇒ 也**再次支持**旧结论：「定基发生在**编码器原始读数那一层**，不在软件位置链」。

**⇒ 因此本节给用户的答复是：那 74.909° 不是位置链能解释的差；它更可能是**
**① 两次读数之间 3150 一侧丢了定基（下/上使能）**，或 **② 编码器预置值本身不同**。
**这两个都需要运行期数据（SDO 时序 / 编码器寄存器）才能判定，纯静态做不到。**
