# 回零结果通道 —— 总线级解剖（2026-09-23）

> 数据源：codex 采集的两份 EtherCAT 总线抓包，归集在 `data/codex_b/ethercat_pcap/`。
> 分析脚本：`tools/ecat_decode.py`、`ecat_mailbox.py`、`ecat_events.py`、`ecat_j1block.py`、`ecat_rxtx.py`、`ecat_series.py`。
> 对象名来自控制器 codesys 日志里逐站的 PDO 映射写入记录（`data/codex_b/sdow_raw.txt`）。

---

## 0. 一句话结论

> **回零没有"结果通道"。** 控制器做的事就是：**把每轴 RxPDO 里的 `0x607A 目标位置` 置 0**，
> 然后驱动器自己把 `0x6064 位置实际值` 重新定基到 0。
> **两版控制器发的命令一模一样，差别全在驱动器跟不跟。**

---

## 1. 总线的真实结构

每周期 5~6 帧，1111 字节那帧的布局（已逐字节解码）：

```
ARMW 0x0910 (20B, 分布式时钟)  +  LWR 0x0100 (452B, RxPDO 主→从)
+ LRD 0x0200 (574B, TxPDO 从→主) + LRD 0x0008 (21B) + FPRD 0x0130 (14B) + BRD 0x0130 (14B)
= 1111 字节
```

邮箱（SM0 `0x1800` / SM1 `0x1A30`，各 512 B）**整份抓包里只出现 24 次，全部集中在标定窗口**。

## 3. `/calibrate/home` 的完整动作（逐帧实测）

以 `POST /calibrate/home` 到达控制器为 t=0：

| 时刻 | 动作 | 证据 |
|---|---|---|
| +0.006 … +0.697 s | 逐轴（站 1003→1008，间隔 0.136 s）邮箱 **SDO Upload（读取）`0x607C Home offset`** | 24 个邮箱帧 |
| +0.118 … +0.798 s | 逐轴把 RxPDO 的 **`0x607A 目标位置` 置 0** | LWR 数据 |
| +0.113 … +0.793 s | **3.2.D.8**：各轴 `0x6064` 随之变 0 | LRD 数据 |
| 同上 | **3.1.5.0**：`0x6064` **不变** | LRD 数据 |
| +0.9 s | 写 `homeEncoder.json` | 控制器日志 |

**SDO 读取的内容两版逐字节相同**（这推翻了它作为"结果通道"的可能）：

```
请求 (FPWR, ADO 0x1800):  40 7c 60 00   → CoE svc2, SDO cmd 0x40 = Upload Request, index 0x607C sub 0
响应 (FPRD, ADO 0x1A30):  43 7c 60 00 00 00 00 00 → cmd 0x43 = Upload Response, 值 = 0
两版都返回 0。
```

## 4. 两版的差别（决定性对照）

### 4.1 标定瞬间

| | `0x607A`（主站发） | `0x6064`（从站回） |
|---|---|---|
| **3.2.D.8** 标定前 | 598234 | 598234 |
| **3.2.D.8** 标定后 | 0 | **0**（+7 ms 内跟上，且保持） |
| **3.1.5.0** 标定前 | 45882 | 45882 |
| **3.1.5.0** 标定后 | 0 | **45882**（不跟） |

### 4.2 3.1.5.0 随后发生的事（这才是用户症状的直接来源）

| 相对时刻 | 事件 | J1 `0x6064` |
|---|---|---|
| POST + 0.118 s | 控制器置目标 0 | 45882（不动） |
| POST + 4.5 ~ 6 s | 下使能（日志 16:31:18.454） | 降到 **≈ -5 ~ 66**（≈0.01°，**短暂定了零**） |
| POST + **10.85 s** | **重新上使能**（日志 16:31:24.850） | **弹回 45877** ← **零点丢失** |

**⇒ 3.1.5.0 的定零是"易失"的：驱动器会短暂接受，一下使能/上使能就丢。**
**⇒ 3.2.D.8 的定零是"非易失"的**：标定后一路保持 0。

这与用户实机现象完全一致，也解释了 3.2.D.8 下重新上使能残留的 ~0.4° —— 那只是上使能时机械臂晃动的读数误差。

## 5. 由此得到的两条实用结论

### 5.1 现场判据（一行命令）

```bash
ssh root@192.168.5.1 "cat /dobot/userdata/project/settings/function/homeEncoder.json"
```

使能状态下点完"零点标定"，看 `innerEncoder`：**非全 0 = 正常；全 0 = 就是这个故障**。

### 5.2 固件版本可以从总线直接读出来

TxPDO 里每站都带一个 16 位版本字：`0x32D8` = 3.2.D.8，`0x3150` = 3.1.5.0。
⇒ **以后只要有总线抓包，就能逐轴确认实际跑的是哪版固件**，不必依赖控制器显示的版本串
（而我们已知那个显示来自 EEPROM/ESI，不可靠）。

---

## 5.3 ⚠️ 对"innerEncoder 是零偏置"的修正（2026-09-23 晚，在线反证）

在线设备最新一条 `homeEncoder.json`（2026-09-23 11:26:53）：
`innerEncoder = [-2506, 8, -2522, 2536, 2508, 2507]` ≈ ±0.45°，
而**标定刚做完时关节读数 = 0**。

若关节角 = (0x6064 − innerEncoder) × scale，此刻应读出 **−0.45°**，与实测 0 矛盾。
⇒ **`innerEncoder` 不参与运算，只是标定时刻 0x6064 的一份记录。**
⇒ **关节角 = 0x6064 × scale**，零点完全由驱动器维持。

这也意味着：用户观察到的重新上使能后 ~0.4° 残余，**确实是上使能时机臂晃动的读数误差**（不是 innerEncoder 造成的）。

## 6. 仍未解的一点（诚实标注）

`homeEncoder.json` 的 `innerEncoder` 为何在 3.1.5.0 上是 0：

- 3.2.D.8 记的是 **标定前的原始读数**（598234），等于当时 `0x607A`/`0x6064` 的值；
- 3.1.5.0 记的是 **0**，而同一时刻总线上 `0x6064` = 45882。

控制器在两版上执行的时序完全相同（都是 POST+0.9 s 写文件），所以"记早了/记晚了"解释不通。
**最可能的解释**：`caliHome` 从 `runtime+0x3110` 取的**不是 PDO 镜像，而是回零回调的返回值**；
3.1.5.0 的驱动器**没有正确应答回零命令**，控制器就把结果缓冲置 0。
这与"3.1.5.0 的定零易失"是同一个根因的两个表现。
**但这仍是推断，缺少直接观测——要证实需要在驱动器侧或控制器回调侧取证。**
