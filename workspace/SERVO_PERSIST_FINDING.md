## 1. ★ 卡点 A 已被官方文件回答 —— 不需要从固件里猜

`SERVO_FW_OD_FINDING.md` §4/§6/§7 把"OD 表项 → 厂商参数地址"列为**唯一卡点**，
并假设答案在 `0x080513cc` 那 6 个字面量里、或"参数地址是表内偏移的函数"。

**两者都不需要。厂商自己的参数表 `data/official/servoCSV/param.csv` 就是这张映射表**
（GBK 编码，**259 条** `H<组>.<序号>` 参数）。

| 列 | 含义 |
|---|---|
| `ParaIndex` | 参数名 `H00.00` … `H0E.12`（H 组 + 组内序号） |
| `ParaMapIndex` | 厂内参数映射索引 **0..259** |
| `ParaName` | 中文参数名（GBK） |
| `ParaValue/MIN/MAX/Unit/ReadOnly/EffectImmediate/SaftyLevel` | 默认值、范围、单位、只读、是否立即生效、安全等级 |

### 1.1 现场编码规则被官方表**逐字确认**

2026-09-18 从 HTTP 通道抓到的两条真实地址，在官方表里都对上：

```
H0C.00  map=187  ->  EtherCAT 0x200C:1    编码器… 实测 addr200C01 -> 0x200C:1  ✓
H01.17  map=38   ->  EtherCAT 0x2001:18   实测 addr200118 -> 0x2001:18        ✓
```

⇒ 规则钉死：**`H<gg>.<ss>` → EtherCAT index `0x20<gg>`、subIndex `ss+1`**，
而 `addr<hex(0x2000+组号)><两位十进制(组内序号+1)>` 只是**同一个地址的另一种拼法**。

### 1.2 ⚠️ 一处重要更正：`addr200C01` **不是零点参数**

`HANDOVER.md` / `HANDOVER_2.md` 一直把 `addr200C01` 当作零点相关地址在追。**它是"故障复位"**：

```
H0C.00  map=187  0x200C:1  故障复位           ro=False  默认 0:无操作
H0C.02  map=189  0x200C:3  编码器校零使能      ro=False  默认 0
```

⇒ 2026-09-18 那次"写 `addr200C01` = 0"是**下发一次故障复位**，
与零点写入无关 —— 这也解释了它为什么对关节值毫无影响。
**真正的零点候选参数在下表。**

## 2. ★ 新发现：固件里有一条完整的**非易失存储**路径

用 `tools/servo_flash_hunt.py` 在两版**都**找到完整的 STM32F4 flash HAL：

| 常量 | 含义 | 3.2.D.8 | 3.1.5.0 |
|---|---|---|---|
| `0x40023C00` | FLASH 寄存器块 | ✓ | ✓ |
| `0x40023C0C` | FLASH_CR | ✓ | ✓ |
| `0x40023C10` | FLASH_SR | ✓ | ✓ |
| `0x45670123` / `0xCDEF89AB` | **解锁密钥对** | ✓ | ✓ |

**解锁函数各只有一个调用者 ⇒ 那条调用链就是"存档"例程**：

```
3.2.D.8   解锁 @0x080044ec   调用者 @0x08001862   例程入口 0x080017d0   magic 字面量 @0x08001854
3.1.5.0   解锁 @0x0800416c   调用者 @0x08001862*  例程入口 0x08001810   magic 字面量 @0x08001894
```

例程行为（反汇编，`tools/thumb_dis.py`）：

1. 在栈上准备 **24 字节（0x18）** 记录；
2. 取一个 RAM 指针（3.2.D.8：`[0x20003470]`），与**高水位常量 `0x08080000`** 相减；
3. 与当前记录比较，**相同就直接返回 0x800D（跳过，不重复写）**；
4. 不同则把 **magic `0xBE6D4A8B`** 放进记录；
5. **逐字节**调用 `HAL_FLASH_Program(0x0800C000 + i)` 写 **24 字节**；
6. 调用 lock（3.2.D.8 `0x0800433c`）收尾。

⇒ 即一块 **追加式（log-structured）flash 区**：新纪录写在 `0x0800C000` 起，
高水位推进到 `0x08080000` 后应当回绕/擦除。
**这是驱动器侧真实存在的"把参数存到 flash"能力**，与 AGENTS.md 里
"持久化很可能发生在驱动器内部，不走 OD、不产生日志"的推测**方向一致**。

## 3. ⛔ 但两版的存档例程**几乎完全相同** —— "固件差异 = flash 持久化"被否证

`tools/servo_persist_cmp2.py`（以 magic 为锚，不猜偏移）：

| 度量 | 结果 |
|---|---|
| 例程入口 | `0x080017d0` vs `0x08001810`（**+0x40**） |
| 指令条数 | **58 vs 58** |
| 逐条（助记符+寻址形态）一致 | **56 / 58 = 96.6%** |
| 那 2 处"差异" | 都在**字面量池数据**上，不是代码 |
| 整个 HAL 段平移 | 常量 **−0x29C**（`0x080044ec→0x0800416c` 等全部自洽） |

⇒ **两版的 flash 存档例程是同一个函数、同一套 magic、同样写 24 字节到 `0x0800C000`。**
所以：

> **U5「3.2.D.8 到底改了什么」的答案不在"有没有 flash 持久化"上 —— 两版都有。**

### 3.1 参数持久化子系统：两版**同构**（已用"按角色比对"证实）

顺着 magic `0xA1B2C3D4` 锚点，两版都能定位到**同一套"参数掉电保存"子系统**：

```
0x080045A8  (D8 地址)  掉电保存 API
    若 [flag] != 0 → 立即持久化；否则暂存到 RAM 缓冲，容量 0x180，溢出返回 0x8003
0x08001708  (D8 地址)  持久化例程（上面那个 API 的唯一调用者）
    要求长度 ≥ 0x20；校验 buffer[0] == 0xA1B2C3D4
    跳过 0x20 字节头，其余**按字**写入 flash，指针 [wptr] 每字 +4
    坏 magic/长度 → 0x800D
0x080017D0  (D8 地址)  日志追加：0x18 字节记录，magic 0xBE6D4A8B，写到 0x0800C000
0x08009BF8  扇区分类器（0x08004000..0x08100000 → 0/8/…/0x58）
```

**按角色（而不是按地址）逐条比对两版持久化例程**（`tools/servo_persist_roles.py`）：

| 度量 | 结果 |
|---|---|
| 指令条数 | 126 vs 126 |
| 助记符+完整操作数一致 | 100 / 126 = 79.4% |
| **那 26 处不一致全部是 `b` / `bl` / `blt` / `cbz` 的绝对目标地址** | ⇒ **纯重定位，控制流与常量完全相同** |
| RAM 全局用量 | **各 12 个，角色一一对应** |

> ## ⛔ 我先前写下的"v3.1.5.0 缺 5 个 RAM 常量"是**方法错误，已作废**
>
> 我一度用"同一批 RAM 绝对地址在两版里是否存在"来判定差异，得出
> "v3.1.5.0 **缺** `0x20009714 / 0x200096E4 / 0x2000348C / 0x20003494 / 0x20003470`"
> —— 看起来像"3.1.5.0 根本没有参数持久化"。
>
> **这是假的。** 真相是两版**都有**这套代码，只是**链接器把 RAM 全局变量放在了不同地址**：
>
> | 角色 | 3.2.D.8 | 3.1.5.0 |
> |---|---|---|
> | 暂存镜像目标 | `0x200096E4` | `0x200091FC` |
> | 标志字节 | `0x2000348C` | `0x20003384` |
> | 写指针 | `0x20003470` | `0x20003380` |
>
> **⇒ 跨构建比对时，绝不能用 RAM 绝对地址判定"有无"**；必须按代码结构/角色比对。
> （残余不确定：两版暂存缓冲的**容量**都是 `0x180` 吗？我只在 D8 侧确认过，见 §8。）

（这同时修正了 `HANDOVER_2.md` §4.1 的方向：不必再从 OD 表里找地址映射，
也不必把 flash 路径当成版本差异的候选。）

## 6. 顺手修掉的一个文档缺陷

`SERVO_FW_OD_FINDING.md` **含 13 个控制字节**（10× NUL、3× BEL、1× TAB），
是写入时的转义 bug：**每个控制字符都顶掉了某个字面量的首字母** ——

```
TAB(0x09) 顶掉 't'  ->  <TAB>ools/od_refs2.py    应为  tools/od_refs2.py
BEL(0x07) 顶掉 'a'  ->  <BEL>ddr200C01           应为  addr200C01
NUL(0x00) 顶掉 '0'  ->  <NUL>x080513cc           应为  0x080513cc
```

后果很实际：**`read` 工具拒读该文件（报 "binary file"）、ripgrep 直接跳过它** ——
即那份交接文档在多数工具里是"隐形"的。已用 `tools/fix_od_finding.py --apply` 修复
（14 处替换全部断言通过、字节数不变、自动备份 `.bak_20260923_212848`），
现在 `read` 与 grep 都能正常读它。

> ⚠️ 提醒：**今后写文档别让 `\t` / `\a` / `\0` 这类转义碰字面量**；
> 本次损坏正好都发生在 `0x…`、`addr…`、`tools/…` 这些**最关键的标识符**上。

## 8. 诚实清单

**事实**
* 官方 `param.csv` 有 259 条 H 参数，含 `ParaMapIndex`；`H0C.00→0x200C:1`、`H01.17→0x2001:18`
  **与现场抓包逐字吻合** ⇒ 编码规则 `0x20<组>:<序号+1>` 由官方表确认。
* `addr200C01` = `H0C.00` = **故障复位**（不是零点参数）。
* 两版固件都有完整 STM32F4 flash HAL + magic `0xBE6D4A8B` + 写 24 B 到 `0x0800C000` 的存档例程。
* 两条存档例程 **58 vs 58 条指令、96.6% 相同** ⇒ flash 路径**不是**版本差异所在。
* OD 表记录第一字节即 type 码；平坦 6 字节网格不成立。
* `SERVO_FW_OD_FINDING.md` 原有 13 个控制字节，修复后字节数不变。

**假设 / 未验证**
* `H01.17`（编码器位置角，默认 90）是零点偏置的载体 —— **未验证**。
* `H0C.02`（编码器校零使能）是 `cali home` 的实际落点 —— **未验证**，但是新增的强候选。
* flash 区 `0x0800C000..0x08080000` 的**记录语义**（0x18 字节记录里除 magic 外各字段、
  0x20 字节头里除 `0xA1B2C3D4` 外各字段）**未解**。
* 参数持久化暂存缓冲的容量常量 `0x180` 只在 **3.2.D.8** 侧确认过；3.1.5.0 侧的对应常量**未核对**。
* 两版持久化例程"同构"是按助记符+操作数形态算的，**未做逐字节等价证明**。

**已作废**
* ~~"v3.1.5.0 缺 `0x20009714` 等 5 个 RAM 常量 ⇒ 3.1.5.0 没有参数持久化"~~ ——
  **方法错误**：跨构建不能按 RAM 绝对地址判有无，两版都有这套代码（地址不同）。
* ~~"参数地址是 OD 表内偏移的函数"~~ / ~~"§7.2 的 9 字节记录、低字节 `0x20` 是地址编码"~~ ——
  地址由**厂商参数表 + `0x20<组>` 规则**决定，与 OD 表无关。
* ~~"固件版本差异在于 flash 持久化有无"~~ —— 两版都有，且按角色比对同构。
* ~~`addr200C01` 与零点有关~~ —— 它是故障复位。
