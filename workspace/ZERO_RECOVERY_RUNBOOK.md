# CR5 零点恢复 runbook（3.1.5.0 六轴 + 不触发 0x86 报警）

> 2026-09-24 现场实测 + 代码级证据。目标状态：**六轴伺服 `DS.3.1.5.0`、零点有效、关节显示 0、上使能不报警**。

---

## 0. 一句话结论

**先回退成原版主控 → 上使能 → 标零 → 再把六轴补丁装回去。**
顺序反了就一定会撞 0x86；顺序对了两步都不会报。

### 0b. ★★ 硬约束：标零必须在**原版**主控下做（2026-09-25 实测）

| 主控版本 | `cali home` 结果 |
|---|---|
| **原版**（`8416cf0e…`） | `HomeNumdone : 0 → 2 → 4 → 6` ⇒ **`servo calihome done ...`**，六轴归 0 ✓ |
| **补丁版**（`9a808cd9…`） | `HomeNumdone` **死在 2**（轮询 20 次仍是 2），3 s 超时失败，六轴读数一点没变 ✗ |

复现：2026-09-25 18:04 / 18:09（补丁版：使能成功、六轴 `OP-ENABLED`、`0x603F = 0`，
`HomeNumdone` 恒 2）vs 18:13（换回原版 + 重启，**同一姿态一次通过 0→2→4→6**）。
⇒ `cali home` 的逐轴完成判据依赖「原版读的那个位置对象」，补丁把它换掉了。
⇒ **顺序永远只能是**：回退原版 → 重启 →（机械对齐）→ 上使能 → 标零 → 装补丁 → 重启 → 验收。
反过来（先装补丁再标零）**一定失败**，别浪费现场时间。

### 0c. 同轮踩到的两个坑

- **驱动器故障会拦住使能**：故障时使能被直接拒绝（`settControlMode : enable` 后紧跟
  `exist an error not collision, can't enable robot`），标零则卡在 `HomeNumdone : 2`。
  **判据**：逐轴读 `0x603F`，非 0 即故障（本次 J1 出现 `0x8612` = 厂商 `alarm_servo` 34322
  「位置给定超范围保护」）。复位：厂商参数 **`H0C.00`（`0x200C:01`）写 1**
  （`POST /settings/modifyServoParams`，payload 形状就是 `servoParams.json` 里那种），或整柜断电。
  **`clearAlarms` 只清报警、不清驱动器故障。**
- **只读 SDO 的返回值在日志 `readSDO#...` 行里** —— 抓「新鲜行」时 grep 模式**必须包含 `readSDO`**，
  否则解析全空、会误报成 `0x0000`（本次踩过）。

## 1. 报警 0x86 到底是什么（代码级判据，已逐条读码）

`libalgs_framework.so` → `ServoControl()` @`0x976fc`，循环 `0x99c54–0x99c70`：

```
vldmia r4!,{d6}          ; A = gSysParams+0x168   （控制器认为机器人在哪，f64[6]）
vldmia r6!,{d7}          ; B = 伺服上报的关节姿态   （f64[6]，GOT 槽 0x144c）
vsub.f64 d7,d6,d7
vabs.f64 d7,d7
vcmpe.f64 d7,d8          ; d8 = 5.0（硬编码，vmov.f64 d8,#5.0 @0x99c3a）
ble  → 下一个关节
else → movs r0,#0x86 ; bl AlarmSysSetBit(@0x9208c)   → 置位并强制下使能
```

**⇒ 判据就是一句话：`|控制器认为的姿态 − 伺服上报的姿态| > 5.0°（任一关节）` ⇒ 报 0x86「上使能关节位置偏差过大」⇒ 自动下使能。**
（`alarm_controller.json` id 134；`gSysParams+0x160` 的计数器让它在使能后 ~0.2 s 才检查，所以现象是「上使能成功 → 0.2 s 后报警掉使能」。）

### 谁决定「伺服上报的姿态」

由 PLC 应用里那六张 TxPDO 映射表决定（`Application.app`，每轴表最后一项）：

| 版本 | 最后一项 | 上报值 = | 未使能 | 已使能 |
|---|---|---|---|---|
| **原版** | `0x6062` | 驱动器 `0x6062` | = `0x6064`（定基值） | **= 编码器原始绝对角**（3.1.5.0 特征） |
| **补丁版** | `0x6064` | 驱动器 `0x6064` | 定基值 | 定基值 |

- `0x6064` = 原始绝对角 − 零点基值（两版固件、两种状态下都定基）。
- 3.1.5.0 的 `0x6062` **一使能就变成原始绝对角**（D8 不会，这就是当年"零点不保持"的真凶）。

### 于是三种状态自洽解释全部现象

| 状态 | 上报值 | 真实姿态 | 差值 | 结果 |
|---|---|---|---|---|
| 原版 + 零点坏 | 原始绝对角（8–35°） | 8–35° | ≈0 | **不报警**（但显示值不是 0） |
| 补丁 + 零点坏 | 定基值（110–144°） | 8–35° | **119–139°** | **报警 0x86** |
| 补丁 + 零点好 | 0 | 0 | ≈0 | **不报警，且显示 0** ← 目标状态 |

本机实测（2026-09-24）：

| | J1 | J2 | J3 | J4 | J5 | J6 |
|---|---|---|---|---|---|---|
| 补丁版·未使能显示 | +110.98 | −45.75 | +144.64 | +58.79 | −131.45 | −0.016 |
| 原版·**使能后**显示 | **−8.09** | **+11.18** | **+35.35** | **+2.06** | **+7.39** | **+20.49** |

原版使能后读到的就是编码器绝对角 ⇒ 与真实姿态一致 ⇒ 差值 <5° ⇒ 过。
（J6 的零点一直是好的：补丁版下 `0x6064`≈0，所以它一直没报过 —— 这就是"J6 单独装补丁却好使"的原因。）

## 2. 为什么补丁是必须的（不能只用原版）

原版在 3.1.5.0 上使能后上报的是**编码器绝对角**（8–35°），不是关节真值 —— 这就是你要修的「关节值不是 0」。
补丁把上报源换成 `0x6064`，只要**零点基值有效**，上报值就是正确的关节角（参考位姿下 = 0）。
所以最终必须回到「**零点有效 + 补丁**」，两者缺一不可。

### 关键前提（实测，别踩）

- **标零必须在使能状态下做**：机器人下使能时发标零，驱动器不响应（日志 `HomeNumdone : 0` 一路到 0，然后失败）。
- **每次「上使能 → 被报警掉使能」都会让 J3 下坠 5–11°**（抱闸释放那一瞬间没有有效保持力矩）。所以在零点没修好之前，**不要反复试着上使能**。
- 标零用的是 CiA402 回零方式 `0x6098 = 35`（当前位姿设为原点），**不会让机械臂动**。
- 标零后驱动器把 `0x6064` 重新定基到 0，**掉电保持**（3.1.5.0 也保持；之前"不保持"是读错了对象 `0x6062`）。

## 4. 最终验收（第 5 步）

装完补丁、重启之后，**你上使能，我这边盯报警**：

```powershell
cd D:\mydata\workspace
& "C:\Program Files\PyManager\python.exe" tools\watch_enable.py 90
# 它会等你 90 s：你在这期间上使能，它逐 5 s 轮询日志，最后给出判决：
#   OK - enable 保持且没有 0x86   /   alarm 0x86 DID fire（并提示回退命令）
```

然后逐条确认：

1. 上使能 → 读 `192.168.5.1:30005` 六个关节值：应**全 ≈0**（原版下会读到 8–35° 的绝对角，那是补丁没装的标志）。
2. 使能保持 ≥30 s，日志里**没有新的** `index=0x86`。
3. 下使能 → 上使能，值不变。
4. **整柜断电 30 s → 上电 → 上使能 → 等机械臂完全静止 ≥30 s → 记 V2**；与断电前 V1 的 `|V1−V2|` 应 ≲ 0.05°。
5. **点动每一个关节**（补丁改变了 PLC 第 2 项字段的含义，只有 J6 被现场验证过）：确认运动、限位、状态显示都正常。

随时可以只读复核：`python tools\apply_patch_now.py --verify`（关节值 + `0x1A00` 映射 + 0x86 统计）。
