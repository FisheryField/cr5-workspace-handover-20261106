## 1. ✅ 表的位置与记录结构（已钉死）

**位置**：flash **`0x08024991` .. `0x0802642e`**（6,813 B），共 **97 条**可解析条目。

**记录布局**（`name\0` 之后紧跟 6 字节，每字段 2 字节小端、高字节恒为 0）：

```
+0x00  "Object name\0"           ASCII，NUL 结尾
...    6 字节记录：
         +0  u16 type   0x02=i8 0x03=i16 0x04=i32 0x05=u8 0x06=u16 0x07=u32
         +2  u16 bits   8 / 16 / 32
         +4  u16 attr   访问权限位域：0x0007=读写，0x0087=只读（另见 0x003f/0x007f/0x000f）
```

例（原始字节 → 解读）：
```
"Control Word\0"           [06 00 10 00 87 00]  -> u16 / 16bit / attr=0x0087 只读
"Target Position\0"        [04 00 20 00 07 00]  -> i32 / 32bit / attr=0x0007 读写
"Following error window\0" [06 00 10 00 3f 00]  -> u16 / 16bit / attr=0x003f
```

## 4. ⚠️ 关键结论：这张表**不含**参数地址

**表里既没有对象 index，也没有厂商参数地址**（例如 `H0004` 那类编码）。
只有 名字 + 类型 + 位长 + 权限。

⇒ **"表项 → 真实参数地址"的映射由代码算出来，或在另一张数组里。**
这是下一步的目标，也是本次**没有**解出的部分。

### 4.1 已排除的找法

* 字面量池里指向本表的 32 位字：**全镜像只有 6 个**，都在 `0x08051300-0x08052800`
  （那块是"代码+字面量混排"）：
  ```
  0x080513cc -> 0x08024945    0x080513f4 -> 0x08024d15
  0x08052520 -> 0x08025f39    0x080527a4 -> 0x08025eed
  0x080527a8 -> 0x08025f11    0x080527b4 -> 0x08025991
  ```
  这些目标**不是条目开头**（落在名字串中间）⇒ 是**按偏移索引**进去的，不是逐条引用表项。
  **"按偏移索引"这条线索很重要：参数地址很可能就是"表内偏移"的函数。**
* 搜"指向条目名的指针字"：**0 个** ⇒ 表不是指针数组组织的。

## 7. 本轮追加：描述符是**内联**的，且记录带一列额外信息

### 7.1 反查字面量读取者 → 无（说明是内联描述符）

用 tools/od_refs2.py 查那 6 个"指向 OD 表内"的字面量（如 0x080513cc），
结果 **0 个读者** —— 全镜像 8,143 个 ldr rX,[pc,#n] 站点里没有任何一条的**有效地址**等于它们。
⇒ 这些字面量不是"被 PC 相对加载的常量池"，而是**内联在数据结构里**（对着数据当表用）。

周围结构（每 12 字节一组，模式很规整）：
`
  0x080513c0: 0x0801daf0   0x09801401   0x08024945   <- 第1组
  0x080513cc: 0x08030a39   0x16c50c78   0x0e610802
  0x080513d8: 0x4cc90802   0x0a181402   0x08023efd   <- 又出现 flash 指针
  ...
  0x080513f4: 0x08024d15   0x8824c709   0x0802ad0a
`
0x09801401 的低字节 0x09 很可疑 —— 若它是**长度/项数字段**，9 项 × 4 B = 36 B 恰好是这个步长，
与下面 7.2 的"9 字节记录"互相印证。

### 7.2 追加观察：OD 记录后面还跟着一列（**候选的参数地址编码，待验证**）

把名字之后的字节按 **9 字节** 看（而不是 6 字节），所有 OD 条目都自洽：

`
Home offset            20 00 05 00 08 00 07 00 04     -> ? 05(u8) 08bit attr=0x0007  idx=0x0004
Facturer_specified1    20 00 05 00 08 00 3f 00 07     -> ? 05(u8) 08bit attr=0x003f  idx=0x0007
Modes of Operation D.  20 00 02 00 08 00 87 00 04     -> ? 02(i8) 08bit attr=0x0087  idx=0x0004
`

⚠️ **尚未独立验证**，但值得注意：**低字节 0x20 出现在每一条上**，
而现场抓包已知的编码是 addr + hex(0x2000 + H组号) + 两位十进制(组内序号+1)
（addr200C01 → 0x200C:1、addr200118 → 0x2001:18）。
**0x20 与地址里的 0x2000 高字节同形** ⇒ 强烈提示这里有对应关系。

**验证方法（下一步）**：
1. 用 9 字节布局重解整张表，看 idx 字段是否**连续/无重复**（真索引应如此）；
2. 与现场 servoParams.json / homeEncoder.json 里出现过的地址（0x200C:1、0x2001:18）
   比对是否能对上；
3. 对上即可确认"OD 表项 → 厂商参数地址"的映射规则 —— **这就打通了唯一卡点**。

> ⚠️ 这一节是**观察 + 假设**，不是结论。在 §7.2 的三步验证做完之前，
> 不要把 0x20 当成已确认的编码。
