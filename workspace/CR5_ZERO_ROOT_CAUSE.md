# CR5 机械臂「零点/回零异常」底层原因整理

> 归档时间：2026-09-27 ｜ 素材来源：9/16–9/27 全部现场实验、总线抓包、固件逆向、厂商参数表
> 结论先行：**不是主控的错，是驱动器（固件 3.1.5.0）不接受"定基"，导致主控与驱动器处在两套相差几十度的参考系里。**

---

## 一、现象（可观察）

| # | 现象 | 观测方式 |
|---|---|---|
| 1 | **上使能后手臂"自动回零"**：几秒内被开走几十度 | 目视 + `GetAngle()`/反馈流 |
| 2 | **或上使能后立刻掉使能，手臂下坠**（J2 实测掉了 16.5°） | 日志 `robot disabled … this enable last 0 sec` |

| 4 | 报警：`0x8612`(34322 位置给定超范围)、`0x63`(99 关节2轴状态错误)、`249/250`(稳态误差过大) | `GetErrorID()` |
| 5 | `homeEncoder.json` 的 `innerEncoder` **恒为 0** | 控制箱文件 |

## 二、底层原因（一句话 + 三步机制）

**一句话**：驱动器固件 **3.1.5.0 不接受主控下发的"定基"（re-base）**——它的 `0x6064 位置实际值`永远停留在**编码器原始绝对计数系**；而主控（`0x6062`、规划、零点、界面）工作在**自己建立并持久化的"定基系"**里。两套参考系相差几十度。

**三步机制**：

```
① 主控在"定基系"里发目标（例如"去 0"）
   驱动器按"原始系"解释这个目标 ⇒ 差值巨大
   ⇒ 手臂被驱动到错误位置 = 用户看到的"自动回零 / 被开走" ✗

② 驱动器发现指令越界 ⇒ 报 0x8612「位置给定超范围」
   ⇒ 主控 0 秒内下使能
   ⇒ 刹车释放 ⇒ 重力做功 ⇒ 手臂下坠（J2 −16.5°）✗

③ 主控从总线读回的实际值仍在"原始系"
   ⇒ 与主控内部信念不一致 ⇒ 界面数值乱跳 ✗
```

### 3.6 编码器硬件事实（厂商每轴参数表 `J1..J6.csv`）

| 参数 | 值 | 含义 |
|---|---|---|
| H1.13 编码器类型 | **5 = BiSS-C** | 不是 param.csv 默认的"松下=2" |
| H1.14 单圈分辨率 | **19 位** | |
| **H1.15 多圈分辨率** | **0** | **没有多圈计数！** |
| HA.12 编码器电池故障使能 | 1 | **确实有电池** |
| H1.17 编码器位置角 | J1=352、J2~J6=330 | 逐轴标定值 |
| HC.02 校零使能 | **六轴全 0** | "校零"从未被触发过 |

⇒ **单圈绝对 + 无多圈 + 靠电池** ⇒ **关节绝对位置必须由"电池保持的圈数 + 一个偏置"合成** ⇒ **"定基"就是这个偏置被锚定的动作**；
⇒ 该偏置**掉电不丢**，且**不在应用 flash 里**（`3.1.5.hex` 的 `0x0800C000`、`0x08080000` 两处全 FF ✓）⇒ **只能落在编码器内部 / 驱动器非易失层**。

### 3.7 固件逆向结论：位置链里没有"零点变量"

- 两版固件的 `0x6064` 生产链**已闭环读出**：`+0xA8（基准）→ ×20000÷20000 归一化 → +0xB0 → +[sp+0x18]+0x10 → +0x234 → 经函数指针 → +0x238（0x6064）`；
- **逐条读码确认：链条里没有任何"零点/偏移"变量** ✗ —— `0x6064` 是「原始计数 × 常量比例」的**纯函数**；
- ⇒ **软件侧根本不参与定基** ⇒ **定基必然发生在编码器 preset 那一层**（外设/非易失交互，纯静态不可见 ✗）。

## 四、已被排除的假设（避免重复投入）

| 假设 | 排除依据 |
|---|---|
| 取整实现差异（D8 硬件单精度 vs 3150 软件双精度） | **刷进 J2 实测：读数一分未变** ✗（补丁本身正确、反汇编已回读验证 ✓） |
| `+0x234` 多出的 `[0x20013DB0+0x18]` 修正项 | **现场实测无效** ✗（9/24 否证） |
| 参数持久化子系统差异 | 两版**按角色逐条同构** ✗（126 vs 126 条指令，差异全是重定位） |
| 位置分解方式（就地 vs 集中结构 + 状态机） | 判别式双向失效 ⇒ **未证实** ✗ |
| 厂商参数 `H01.17/H0C.02/H01.18` 直接读写 | 该通道**不回答** ✗（HTTP SDO 对本固件无效；写路由一律 400/挂死 ✗） |
| 主控 PDO 补丁（让界面读 `0x6064`） | 只修**显示层** ✗，改不了驱动器实际值 ⇒ **治标不治本** |
| 主控改用原始系（撤补丁 = 方案 C） | **不可行** ✗：驱动器位置环仍以 `0x6064`（原始系）为实际 ⇒ 两世界仍对不上；且 C 等价于"回到故障原状" |
| `0x6007`(24583) 报警 | **独立问题**：面板开关被按下 ✓（已复位解决） |

## 五、现状与能力边界

**主控侧能做的（都已做）**：
- 零点在**控制器侧**建立成功且**扛断电** ✓（重启后最大偏差 0.019°）；
- PDO 补丁让界面数值取定基值 ✓；稳态误差阈值放宽 ✓；RoboDK 脚本两处 bug 修复 ✓。

**这些都改不了"驱动器实际值在原始系"** ✗ ⇒ **治标**。

**唯一被实测证明有效**：**六轴伺服刷 `3.2.D.8`** ✓（但与本机"最终必须 3.1.5.0"的要求冲突）。

## 六、若要在 3.1.5.0 上继续突破，需要什么

1. **把控制器升回 3.5.6.1** ✓ —— 现在的 3.5.4.1 **没有** `readServoParams` 那条 HTTP SDO 通道（实测 HTTPERR ✗），厂商维护工具的参数读写也依赖它；
2. 读出驱动器原始对象：**`0x6062` / `0x6064` / `0x603F`（故障码）** ⇒ 把"两系差多少"用驱动器自己的数定死；
3. 用**厂商维护工具**读/写 **`H01.17 编码器位置角`**、**`H0C.02 编码器校零使能`** ⇒ 试"触发一次校零"（这是唯一还没试过的、且与"定基"直接相关的手段）；
4. 若还能拿到一台 D8 机器的**同一参数表**做对照 ⇒ 直接对比"哪个参数让 D8 接受定基"，这是最短路径。
